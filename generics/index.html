泛型与字典传递：Go 1.26.5 源码分析

TIP

先抓住主干 Go 泛型不是 C++ 那种”每个类型参数生成一份代码”的完全单态化，也不是 Java 那种”全擦成 Object”的装箱，而是两者混合：

  1. GC shape 分组（stenciling）：把”内存布局和 GC 行为相同”的类型归为一个 shape（所有指针一个 shape，int64/uint64/float64 一个 shape，……），每个 shape 生成一份函数机器码。
  2. 字典传递（dictionary）：泛型函数被调用时，编译器额外传入一个字典指针，里面装着具体类型的 *abi.Type、itab、方法函数值、子字典等——所有需要”知道具体类型”的操作都查字典。

结果是：Max[int] 和 Max[uint64] 可能共用一份机器码（同 shape），但执行行为由各自的字典区分，既不爆炸代码体积，又不牺牲太多性能。

注：本系列其他 runtime 笔记可给精确行号；泛型主要是编译期机制，运行时几乎不感知（没有”泛型对象”），所以下面以编译器设计和生成结果为主，不纠结逐行号。

类型参数、约束与类型集

语法层三个概念：

  • 类型参数（type parameter）：函数或类型声明里 [T any]、[T comparable] 的 T，是一个占位类型。
  • 约束（constraint）：类型参数的”类型”，本质是一个 interface。Go 1.18 扩展了 interface：除了方法集，还可以嵌类型集（type set），用 | 列出允许的具体类型，如 constraints.Integer 大致是 ~int | ~int8 | ... | ~uint64。
    • 只有方法的约束是老派接口（io.Reader）；
    • 带类型列表的约束只能用于泛型约束，不能当普通接口值传。
  • comparable：一个内置约束，表示类型可以用 ==/!=。它比”类型集可比较”更微妙，是个编译器特判的约束。

~T（underlying type，近似底层类型）很关键：~int 表示”底层类型是 int 的所有命名类型”。所以 type MyInt int 也满足 ~int，即使它和 int 是两个不同类型。约束匹配按底层类型和方法集判断，不是按类型名。

GC shape：哪些类型共用一份机器码

核心想法：如果两个类型在运行时布局和 GC 行为完全一致，同一份机器码就能正确处理它们，不需要重复生成。

一个 GC shape 由这些因素决定（对类型的归纳）：

  • 大小与对齐（Size_、Align_）；
  • 指针前缀长度 PtrBytes：GC 扫描只看这部分；
  • 是否为指针类型（TFlagDirectIface，值本身是一个指针字）；
  • 哈希/相等函数的族（能否当连续内存 memequal/memhash，还是需要 Equal）。

由此得到直觉：

  • 所有指针 *int、*Foo、*Bar、unsafe.Pointer → 同一个 shape（都是一个指针字）；
  • 所有一字节非指针 int8/uint8/byte/bool → 一个 shape；
  • int64/uint64/float64（在 64 位平台）→ 一个 shape；
  • int32/uint32/float32 → 一个 shape；
  • string、slice、interface、chan、map、func 各自一个 shape（布局固定）；
  • 每个不同字段布局的 struct、不同元素类型/长度的 array，通常各自一个 shape（或按指针位图折叠）。

调用 Max[int] 和 Max[uint64]，若二者属同 shape，编译器只生成一份函数体，符号被 mangle 成 Max[go.shape.uint8]（名字里带 shape 标识，不是具体类型名）。具体是谁，靠字典区分。

这是部分单态化：比全装箱快（没有类型断言/拆箱），比完全单态化省代码（不会 Max[int]、Max[uint]、Max[int64]… 各来一份）。

字典：所有”需要具体类型”的信息

泛型函数机器码里，对类型参数 T 的值能直接做的操作，只有不依赖具体类型的：按字移动内存、清内存、已知偏移的读写。但凡涉及下列操作，必须查字典：

  • 把 T 值装箱进 interface（需要 *abi.Type）；
  • 做类型断言、type switch；
  • 调用 T 的方法（方法地址因类型而异）；
  • 访问结构体字段、调用类型参数的底层类型的方法；
  • 把 T 放进 map（需要哈希/相等函数）、比较 ==；
  • 用 T 调另一个泛型函数（需要传子字典）。

字典在编译期为每个具体调用点构建，是一个编译单元内的只读结构，大致包含：

  • 类型参数对应的 *abi.Type（运行时类型描述符）；
  • 约束方法所需的 itab（见 Interface 笔记）或方法函数值；
  • 字典里的 函数/方法值（method expression）；
  • 嵌套泛型调用的 子字典指针。

调用泛型函数时，字典作为第一个额外参数传入（类似上下文指针）。在 ABIInternal 下走寄存器，不额外占栈。

// 你写的
func MapKeys[K comparable, V any](m map[K]V) []K { ... }
keys := MapKeys[string, int](m)

// 编译器大致生成（示意，非真实代码）
func MapKeys[shapeK, shapeV](dict *Dict, m map[shapeK]shapeV) []shapeK {
    // map 操作通过 dict 里的 hash/equal
    // new([]shapeK) 用 dict 里的 *abi.Type
}
&dictFor_string_int := &Dict{
    Ktype: typeOfString, Vtype: typeOfInt,
    ...
}
MapKeys(&dictFor_string_int, m)

方法、itab 与泛型接收者

泛型类型的方法、以及对类型参数调用约束方法，是字典最能体现价值的地方：

  • type Stack[T any] struct{ ... } 的方法 func (s *Stack[T]) Push(v T) 会按 T 的 shape 生成代码；方法表和接口实现由编译器实例化时补齐。
  • 当一个泛型函数里 T 约束为 io.Reader，并调 T.Read 时：字典里存的是具体类型实现 Read 的函数地址（或一个 itab），函数体通过 dict.ReadFn 间接调用，和接口的动态分发同构，但比接口调用多了内联和去虚化的机会。
  • 泛型类型实现接口时，编译器在实例化点生成对应的 itab/方法表，保证 `var _ io.Reader = &MyStruct[int]{} 能成立。

一个反直觉点：类型参数本身不能直接”断言成具体类型”（除了 type switch），因为它在机器码层是 shape。所有运行时类型识别都要走字典或接口。

泛型与逃逸、内联、性能

  • 字典本身通常不导致分配：它在编译期构建为只读静态数据，传的是指针。
  • 泛型函数里的 new(T) / make([]T, n)：字典给类型描述符，分配走标准 mallocgc；是否逃逸按常规逃逸分析判断，没有因为”泛型”就必然堆分配。
  • 内联：小泛型函数可以被内联，字典和 shape 代码在内联后常常被进一步优化（常量传播、去虚化）。slices.Sort、maps.Clone 这类标准库泛型之所以快，部分原因是编译器能针对 shape 内联和特化。
  • 代码体积：shape 分组已大幅抑制膨胀，但如果用了大量布局各异的 struct 实例化泛型，每个 struct 仍可能是一个独立 shape，体积会增长——这是”用泛型还是接口”的经典权衡。
  • 与接口的选择：
    • 类型集小、操作”数据相关”（排序、集合、算法）→ 泛型，内联 + 无装箱；
    • 类型集开放、只需少量行为（io.Reader）→ 接口，一份代码、二进制小；
    • 两者可组合：泛型函数内部用约束方法，对外暴露接口版本也常见。

边界与误区

  • 泛型是编译期概念：运行时没有”泛型类型”这回事，只有 shape 实例化后的具体类型、字典和普通机器码。反射看不到类型参数（它只看到实例化后的具体类型）。
  • any 不是万能：用 any 做类型参数会退化成大量 interface 操作，反而比直接用接口慢；约束越精确，编译器能生成的代码越好。
  • 方法不能直接引入新的类型参数：Go 目前只允许泛型类型的方法，不允许方法自己声明类型参数（即 func (s Stack[T]) Map[R](...) 不合法）。变通方式是用包级泛型函数。
  • comparable 不是”类型集可比较”那么简单：它包含接口类型、指针等，且随版本演进；不要用它推断结构体字段能否比较。
  • 递归类型参数有约束：像 type T[T2] 这类递归/自引用实例化受编译器规则限制，遇到 F-bounded 多态的写法要小心。
  • 没有 switch T.(type) 对类型参数：对类型参数做分支用普通 type switch 断言其到接口，或通过约束方法分发，不能 switch T.(type) 切换类型参数本身。
  • 跨包泛型实例化：字典和 shape 实例化在调用包发生，Go 的实现避免了”模板重复实例化”的代码膨胀（不同于 C++ 头文件模型）。
