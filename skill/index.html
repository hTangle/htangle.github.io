Skill：给 Agent 的可复用工作手册

📋 一句话定义

**Skill 是一组可发现、可复用的任务知识与执行规程，用来告诉 Agent 在某类场景中“应该怎样做”。**它通常把指令、步骤、约束、示例、脚本、模板和参考资料打包在一起，让通用模型获得稳定的领域做事方法。

如果基础模型是一位聪明但刚入职的工程师，那么 Skill 不是给他装上一双“能操作系统的手”，而是递给他一本经过验证的 SOP 工作手册：什么时候适用、先检查什么、按什么顺序做、哪些坑不能踩、最终怎样验收。

📝 术语边界

**Agent Skills 已经是一种公开、轻量的目录格式规范，但它不是网络协议，也不等于各平台的完整运行时。**规范定义 SKILL.md 与资源目录的可移植形态；具体扫描路径、激活策略、权限模型、工具名称和分发方式仍可能由不同 Agent 平台决定。

1. 为什么只有 Prompt 还不够

一次性 Prompt 可以告诉模型当前任务，但复杂任务往往还依赖：

  • 团队约定，例如目录、命名、审批和发布流程；
  • 专业知识，例如财务口径、数据库迁移风险、设计规范；
  • 可重复步骤，例如“先诊断、再修改、最后验证”；
  • 本地资产，例如脚本、模板、示例文件和检查清单；
  • 工具使用策略，例如什么情况下搜索、怎样传参、哪些动作要确认。

如果每次都把这些内容写进 Prompt，会产生三类问题：上下文膨胀、规则漂移、结果不稳定。Skill 把这些知识变成可维护的模块。

2. 一个 Skill 通常包含什么

一个可维护的 Skill 常见结构如下：

my-skill/
├── SKILL.md          # 入口：适用条件、流程、边界与验收标准
├── references/       # 需要时再读取的领域资料
├── scripts/          # 可重复、确定性的辅助程序
├── templates/        # 文档、配置、代码等模板
└── examples/         # 正反例或期望输出

2.1 元数据：让 Skill 能被发现

入口文件通常包含名称与描述。描述不只是简介，它还是“路由规则”：Agent 根据用户意图判断是否要加载这个 Skill。

---
name: database-migration
description: 在创建、审查或回滚数据库迁移时使用
---

好的描述回答两个问题：

  1. **什么时候必须用？**例如“创建迁移、修改表结构、数据回填”；
  2. **它能提供什么？**例如“风险检查、分阶段发布、回滚验证”。

2.2 指令：把经验写成决策规则

Skill 的核心不是知识百科，而是能改变行为的规则，例如：

  • 修改前读取当前 Schema 和已有迁移；
  • 大表新增非空列时先允许 NULL，回填后再收紧约束；
  • 所有迁移必须提供向前验证和回滚方案；
  • 不把生产凭证写进命令、日志或示例。

“介绍数据库迁移是什么”帮助有限；“遇到某条件时采取什么动作”才是可执行的 Skill。

2.3 资源：把确定性工作交给确定性资产

Skill 可以指示 Agent 调用已有脚本、复用模板、读取参考资料。这样能避免模型每次重新发明实现，也能减少格式和命令错误。

💡 一个实用原则

判断、解释和组合交给模型；重复、精确、可测试的机械步骤尽量固化成脚本或模板。

3. Skill 如何在一次任务中生效

可拆成五步：

  1. 匹配：根据任务语义判断 Skill 是否适用；
  2. 加载：读取完整入口指令，理解边界；
  3. 展开：只在需要时继续读取 references、scripts、templates；
  4. 执行：Skill 影响规划、工具选择、参数、顺序与安全检查；
  5. 验收：根据 Skill 定义的完成条件验证结果。

这里最重要的一点是：**Skill 改变的是 Agent 的决策上下文，并不自动产生外部副作用。**真正读取文件、调用 API、执行测试的仍然是 Tool 和运行时。

高质量 Skill 往往采用三层信息密度：

这叫渐进式披露。它有三个好处：

  • 节省上下文窗口，让模型注意力集中；
  • 避免无关规则干扰当前任务；
  • 允许参考资料独立演进，而入口保持简洁稳定。

如果 SKILL.md 长到像一本教材，模型可能找不到关键约束；如果过短，只写“请谨慎操作”，又无法产生稳定行为。

5. Skill、System Prompt 与 Memory 的区别

概念主要内容作用范围典型变化频率
System Prompt身份、全局规则、安全边界几乎所有任务较低
Skill某类任务的流程与领域方法匹配任务时加载中等，可版本化
Memory用户偏好、历史决策、项目上下文相关会话或项目随交互累积
当前 Prompt这一次要完成的目标当前请求每次都变

简单说：System Prompt 管“始终怎么做”，Skill 管“这类事怎么做”，Memory 管“过去发生过什么”，当前 Prompt 管“现在做什么”。

6. 一个最小但有效的 Skill 示例

下面是“写技术决策记录”的简化入口：

---
name: adr-writer
description: 创建或更新 Architecture Decision Record 时使用
---

## ADR Writer

1. 先收集背景、约束、候选方案和决策者。
2. 不虚构基准数据；没有证据时标记为待验证。
3. 至少比较两个可行方案及其代价。
4. 使用 templates/adr.md。
5. 完成后检查：状态、日期、决策、后果、回滚条件是否齐全。

它有效的原因在于：触发条件明确、步骤可操作、禁止项具体、资产可复用、完成标准可验证。

7. 如何设计高质量 Skill

7.1 写清触发条件与非适用范围

不要只写“处理文档”。更好的描述是：“创建、编辑或审查 .docx 文件时使用；普通 Markdown 不使用”。边界越清楚，误触发越少。

7.2 把规则写成可观察行为

  • 模糊：确保质量。

  • 具体：修改后运行单元测试与格式检查，失败时不得宣称完成。

  • 模糊：注意安全。

  • 具体：发送外部消息前展示收件人和正文；删除数据前解析并复核精确目标。

7.3 说明顺序、分支与停止条件

复杂流程需要表达依赖：A 的结果决定执行 B 还是 C；何时需要用户确认；怎样才算完成。可以使用编号步骤、决策表或 Mermaid。

7.4 内置验证闭环

Skill 不应停在“生成内容”，还要要求检查：

  • 语法或构建是否通过；
  • 输出是否真的写入目标位置；
  • 外部调用是否返回成功；
  • 用户要求的每一项是否覆盖；
  • 是否引入超出范围的改动。

7.5 控制自由度

任务性质Skill 应给的自由度
创意写作、方案探索高：给原则和评价标准
常规工程实现中：给流程、模式和检查项
发布、迁移、财务、安全操作低：给精确命令、审批点和回滚路径

风险越高、错误代价越大，Skill 越应该明确和确定。

8. 常见失败模式

❌ 把 Skill 写成百科全书

大量背景知识却没有“遇到什么 → 做什么 → 怎么验证”，读完仍无法执行。

❌ 把工具能力写进 Skill 并假装已经执行

Skill 可以要求“搜索代码”，但如果运行时没有搜索工具或权限，它不能凭文字创造能力。

❌ 触发描述过宽

“所有编程任务都使用”会导致无关规则挤占上下文，甚至与更具体的 Skill 冲突。

❌ 依赖隐含环境

指令引用了不存在的路径、未安装的命令或私人凭证，却没有检测与降级路径。

❌ 没有版本与验证

外部 API、框架或组织流程变化后，旧 Skill 继续给出过时步骤，结果比没有 Skill 更危险。

9. 什么时候该创建 Skill

满足以下两三项时通常值得创建：

  • 同类任务重复出现；
  • 成功路径包含稳定的多步流程；
  • 错一步的成本较高；
  • 有团队规范或领域知识需要复用；
  • 有脚本、模板、示例可以打包；
  • 希望不同 Agent 或成员产出一致。

如果只是一个一次性的简单问题，一段清晰 Prompt 往往已经足够。

10. Agent Skills 规范级细节

一个符合公开 Agent Skills 格式的 Skill 至少包含目录和 SKILL.md。面试中若只回答“Skill 就是一段 Prompt”，会漏掉它的打包、发现和渐进加载语义。

10.1 Frontmatter 契约

字段必需关键约束作用
name是1–64 字符，小写字母/数字/连字符；与目录名一致稳定标识
description是1–1024 字符；同时说明做什么、何时使用激活路由
license否SPDX 名称或许可证文件说明使用边界
compatibility否最长 500 字符产品、系统包、网络等环境要求
metadata否string → string 映射作者、版本等扩展信息
allowed-tools否实验字段，平台支持度不同预批准工具提示

规范推荐主 SKILL.md 少于 500 行、约 5000 tokens；更深资料放入 references/，确定性逻辑放入 scripts/，交付素材放入 assets/。这不是为了文档美观，而是为了控制激活后的上下文成本。

10.2 allowed-tools 不等于授权系统

allowed-tools 只是一种实验性的预批准声明，不能替代 Runtime 的权限检查。原因包括：

  • 不同 Client 对工具命名和通配语法的解释不同；
  • Skill 本身可能来自不可信来源；
  • 工具参数仍可能越权或具有高风险副作用；
  • 用户本次请求的授权范围可能小于 Skill 声明范围。

正确架构是：Skill 提供“期望使用哪些工具”的声明，Policy Engine 根据用户、环境、工具和参数做最终决定。

11. 从 Runtime 视角实现 Skill

支持 Skills 的 Agent Runtime 至少需要五个组件：

11.1 Discovery

  • 扫描平台约定的项目级、用户级和内置目录；
  • 解析 YAML，检查必填字段和目录名；
  • 对语法损坏、符号链接越界、重复名称做诊断；
  • 保存绝对入口路径与内容哈希，供激活和审计。

11.2 Catalog

会话启动时只向模型披露名称和描述。Catalog 应稳定排序，以提高提示缓存命中；同名 Skill 要有确定优先级，例如：项目级覆盖用户级，用户级覆盖内置，但覆盖必须可见且可审计。

11.3 Router

常见路由方式有三种：

方式优点缺点
关键词/规则快、可解释、确定召回差，难覆盖同义表达
Embedding 检索可扩展、语义召回好阈值难调，可能误触发
模型自主选择理解上下文与组合意图成本更高，结果有随机性

生产系统通常采用混合路由：规则处理强约束，检索缩小候选，模型做最终相关性判断；同时允许用户显式指定 Skill。

11.4 Loader 与上下文组装

Loader 读取完整 SKILL.md 后，要明确其指令优先级低于系统安全规则和用户当前目标。相对路径必须以 Skill 根目录解析，防路径穿越；参考文件按需加载，不要递归扫完整目录。

11.5 Executor

脚本不是“知识文本”，而是代码执行供应链。Runtime 应在沙箱中运行，限制文件、网络、CPU、内存、时长与环境变量；不能因为脚本和 SKILL.md 位于同一目录就默认可信。

12. Skill 是上下文工程，不是 Prompt 堆砌

Skill 的效果可以理解为：

$$ P(成功) = f(路由正确率, 指令可执行性, 工具可用性, 环境匹配度, 验证闭环) $$

只优化措辞而忽略其他项，最终效果仍可能很差。

12.1 指令应分为四层

  1. 不变量：绝不能违反，例如不泄露密钥、不覆盖用户未授权文件；
  2. 决策规则：如果条件 A，则采取 B；
  3. 默认策略：无特别说明时优先 C，但允许根据上下文调整；
  4. 示例：展示期望形态，不应被误读为唯一合法答案。

混在一起时，模型难以判断优先级。高级 Skill 会显式区分 MUST、SHOULD、MAY，或用“要求 / 默认 / 可选”表达。

12.2 为什么过长 Skill 反而降低效果

  • 关键约束在长上下文中被稀释；
  • 多个边缘场景互相冲突；
  • 每次激活都支付相同 token 成本；
  • 模型可能过拟合示例而忽略当前差异；
  • 缓存失效与维护成本上升。

解决方案不是简单删字，而是将稳定主流程留在入口，将错误码、API 细节、长示例按触发条件路由到 references。

13. Skill 的组合、冲突与优先级

真实任务可能同时命中多个 Skill，例如“修改 Spring Boot 数据库迁移并做安全审查”。如果 Runtime 只是拼接全文，会出现规则冲突和上下文爆炸。

推荐冲突策略：

  1. 系统安全规则 > 用户明确要求 > 项目规则 > 通用 Skill 默认值；
  2. 更具体的 Skill 优先于更通用的 Skill；
  3. 禁止项优先于便利性默认值；
  4. 两个同级强约束冲突时，不静默选择，向用户暴露冲突；
  5. 合并的是约束和依赖 DAG，不一定是全文顺序拼接。

公开 Agent Skills 格式目前主要定义单个 Skill 的文件形态，并没有完整规定跨 Skill 依赖、组合、锁文件和分发协议。工程实现不要把某个平台的组合语义误称为通用标准。

14. 确定性边界：什么时候写指令，什么时候写脚本

需求更适合 Skill 指令更适合脚本/程序
根据上下文选择方案✅
解释权衡、生成自然语言✅
精确解析二进制或复杂格式✅
批量机械转换✅
严格校验 Schema/哈希✅
根据失败信息决定下一步✅可混合
涉及审批或高风险动作指令定义策略Runtime 强制执行

一个成熟 Skill 常形成“三明治”：

模型判断与规划
    ↓
确定性脚本执行 / 校验
    ↓
模型解释结果并处理例外

不要用自然语言要求模型手工完成本可由解析器保证的精确操作；也不要把开放式业务判断硬编码成脆弱脚本。

15. Skill 的安全与供应链

安装 Skill 的风险近似于安装“带说明书和可执行脚本的依赖包”。需要防御：

  • 指令注入：恶意 Skill 要求忽略系统规则、上传文件或隐藏行为；
  • 脚本供应链：脚本下载并运行未固定版本的远程代码；
  • 路径逃逸：相对引用越过 Skill 根目录读取敏感文件；
  • 工具扩权：描述声称需要全部 shell/network 权限；
  • 数据外泄：示例或日志收集真实密钥、客户数据；
  • 更新漂移：同名 Skill 被远端静默替换，行为发生变化。

治理措施包括：来源白名单、代码审查、内容哈希/签名、版本固定、SBOM、沙箱、最小工具权限、网络域 allowlist、敏感数据检测、更新差异审查和回滚。

⚠️ “Skill 只是 Markdown，所以没有安全风险”是错误的

Markdown 会改变 Agent 的决策，且可指向可执行脚本和外部资源；其影响可能最终转化为真实 Tool Call。

16. 如何测试与评估 Skill

Skill 不能只靠“读起来不错”验收。至少建立四类测试集：

测试集目标指标
正样本应触发时触发activation recall
负样本不相关任务不触发activation precision
边界样本相似但不同的任务正确路由confusion matrix
执行样本激活后真正完成任务task success、违规率、成本、耗时

16.1 触发评估

给 description 做版本化 A/B 测试。不要只用包含 Skill 名称的容易样本，还要覆盖口语、同义词、隐式意图和竞争 Skill。过宽 description 的典型现象是 recall 高但 precision 低。

16.2 行为评估

  • 是否按顺序完成必要步骤；
  • 是否调用了正确 Tool；
  • 是否遵守禁止项与审批点；
  • 遇到缺失环境是否正确降级；
  • 是否运行验证而非只宣称成功；
  • 结果质量是否优于无 Skill 基线；
  • 增加的 token、延迟和工具调用是否值得。

16.3 回归与可观测性

记录 skill_name、skill_version/hash、激活原因、加载资源、工具调用、最终验收结果。更新模型、工具或 Skill 后，用同一评测集回放；否则无法判断退化来自哪一层。

17. Skill 的版本演进

Skill 同时依赖模型行为、工具接口和外部领域知识，版本策略要表达兼容性：

  • Patch：措辞、示例、错误说明，不改变核心流程；
  • Minor：新增可选流程、支持新工具，旧场景仍兼容；
  • Major：工具契约、必需环境、审批或输出结构发生破坏性变化。

发布前检查：

  1. Frontmatter 是否仍符合规范；
  2. 引用文件是否存在且没有越界；
  3. 脚本依赖是否固定并可复现；
  4. 旧正/负/边界样本是否通过；
  5. compatibility 是否反映新环境要求；
  6. 用户是否能知道实际加载的是哪个版本。

18. 生产环境落地：Skill 不是写完就结束

生产环境最难的不是创建第一个 Skill，而是维护几十或几百个 Skill 后，仍然知道：哪个被加载、为什么加载、用了哪个版本、是否真的提高成功率。

18.1 目录分层与覆盖策略

常见部署分为三层：

内置 Skills       平台维护，提供基础能力
用户级 Skills     个人偏好与跨项目流程
项目级 Skills     仓库规范、版本与团队流程

经验上项目级可以覆盖同名用户级配置，但必须在日志或 UI 中显示最终来源。否则同一任务在两台机器表现不同，很难排障。

建议 Catalog 为每个 Skill 记录：

name: database-migration
source: project
path: /repo/.agents/skills/database-migration/SKILL.md
content_hash: sha256:...
owner: database-platform
version: 2.3.1
trust_level: reviewed

content_hash 比只记版本更可靠，因为开发者可能修改内容却忘记升版本。

18.2 将 Skill 视为生产依赖

  • 与代码一起走 Code Review，不允许直接在线改生产 Skill；
  • 指定 owner 和 backup owner，避免流程无人维护；
  • 依赖的 CLI、SDK、模板必须固定版本或声明兼容范围；
  • Skill 更新要有 changelog、评测结果和回滚版本；
  • 引用外部 URL 时预期其会变化，关键资料应固定快照或校验内容；
  • 脚本默认在无凭证、受限网络、只读工作区中测试；
  • 删除 Skill 前先统计实际激活量和下游依赖。

18.3 不要让生产 Skill 依赖隐式机器状态

最常见的“我这里能跑”来源：PATH 不同、CLI 版本不同、用户全局配置不同、当前目录错误、凭证只存在作者电脑。

Skill 应在入口处声明并检查：

  • 必需命令及最低/最高版本；
  • 当前工作目录与项目标志文件；
  • 网络是否必需、允许访问哪些域；
  • 必需环境变量只检查是否存在，不打印值；
  • 输出目录、临时目录和磁盘空间；
  • 平台/架构差异；
  • 缺失条件时的降级或停止方式。

💡 生产经验

先运行一个轻量 preflight 脚本统一检查环境，比让 Agent 执行到一半再从模糊报错中猜缺什么稳定得多。

19. 生产事故模式与修复经验

19.1 Description 过宽，几乎所有任务都触发

现象：回复变慢、无关工具调用增多、模型总套用同一种格式。

根因：description 写成“用于所有代码任务”或堆入大量热门关键词，只追求召回率。

修复：

  1. 增加明确正向场景与排除场景；
  2. 用真实历史请求建立正/负样本；
  3. 同时度量 precision 与 recall；
  4. 先灰度新 description，不直接全量；
  5. 对竞争 Skill 建立混淆矩阵。

19.2 Skill 太长，关键约束反而被忽略

现象：模型读了 Skill，但漏掉上线前必须运行测试等关键步骤。

根因：入口包含上万 token 的背景、API 表和边缘案例，关键约束被稀释。

修复：入口只保留不变量、主流程、路由和验收；错误码、长示例和框架细节拆入 references，并写明“什么条件下读取”。对压缩前后版本做同集评测，而不是凭主观判断。

19.3 Skill 引用的脚本悄悄发生破坏性变化

现象：Skill 文本没改，某天开始生成不同文件或发送额外网络请求。

根因：脚本从 main 分支或 latest 下载，未固定 hash；或者脚本文件更新未触发 Skill 评测。

修复：把 Skill 目录整体作为版本单元，CI 对全部文件计算 hash；固定依赖；脚本变化必须重跑执行评测和安全扫描。

19.4 Skill 要求使用不存在的工具

现象：Agent 假装执行、反复寻找命令，或生成无法落地的结果。

修复：在 compatibility 和 preflight 中声明工具；Runtime 激活时检查实际 Tool Catalog；缺失时选择替代路径或明确停止，禁止“文字模拟成功”。

19.5 多个 Skill 的规则互相覆盖

现象：一个要求先写测试，另一个要求直接修改；Agent 每次顺序不同。

修复：Runtime 记录激活顺序与来源，合并前抽取 MUST/SHOULD；使用明确优先级；对常见组合建立集成测试。不要让“后加载者覆盖前加载者”成为隐含规则。

19.6 旧 Skill 在 API 升级后继续给错命令

修复经验：

  • 对外部 API/CLI 建立定期漂移检测；
  • reference 标注验证日期与支持版本；
  • 在 CI 用最小真实命令或契约测试验证；
  • 新旧接口并存时写清版本路由；
  • 超过维护窗口的 Skill 标记 deprecated，默认不再激活。

20. Skill 的 CI/CD 与灰度流程

20.1 建议流水线

CI 最少检查：

1. frontmatter 规范与目录名
2. 相对引用存在、不能逃逸 Skill 根目录
3. Markdown/代码块/示例语法
4. 脚本 lint、测试、依赖漏洞和敏感信息
5. 正样本触发率、负样本误触发率
6. 端到端任务成功率与安全用例
7. 与上一个版本的 token、延迟和 Tool Call 差异

20.2 Shadow 与 Canary

  • Shadow：新 Skill 只做离线选择与计划，不执行 Tool；比较它与当前版本的路由和计划差异。
  • Canary：仅对内部用户、特定仓库或 1% 会话生效；保留旧版本作为对照。
  • Full rollout：满足质量门槛后扩大；高风险 Skill 分阶段开放写工具。

灰度分桶应稳定，例如按 user_id + project_id 哈希；不要让同一用户在一次任务中随机切换 Skill 版本。

20.3 回滚条件

预先定义，而不是事故发生时争论：

  • 任务成功率下降超过 3%；
  • 高风险 Tool 未确认调用出现任何一例；
  • 误触发率超过阈值；
  • p95 延迟或 token 增长超过预算；
  • 脚本错误率或环境不兼容显著增加；
  • 出现数据外泄、越权或不可逆副作用。

21. 在线观测与运营指标

21.1 一次激活应留下什么证据

{
  "skill_name": "database-migration",
  "skill_version": "2.3.1",
  "content_hash": "sha256:...",
  "source": "project",
  "activation_reason": "user requested schema change",
  "resources_loaded": ["references/postgres.md"],
  "tools_used": ["shell", "database_schema_read"],
  "verification": "passed"
}

实际日志应避免保存完整用户内容和敏感参数；可存分类、哈希和脱敏摘要。

21.2 Dashboard

指标用途
activation precision/recall路由是否准确
activation rate by skill/version是否异常暴增或没人使用
task success uplift相比无 Skill 的真实收益
tool error / retry rate指令是否与环境不匹配
user correction rate用户是否频繁纠正流程
safety violation rate是否绕过审批或越权
token / latency uplift上下文成本是否合理
resource load distributionreferences 是否拆分合理

21.3 维护节奏

  • 高频、高风险 Skill：每次工具/API 变更触发检查，至少每月审视；
  • 一般团队 Skill：季度检查所有权、链接和评测；
  • 长期零激活 Skill：确认是否未被发现、已过时或可下线；
  • 每次重大模型升级：重跑路由和行为评测，不能假设新模型一定更遵循旧 Skill。

22. 生产上线检查单

  • Skill 有 owner、版本、来源与内容 hash；
  • description 已用正/负/边界样本评测；
  • 主 SKILL.md 只保留核心流程，引用按需加载；
  • compatibility 与 preflight 覆盖运行环境；
  • 引用路径不能逃逸 Skill 根目录；
  • 脚本固定依赖、通过测试和安全扫描；
  • 高风险行为由 Runtime 强制审批，不只写在文字里；
  • 与常见其他 Skills 的组合经过测试；
  • 可观测到实际加载版本、资源和 Tool Calls；
  • 有 shadow/canary、回滚阈值和旧版本；
  • API/CLI 漂移有检测或定期复核；
  • 弃用流程不会静默破坏依赖者。

23. 一些额外的QA

❓ - Q1：Skill 和 Fine-tuning 的区别？

Fine-tuning 把模式写入模型权重，适合大量稳定行为分布；Skill 在推理时加载，适合可审查、频繁变化、项目特定的流程。Skill 更新快、可版本化、可按需启用，但占上下文并依赖指令遵循。两者可组合，而非互斥。

❓ - Q2：为什么 description 是核心接口？

因为渐进披露的第一层只暴露 name 与 description。它同时承担检索文档和路由规则的角色；写得太窄会漏触发，太宽会误触发。需要用正负样本测 precision/recall，而不是凭感觉修改。

❓ - Q3：Skill 能保证 Agent 一定按流程执行吗？

不能。Skill 是上下文约束，不是类型系统或权限系统。高风险不变量必须由 Runtime、Policy、Schema、沙箱和审批强制；Skill 负责指导与解释。

❓ - Q4：怎样处理多个 Skill 同时适用？

先提取目标、约束与依赖，形成执行 DAG；按系统/用户/项目/通用优先级解决冲突；只加载相关章节；同级强约束冲突时显式询问。不要简单按发现顺序拼接。

❓ - Q5：如何证明一个 Skill 有价值？

与无 Skill 基线和旧版本做同集评测，比较触发 precision/recall、任务成功率、安全违规率、人工修改量、tokens、延迟和成本。只有结果质量提升且代价合理，才说明 Skill 有效。

❓ - Q6：Skill、Plugin、Tool 的关系？

Skill 是可加载的程序性知识；Plugin 通常是分发和扩展单元，可同时包含 Skills、Tools、MCP Server 或 UI；Tool 是可执行能力。一个 Skill 可以指导使用 Tool，但自身不自动提供 Tool 权限。

❓ - Q7：如何设计企业内部 Skill 治理？

建立所有权、代码审查、签名与版本固定；区分内置/团队/个人信任级别；静态扫描脚本与指令；按环境限制工具和网络；维护评测集、变更日志、弃用窗口和快速回滚。
