哈希表：Go 1.26.5 Swiss Table 源码分析

[!abstract] 一句话理解 Go 1.26.5 的内置 map 使用 Swiss Table：8 个键值槽组成一个 Group，8 字节控制字一次筛选整组候选；Group 之间使用二次探测，Table 达到阈值后扩容或分裂，顶层 Directory 通过可扩展哈希选择 Table。

本文以 Go 1.26.5、提交 c19862e5f8415b4f24b189d065ed739517c548ba 为准。基础延伸：解决哈希冲突的几种办法、同步和锁、内存分配器、垃圾收集器。

1. 先分清语言契约与实现

语言层面可以依赖：

  • key 必须是可比较类型；
  • 查询不存在的 key 返回元素零值，逗号 ok 可区分是否存在；
  • nil map 可读、可 len、可 delete、可 clear，但写入会 panic；
  • 迭代顺序未指定；迭代期间删除尚未到达的项不会返回，新增项可能返回也可能不返回；
  • 普通 map 不支持无同步的并发读写。

实现层面用于理解性能，不能作为业务协议：Group 固定 8 槽、H2 使用 7 位、Table 上限 1024 槽、目录分裂策略、具体内存布局和扩容时机。

源码总览见 internal/runtime/maps/map.go#L16-L180。核心层次如下：

术语：

层级职责

internal/abi 固定每组 8 个槽，key 或 elem 大于 128 字节时改为间接存储，见 internal/abi/map.go#L11-L23 和 MapType#L32-L64。

3. Map 顶层结构

运行时 Map 定义见 map.go#L194-L246：

type Map struct {
    used              uint64
    seed              uintptr
    dirPtr            unsafe.Pointer
    dirLen            int
    globalDepth       uint8
    globalShift       uint8
    writing           uint8
    tombstonePossible bool
    clearSeq          uint64
}
  • used 必须在首字段，编译器据此实现 len(m)；
  • seed 是每个 map 独立的随机哈希种子；
  • dirPtr/dirLen 指向 Directory；
  • globalDepth/globalShift 决定使用多少哈希高位选择 Table；
  • writing 用于尽早发现并发写、读写冲突；
  • clearSeq 帮助迭代器识别迭代期间的 clear。

map 变量本身类似指针语义：赋值或传参共享同一个运行时 Map，不会深拷贝键值。

a := map[string]int{"x": 1}
b := a
b["x"] = 2
fmt.Println(a["x"]) // 2

4. 小 map：单 Group 快速路径

最多 8 项的小 map 可以让 dirPtr 直接指向一个 Group，此时 dirLen == 0，无需 Directory、Table 和探测序列。说明见 Map.dirPtr#L204-L222。

NewMap#L264-L328 对 hint <= 8 延迟分配 Group；如果没有任何写入，连 Group 分配也能省掉。编译器还可能把不逃逸的 Map 和首个 Group 放在栈上，运行时入口见 runtime/makemap。

写入第 9 个不同 key 时，小 map 转为完整 Table，见 Map.PutSlot#L486-L533。

5. Group 与控制字

每个 Group 有 8 个控制字节，与 8 个 Slot 一一对应：

ctrl:  [c0 c1 c2 c3 c4 c5 c6 c7]
slots: [s0 s1 s2 s3 s4 s5 s6 s7]

编码见 group.go#L114-L126：

empty:   1 0 0 0 0 0 0 0   = 0x80
deleted: 1 1 1 1 1 1 1 0   = 0xfe
full:    0 h h h h h h h   = H2

一个哈希值被拆为：

H1 = hash >> 7   // 高 57 位，选择目录和探测起点
H2 = hash & 0x7f // 低 7 位，写入控制字节

源码见 h1/h2#L181-L192。

5.1 为什么控制字快

查找时先把目标 H2 与整个 64 位控制字比较，得到候选槽位 bitset，再只对候选做完整 key 比较：

通用位运算实现见 ctrlGroupMatchH2#L150-L171；AMD64 会替换为 SIMD intrinsic。H2 只有 7 位，会产生假阳性，但随后完整 key 相等比较保证正确性。

6. 查询完整路径

通用访问入口见 runtime_mapaccess1#L49-L128：

看到 Empty 就能结束，是开放寻址的关键不变量：插入搜索如果曾越过该位置，这里就不会仍是 Empty。Deleted 不能终止搜索。

6.1 二次探测

Group 探测序列见 probeSeq#L1261-L1292：

p(i) = H1 + (i² + i) / 2  mod groupCount

即：H1, H1+1, H1+1+2, H1+1+2+3 ...。Group 数必须是 2 的幂，这个序列才会恰好访问每个 Group 一次。

时间复杂度通常摊销 O(1)，但语言不承诺严格最坏 O(1)。碰撞、超大 key 比较、哈希成本和缓存局部性都影响真实延迟。

7. 写入：更新、复用墓碑或扩容

Table 插入实现见 table.PutSlot#L259-L364：

负载阈值由 maxAvgGroupLoad = 7 控制，即多 Group Table 平均最多使用 7/8 槽位，以保证探测最终能遇到 Empty。

make(map[K]V, hint) 是容量提示，不是固定容量，也不是保证不扩容。合理 hint 可减少 rehash；极端高估会提前占用内存。

8. 删除与墓碑

删除实现见 table.Delete#L421-L493。找到目标后先清理 key/elem，之后决定控制字：

  • 当前 Group 仍有 Empty：目标槽可直接标 Empty；
  • 当前 Group 没有 Empty：标 Deleted 墓碑，防止后续查询提前停止。

插入会优先复用墓碑。墓碑过多会增加探测成本，因此写入无剩余增长空间时先尝试 pruneTombstones#L496-L610；只有墓碑达到容量约 10% 才值得做 O(n) 清理，否则进入 grow/split。

clear(m) 清空所有元素、保留 map 可继续使用，并更新随机种子/清理迭代状态；它不等于把变量赋为 nil，也不承诺立刻归还全部底层内存。

9. 扩容：Table grow 与 split

单个 Table 的最大容量当前为 1024 个槽，见 maxTableCapacity。rehash#L1142-L1168 有两条路径：

Table grow 见 table.grow#L1223-L1259，split 见 table.split#L1178-L1221。两者都会重新散列有效元素，顺便消除墓碑。

9.1 可扩展哈希目录

Directory 长度为 1 << globalDepth。每个 Table 保存自己的 localDepth；当 localDepth < globalDepth 时，连续多个目录项可以指向同一 Table。

如果被拆分 Table 的 localDepth == globalDepth，目录先翻倍；原目录的每个引用复制两份，再安装新分裂的 left/right。代码见 installTableSplit#L363-L414。

这种结构把一次增长的搬迁范围限制在一个 Table，而不是一次处理整张大 map；但触发 split 的那次写入仍可能出现明显尾延迟，尤其 key/elem 很大或哈希昂贵时。

10. 迭代器为何复杂

迭代语义和扩容处理的设计说明见 map.go#L132-L180，实现见 Iter#L641-L700 与 Iter.Next#L803-L1140。

必须同时满足：

  1. 同一项不能返回两次；
  2. 迭代中新增项可能出现；
  3. 已修改项返回最新值；
  4. 已删除项不能返回；
  5. 顺序不确定，当前实现主动随机化起点。

扩容发生后，迭代器继续沿旧 Table 的槽位决定“哪些 key 已遍历”，避免重复；真正返回前再到当前新 Table 查一次，拿最新值并确认未删除。

不要用 map range 顺序做分页、签名、测试快照或一致性协议。需要稳定输出时先收集 key 并排序。

11. 并发安全

运行时会在一些冲突中抛出：

  • concurrent map writes；
  • concurrent map read and map write；
  • concurrent map iteration and map write。

例如访问路径在 runtime_mapaccess1#L77-L79 检查写状态，迭代在 Iter.Next#L818-L821 检查。

[!danger] fatal 检查不是同步机制 它不能保证捕获所有数据竞争，也不能把竞态程序变正确。共享 map 必须使用 mutex、RWMutex、channel 所有权、copy-on-write，或在适用场景选择 sync.Map。

选型建议：

场景常用方案
普通读写、需要复合不变量map + sync.Mutex
读多写少且临界区只读评估 map + sync.RWMutex
单 goroutine 拥有状态channel 传命令
写少读多、快照整体替换immutable map + atomic.Pointer
key 稳定且多 goroutine 各写不同 key，或读多写少缓存基准验证 sync.Map
go test -race ./...

12. 性能与生产诊断

12.1 key/elem 设计

  • 大于 128 字节的 key 或 elem 会间接存储，增加分配与指针追踪；
  • string key 的成本还包含按字节哈希和比较；
  • 含指针 key/elem 增加 GC 扫描；
  • 结构体 key 应避免未规范化字段导致逻辑重复；
  • 不要为省一次转换用 unsafe 制造可变 string key。

12.2 容量和生命周期

m := make(map[string]Item, estimated)

hint 接近实际峰值可减少 grow/split；长期高峰后元素大量删除，map 的内部容量可能仍保持较高。若内存必须回落，可以在合适的维护点重建：

next := make(map[K]V, len(old))
for k, v := range old {
    next[k] = v
}
old = next

这会产生瞬时双份内存，应结合流量窗口、内存预算和回滚策略实施。

12.3 观测

go test -bench=. -benchmem ./...
go test -run='^$' -bench=BenchmarkMap -cpuprofile=cpu.out -memprofile=mem.out
go tool pprof cpu.out
go tool pprof -alloc_space mem.out

生产侧关注：map 元素数量与 key 字节数、分配速率、堆/RSS、GC CPU、写入 P99、锁等待、热点 key、缓存命中率和基数增长。运行时不会暴露某张 map 的墓碑数或 split 次数，必要时从业务层建立可解释指标。

13. 常见误区

[!failure] map 的操作永远是 O(1) 通常是摊销 O(1)，但哈希、碰撞、比较、扩容和缓存未命中都会影响尾延迟。

[!failure] make 的 hint 是容量上限 它只是初始容量提示，map 会继续增长。

[!failure] 只并发读取一定安全，所以写很少可以不加锁 一旦任何写与读/迭代并发，就有数据竞争；“写得少”不会改变正确性。

[!failure] delete 后内存一定立即下降 元素引用会被清理，但 Table/Directory 容量可能保留，且 GC/RSS 回落另有节奏。

[!failure] 可以依赖某次观察到的 range 顺序 顺序未指定且实现主动随机化，扩容还会改变遍历结构。
