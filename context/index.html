Context：Go 1.26.5 源码分析

context.Context 是 Go 中跨 API 边界传递 取消信号、截止时间、取消原因和请求域数据 的标准协议。它本身不创建“控制中心”，而是通过一棵不可变的派生链，把取消从父节点广播到所有仍然注册的子节点。

flowchart LR
    R["Background / TODO"] --> C["cancelCtx"]
    C --> T["timerCtx"]
    T --> V1["valueCtx"]
    C --> V2["valueCtx"]
    C -.关闭 Done.-> G1["goroutine / RPC / DB"]
    T -.超时或取消.-> G2["下游任务"]

四个方法定义了一份协作协议

Context 接口 只有四个方法：

type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}
flowchart TB
    C["Context"] --> D["Deadline：何时必须停止"]
    C --> O["Done：广播停止事件"]
    C --> E["Err：为何停止的稳定分类"]
    C --> V["Value：请求域元数据"]

方法契约

方法核心语义容易误解的点
Deadline返回最迟完成时间ok=false 表示没有截止时间，不表示无限资源
Done取消时关闭的只读 Channel可能返回 nil；关闭是广播，不携带原因
Err取消后返回 Canceled 或 DeadlineExceeded取消前必须返回 nil；原因细节看 Cause
Value沿父链查询请求域键值不应用于可选参数、依赖注入或业务配置

同一个 Context 的方法可以被多个 goroutine 并发调用。调用方不应自行实现一个返回行为不稳定的 Context，也不应把 Context 保存进结构体后跨请求复用。

Context 是一条包装链，也是一棵取消树

每次 With... 返回一个包装父 Context 的新对象；父节点不会被修改：

flowchart TD
    B["backgroundCtx"] --> C1["cancelCtx A"]
    C1 --> T1["timerCtx B"]
    T1 --> V1["valueCtx C"]
    C1 --> C2["cancelCtx D"]
    C2 --> V2["valueCtx E"]
    C1 -.cancel.-> T1
    C1 -.cancel.-> C2
    T1 -.cancel.-> V1
    C2 -.cancel.-> V2

“包装链”解释 Deadline 和 Value 如何向父级查询；“取消树”解释 cancelCtx.children 如何把取消向下传播。这是同一组对象的两个观察角度。

根 Context：Background 与 TODO

emptyCtx 的 Deadline 返回无截止时间，Done 返回 nil，Err 返回 nil，Value 返回 nil。

  • Background() 用在 main、初始化、测试和请求树根部。
  • TODO() 的运行语义相同，但表达“这里应该传什么 Context 尚未决定”。它是代码审阅信号，不是永久默认值。

⚠️ 不要传 nil Context

标准库构造函数会对 nil parent panic。即使暂时不确定，也应显式传 context.TODO()。

cancelCtx：取消树的核心

数据结构

cancelCtx 内嵌父 Context：

type cancelCtx struct {
    Context
    mu       sync.Mutex
    done     atomic.Value
    children map[canceler]struct{}
    err      atomic.Value
    cause    error
}
flowchart LR
    C["cancelCtx"] --> P["Context：父节点"]
    C --> D["done：惰性创建的 chan struct{}"]
    C --> K["children：可取消直接子节点集合"]
    C --> E["err：Canceled / DeadlineExceeded"]
    C --> A["cause：业务取消原因"]
    C --> M["mu：保护 done 初始化、children、cause"]

done 和 err 用 atomic.Value 加速高频读取；结构性修改仍由 mu 串行化。cause 与 err 一起在首次取消时固定，之后的取消调用不会覆盖它们。

Done 为什么惰性创建

Done 先原子读取；只有调用者真的索取 Done() 时，才在锁内创建 chan struct{}。

flowchart TD
    A["ctx.Done()"] --> L["atomic.Load(done)"]
    L -->|已有| R["直接返回"]
    L -->|nil| M["加锁并二次检查"]
    M -->|仍为 nil| C["make(chan struct{}) 并 Store"]
    M -->|已有| R
    C --> R

很多 Context 只用于 Value 或传递，并不会等待取消；惰性创建避免为它们都分配 Channel。如果 Context 在第一次调用 Done 前已经取消，源码直接存入全局复用的 closedchan。

Err 的原子快路径

Err 用原子读取替代锁；源码注释指出紧密循环中原子读取约快五倍。观察到非 nil 错误后，它还会接收一次 Done()，保证返回错误前 Channel 已经关闭。

父子取消如何传播

propagateCancel 有四条路径，不是每个子 Context 都创建一个 goroutine：

flowchart TD
    A["propagateCancel(parent, child)"] --> D{"parent.Done() == nil?"}
    D -->|是| N["永不取消，无需注册"]
    D -->|否| C{"parent 已取消?"}
    C -->|是| X["立即取消 child"]
    C -->|否| P{"能找到内部 *cancelCtx?"}
    P -->|是| K["把 child 加入 parent.children"]
    P -->|否| F{"parent 实现 AfterFunc?"}
    F -->|是| AF["注册回调，并用 stopCtx 保存注销函数"]
    F -->|否| G["启动一个 goroutine 监听 parent.Done / child.Done"]

最常见的标准库父子链走 children 注册，取消成本是 O(直接/递归子节点数)，而不是每层一个 goroutine。只有自定义 Context 无法暴露内部父节点、也不支持 AfterFunc 时才使用兜底 goroutine。

parentCancelCtx 通过一个私有 key 找到最内层 *cancelCtx，并验证它的 Done 与父 Context 暴露的 Channel 完全相同；如果自定义包装替换了 Done，标准库不会绕过它。

取消：只执行第一次，先发布状态再广播

cancelCtx.cancel 的顺序非常关键：

sequenceDiagram
    participant F as CancelFunc
    participant C as cancelCtx
    participant Ch as Done channel
    participant Kids as children
    F->>C: cancel(err, cause)
    C->>C: lock；若已有 err 则返回
    C->>C: Store err；设置 cause
    C->>Ch: close(done) 或存 closedchan
    C->>Kids: 递归 cancel 每个 child
    C->>C: children=nil；unlock
    C->>C: 可选：从 parent 移除自己

为什么先设 err/cause 再关闭 Done？因为其他 goroutine 从 <-Done() 返回后，必须能立即读取到稳定的 Err() 和 Cause()。

⚠️ 取消函数必须被调用

即使操作成功提前完成，也应 defer cancel()。它不仅关闭信号，还会停止 timer，并把子节点从父节点的 children 集合移除；长期遗漏会保留对象和定时器直到父节点取消。

取消原因：Cause

传统 Err() 只有两个稳定类别：context.Canceled 与 context.DeadlineExceeded。Go 1.20 的 WithCancelCause 与 Cause 把“控制流分类”和“业务根因”分开：

ctx, cancel := context.WithCancelCause(parent)
defer cancel(nil)

if err := worker(); err != nil {
    cancel(fmt.Errorf("worker failed: %w", err))
}

<-ctx.Done()
log.Printf("class=%v cause=%v", ctx.Err(), context.Cause(ctx))
读取用途
ctx.Err()稳定分支：取消还是超时
context.Cause(ctx)日志、上报和保留业务错误链

第一个取消胜出：父先取消，子继承父 cause；子先用自己的 cause 取消，则子保留自己的 cause，即使父稍后再取消。

截止时间：timerCtx

WithTimeout 只是把 duration 转为 deadline，再调用 WithDeadline。真正实现位于 WithDeadlineCause：

flowchart TD
    A["WithDeadline(parent, d)"] --> P{"父 deadline 更早?"}
    P -->|是| C["退化为 WithCancel(parent)"]
    P -->|否| T["创建 timerCtx 并注册父取消"]
    T --> E{"d 已到期?"}
    E -->|是| X["立即 DeadlineExceeded"]
    E -->|否| R["time.AfterFunc(until d)"]
    R --> X
    X --> S["cancelCtx.cancel + 停止/清理 timer"]

父 deadline 更早时不再创建第二个 timer，因为子不可能活得比父更久。timerCtx.cancel 先执行通用取消，再从父节点移除自己并停止 timer。

AfterFunc：取消后异步执行回调

AfterFunc 注册一个在 Context 完成后由新 goroutine 执行的函数，并返回 stop() bool。

stateDiagram-v2
    [*] --> Pending
    Pending --> Started: Context 取消，once 赢
    Pending --> Stopped: stop() 赢
    Started --> Finished: f 返回
    Stopped --> [*]
    Finished --> [*]
  • afterFuncCtx.once 决定“启动 f”与“阻止 f”谁赢。
  • stop() 返回 true 表示成功阻止启动；返回 false 可能是已经启动，也可能是此前已停止。
  • stop() 不等待正在运行的 f 完成，需要等待时必须自己用 Channel/WaitGroup 协调。
  • 多个 AfterFunc 相互独立，执行顺序不保证。

WithoutCancel：截断控制流，但保留 Value

WithoutCancel 返回一个仍指向 parent 的轻量包装：

方法结果
Deadline无
Donenil
Errnil
Causenil
Value继续向 parent 查询

典型场景是请求结束后仍需完成一个与请求取消解耦、但需要 trace ID 的收尾任务。它不是“后台任务无限运行许可证”；通常还要重新包一层明确的超时：

base := context.WithoutCancel(req.Context())
ctx, cancel := context.WithTimeout(base, 2*time.Second)
defer cancel()
return flushAudit(ctx)

Value：沿链向上查找

WithValue 要求 key 非 nil 且可比较；value 用循环识别标准库各包装类型，避免每层递归调用：

flowchart LR
    V3["valueCtx(k3,v3)"] --> V2["valueCtx(k2,v2)"] --> C["cancelCtx"] --> V1["valueCtx(k1,v1)"] --> B["Background"]
    Q["Value(k1)"] -.逐层比较.-> V3
    V3 -.miss.-> V2
    V2 -.miss.-> C
    C -.miss.-> V1
    V1 -.hit.-> A["返回 v1"]

查询复杂度与链深度线性相关。不要在循环中制造很深的 Value 链，也不要使用内置 string 作为跨包 key：

type traceIDKey struct{}

func WithTraceID(ctx context.Context, id string) context.Context {
    return context.WithValue(ctx, traceIDKey{}, id)
}

正确的 API 设计

传递规则

  1. Context 通常作为第一个参数：func Do(ctx context.Context, ...)。
  2. 不要把它存进结构体；例外需要清晰生命周期说明。
  3. 不要传 nil；使用 TODO 明确技术债。
  4. 不要在库函数内部无条件改用 Background，否则会截断调用方的取消链。
  5. 不要向参数列表塞进 Context Value；Value 只放跨进程/API 边界的请求域元数据。
  6. 调用 WithCancel/Timeout/Deadline 后立即安排 defer cancel()。

在阻塞点响应取消

func send(ctx context.Context, out chan<- Item, v Item) error {
    select {
    case out <- v:
        return nil
    case <-ctx.Done():
        return context.Cause(ctx)
    }
}

Context 的 Done 本身就是只读 Channel；其关闭唤醒机制由 Channel（Go 1.26.5 源码分析） 中的 closechan 实现。

并行任务的取消

Context 只负责停止协议，不负责等待 goroutine 退出。启动 goroutine 后，还需要 WaitGroup、errgroup 或结果 Channel 收拢生命周期：

flowchart LR
    P["parent ctx"] --> C["WithCancelCause"]
    C --> W1["worker 1"]
    C --> W2["worker 2"]
    W1 -->|首个错误| X["cancelCause(err)"]
    X --> W2
    W1 --> J["Wait / join"]
    W2 --> J
    J --> R["返回 Cause(ctx)"]

常见陷阱

  • 只检查 Err() 一次：长循环应在合适边界反复检查或 select Done。
  • 取消后不等待子任务：取消是请求，不是 goroutine 已退出的证明。
  • defer cancel 放在大循环中：defer 到函数返回才执行，可能累积大量 timer/子节点；把一次迭代提成函数或显式 cancel。
  • 把 Context 当事件总线：它只有单向、一次性的关闭信号，不适合暂停/恢复、进度或多次通知。
  • 期望 AfterFunc.stop 等待完成：它只竞争“是否开始”。
  • 用 WithoutCancel 制造无界后台任务：应重新附加 deadline，并交给有所有权的任务管理器。
  • 把敏感对象放入 Value：Context 会沿调用链传播，容易扩大数据暴露和生命周期。

    }

总结

  1. Context 是不可变包装链；cancelCtx.children 又把可取消节点组织为树。
  2. Done Channel 惰性创建，Err 使用原子快路径，结构修改由 mutex 保护。
  3. 标准父子链直接登记 child，通常不会每层启动 goroutine；自定义 Context 才可能触发兜底监听 goroutine。
  4. 取消先发布 err/cause，再关闭 Done，然后递归取消子节点。
  5. timerCtx 复用父级更早的 deadline，并在取消时停止 timer、解除父子引用。
  6. Cause 保留业务根因；AfterFunc 处理取消后的异步动作；WithoutCancel 只截断控制流。
  7. Context 发出停止请求，但等待、资源回收和 goroutine join 仍由调用者负责。
