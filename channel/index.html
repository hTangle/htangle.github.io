Channel：Go 1.26.5 源码分析

Channel 不只是一个并发安全队列。它把三件事组合在一起：数据传递、goroutine 同步、调度器阻塞与唤醒。一次看似普通的 ch <- x，可能只是写入环形缓冲区，也可能把数据直接复制到另一个 goroutine 的栈上，最后还可能通过 gopark 把当前 G 交回调度器。

当前版本需要注意的变化

版本与 Channel 相关的变化
Go 1.14异步抢占落地，长时间运行的 goroutine 不再只能依赖函数调用协作让出 CPU
Go 1.18TryLock 等同步 API 增加，但 Channel 的核心 hchan 模型未改变
Go 1.23timer/ticker channel 改成对用户呈现无缓冲语义；未引用的 timer/ticker 可被 GC 回收
Go 1.24testing/synctest 以实验形式出现，runtime 开始具备 bubble 相关通道支持
Go 1.25testing/synctest 正式可用；当前 hchan、发送、接收、select 都包含 bubble 校验
Go 1.26本文基线；Channel 主体仍是 hchan + mutex + waitq + sudog，并与 timer、synctest 和泄漏检测协作

先把语义边界说清楚

⚠️ len(ch) 不能用于同步决策

它只是某一瞬间的观察。检查完成后，其他 goroutine 可以立即发送或接收；正确同步应使用实际的 Channel 操作或 select。

Channel 建立的 happens-before

  • 对无缓冲 Channel，接收发生在发送完成之前。
  • 对容量为 C 的缓冲 Channel，第 k 次接收 synchronizes before 第 k+C 次发送完成。这正是容量为 C 的 Channel 可模拟计数信号量的依据。
  • close(ch) synchronizes before 因关闭而返回零值的接收。

Channel 只发布与该次通信存在同步关系的写入；它不会自动保护所有共享变量。

hchan：Channel 的真实对象

语言里的 chan T 在 runtime 中最终指向 hchan：

type hchan struct {
    qcount   uint
    dataqsiz uint
    buf      unsafe.Pointer
    elemsize uint16
    closed   uint32
    timer    *timer
    elemtype *_type
    sendx    uint
    recvx    uint
    recvq    waitq
    sendq    waitq
    bubble   *synctestBubble
    lock     mutex
}

源码维护几个重要不变量：

  • 一般情况下 sendq 和 recvq 至少一个为空；同一 goroutine 在无缓冲 Channel 的 select 中同时等待发送与接收是例外。
  • 对缓冲 Channel，qcount > 0 意味着没有接收者在 recvq 等待。
  • 对缓冲 Channel，qcount < dataqsiz 意味着没有发送者在 sendq 等待。

这些不变量写在 chan.go#L9-L18，理解它们比背分支更重要。

环形缓冲区

  • qcount 是当前元素数量。
  • sendx、recvx 到达 dataqsiz 后回到 0。
  • 写入使用 typedmemmove，取出后使用 typedmemclr 清理槽位，让 GC 不再保留其中的指针。

创建：make(chan T, n)

makechan 先检查元素大小、对齐、容量乘法溢出，再按元素是否含指针选择分配方式：

无指针元素可把控制块和缓冲区合并分配，减少一次分配，也让 GC 无需扫描缓冲区；含指针元素必须保留精确类型信息供 GC 扫描。

发送：ch <- value

总体路径

这四条有效路径分别位于：等待接收者 L229-L233、缓冲写入 L236-L249、非阻塞失败 L252-L255、阻塞排队 L257-L309。

为什么非阻塞快路径可以不加锁

select { case ch <- v: default: } 会以 block=false 调用 chansend。源码先读取 closed，再用 full 判断当前不可发送。

这里并不承诺返回之后状态仍不变；它只需要证明在两次观察之间存在过一个“未关闭且不可发送”的时刻。真正会修改状态的路径都在同一把 hchan.lock 下，锁释放也负责刷新观察。

无缓冲 Channel：直接从发送者栈复制到接收者栈

如果 recvq 已有等待者，数据不经过 hchan.buf：

跨 goroutine 栈写入通常不允许普通代码直接进行。runtime 的 sendDirect 使用专门的写屏障路径；hchan.lock 还与栈收缩协议协作，不能在持锁时直接改变另一个 G 的状态。

阻塞发送：sudog + gopark

当没有接收者且缓冲区已满：

  1. 从缓存取得 sudog。
  2. sudog.elem 指向待发送值，sudog.g 指向当前 G。
  3. 把它加入 sendq，并挂到 gp.waiting，让栈复制逻辑能找到该指针。
  4. 设置 parkingOnChan，调用 gopark(chanparkcommit, &c.lock, ...)。
  5. chanparkcommit 在提交休眠的同时解锁 Channel。
  6. 被接收者或 close 唤醒后，检查 sudog.success；因关闭唤醒的发送者会 panic。

📝 阻塞的是 G，不一定是 M

gopark 把当前 goroutine 置为 waiting，M 返回调度循环，P 可以继续运行其他 G。这正是 Channel 能与 GMP 高效结合的原因，参见 GMP（Go 1.26.5 源码分析）。

接收：value, ok := <-ch

总体路径

关键源码是 chanrecv#L524-L700。非阻塞接收的 empty → closed → empty 检查使用原子读取，避免与并发关闭、清空缓冲区发生重排序后误判。

关闭但缓冲区未空

关闭只禁止后续发送，并不会丢掉已有数据：

因此 for v := range ch 会先耗尽缓冲区，再在 ok=false 时退出。

满缓冲区与等待发送者的交换

当缓冲区已满且 sendq 有发送者，接收不能只取走头部后结束，否则还要再唤醒发送者完成一次独立入队。当前 recv 在同一临界区完成交换：

缓冲区元素数量保持满容量，但最旧值被取走，等待发送者的新值进入队尾。

等待队列与 sudog

waitq 是双端信息的 FIFO 链表，节点不是 G 本身，而是 sudog：

之所以不把 G 直接放进等待队列，是因为一个 G 可能在 select 中同时等待多个 Channel，需要一组独立的等待记录。

waitq.dequeue 对普通等待者直接取队头；对 select 等待者还要 CAS selectDone，跳过已经被另一个 case 赢走的 sudog。

关闭：close(ch)

源码先在锁内构造待唤醒 G 列表，解锁后才调用 goready，见 closechan#L434-L485。这样避免在持有 Channel 锁时改变其他 G 状态，引发与栈收缩的锁顺序死锁。

  • 被唤醒的接收者获得零值和 ok=false。
  • 被唤醒的发送者回到 chansend 后发现 success=false，触发 send on closed channel。
  • Channel 没有“安全探测是否关闭再发送”的原子 API；通常应由唯一发送方负责关闭。

select：随机轮询、有序加锁、一次提交

编译器会把静态的零/单 case select 优化成简单操作；通用多 case 进入 selectgo。

为什么需要两种顺序

  • pollorder 使用 cheaprandn 随机打乱，避免永远偏向源码靠前的已就绪 case。随机不等于严格公平。
  • lockorder 按 hchan 地址排序，所有 goroutine 以一致顺序加多把 Channel 锁，避免 AB-BA 死锁，见 L206-L252。
  • 同一个 G 会为每个 case 建立 sudog。任意 case 成功后，用 selectDone CAS 决定唯一赢家，其他节点在第三阶段移除。

💡 nil Channel 在 select 中很有用

selectgo 会跳过 Channel 为 nil 的 case。把某个 Channel 变量设成 nil，可以动态禁用对应 case，而不会产生额外条件分支。

Timer Channel 的当前语义

Go 1.23 起，time.Timer 和 time.Ticker 的 Channel 对用户呈现同步、无缓冲语义。runtime 内部仍保留 timer 与 Channel 的特殊协作：

  • hchan.timer 指向向该 Channel 投递事件的 runtime timer。
  • empty、chanrecv、selectgo 会在需要时调用 maybeRunChan。
  • chanlen / chancap 会隐藏内部实现细节，对同步 timer channel 返回 0。

不要依赖 Timer.C 的底层容量。业务代码只应依赖 time 包承诺的 API 语义。

设计与使用建议

Channel 还是锁

Channel 不天然优于锁。队列、流水线、fan-in/fan-out、所有权转移适合 Channel；缓存、计数器、复合状态不变式通常更适合锁，参见 同步和锁（Go 1.26.5 源码分析）。

常见陷阱

  1. 多个发送方竞争关闭：指定唯一 closer，或先汇聚发送方再关闭。
  2. 接收方关闭 Channel：接收方通常不知道是否仍有发送者，容易触发发送 panic。
  3. 无缓冲返回通道造成泄漏：调用方提前返回后，工作 goroutine 可能永久卡在发送；必要时使用容量 1 或监听 ctx.Done()。
  4. 把缓冲容量当正确性条件：容量应影响吞吐和背压，而不是掩盖缺失的退出协议。
  5. 忘记 nil Channel 永久阻塞：初始化、关闭后置 nil、动态 select 都要明确状态机。
  6. 假定 select 严格公平：它随机化轮询，但不提供轮次公平或优先级保证。
  7. 复制数据的成本：Channel 传递大对象会复制值；可传指针，但要重新审视所有权与数据竞争。

可取消的发送与接收

select {
case out <- result:
    return nil
case <-ctx.Done():
    return context.Cause(ctx)
}

Channel 负责数据/事件，Context 负责跨调用链取消。二者组合比通过关闭业务 Channel 广播所有错误原因更清晰，参见 Context（Go 1.26.5 源码分析）。

📝 泄漏剖析的边界

Go 1.26 的 goroutineleak 是实验性 profile，依赖可达性判断，能识别大量永远无法解除的 Channel/锁等待，但不是所有逻辑泄漏都能被证明。

总结

  1. Channel 的核心是 hchan：环形缓冲区、发送/接收等待队列和一把 runtime mutex。
  2. 发送与接收优先直接匹配等待者，其次操作缓冲区，最后用 sudog + gopark 阻塞 G。
  3. 无缓冲通信可以在两个 goroutine 栈之间直接复制；runtime 必须与写屏障、栈复制和调度状态协作。
  4. close 是广播事件：接收者返回零值，发送者被唤醒后 panic；唤醒必须在释放 Channel 锁之后。
  5. selectgo 用随机轮询缓解偏置，用统一锁顺序防死锁，用多 sudog + CAS 保证只有一个 case 获胜。
  6. Channel 适合通信与所有权转移；共享状态不变式仍应选择锁。
