MCP：连接模型与外部世界的标准协议

📋 一句话定义

**MCP（Model Context Protocol，模型上下文协议）是一套让 AI 应用以统一方式发现、读取和调用外部能力的客户端—服务器协议。**它解决的不是“模型会不会思考”，而是“模型应用怎样用同一种接口接入文件、数据库、搜索、业务系统等不同能力”。

把 AI 应用想成一台笔记本电脑：每个外部系统原本都有不同插头，接一个系统就要写一套适配代码。MCP 更像 USB-C 标准——它规定连接、握手、能力发现、请求与响应的共同语言。设备仍由各自厂商实现，MCP 只让“怎么接”变得一致。

1. MCP 到底解决什么问题

没有 MCP 时，AI 应用接入 $N$ 个模型和 $M$ 个数据/工具系统，最坏可能维护接近 $N \times M$ 套定制集成：

flowchart LR
    A1["AI 应用 A"] --> X1["文件系统专用适配"]
    A1 --> X2["数据库专用适配"]
    A1 --> X3["搜索服务专用适配"]
    A2["AI 应用 B"] --> Y1["另一套文件适配"]
    A2 --> Y2["另一套数据库适配"]
    A2 --> Y3["另一套搜索适配"]

MCP 把集成边界收敛成协议：AI 应用实现 MCP 客户端，能力提供方实现 MCP 服务器。只要双方遵循同一契约，就可以组合使用。

flowchart LR
    Host["MCP Host<br/>AI 应用"] --> C1["MCP Client"]
    Host --> C2["MCP Client"]
    C1 <-->|"MCP"| S1["文件服务器"]
    C2 <-->|"MCP"| S2["业务系统服务器"]
    S1 --> FS[("本地文件")]
    S2 --> API[("数据库 / API")]

💡 关键价值

MCP 降低的是集成的组合复杂度，同时给能力发现、权限边界、错误返回和生命周期管理提供共同语义。

2. 三个核心角色：Host、Client、Server

2.1 Host：承载用户体验与决策

Host 是用户真正使用的 AI 应用，例如桌面助手、IDE、聊天应用或 Agent Runtime。它通常负责：

  • 管理对话、模型与用户授权；
  • 决定允许连接哪些 MCP Server；
  • 汇总上下文并把结果交给模型；
  • 隔离不同服务器，避免无意共享敏感信息。

2.2 Client：一条连接的协议代理

MCP Client 位于 Host 内部，负责与某个 Server 建立并维护会话、协商能力、收发协议消息。概念上通常是一个 Client 对应一个 Server 连接。

2.3 Server：对外暴露能力

MCP Server 把某个本地或远程系统包装成标准能力。它可以只是一个很薄的适配层，也可以包含鉴权、缓存、审计和业务逻辑。

⚠️ Server 不等于数据源

MCP Server 是协议边界；真正的数据或动作可能位于文件系统、数据库、SaaS API 或企业内网服务中。

3. Server 暴露的三类核心原语

原语直觉典型操作控制权倾向
Tools可执行的动作搜索、发消息、创建工单、执行查询模型提出调用，应用审批/执行
Resources可读取的上下文文件、表结构、日志、知识库条目应用按 URI 选择和读取
Prompts可复用的交互模板代码审查模板、故障分析模板用户或应用显式选择

可以把它们记成：Tool 是动词，Resource 是名词，Prompt 是做事的模板。

部分实现还会支持由 Server 向 Host 请求模型推理或用户补充信息等能力。它们仍然需要 Host 控制授权，Server 不应绕过用户直接获得无限模型或数据访问权。

4. 一次完整 MCP 会话怎样发生

sequenceDiagram
    participant H as Host
    participant C as MCP Client
    participant S as MCP Server
    participant D as 外部系统
    H->>C: 创建连接
    C->>S: initialize（协议版本与能力）
    S-->>C: Server 能力
    C->>S: initialized
    C->>S: tools/list
    S-->>C: 工具及输入 Schema
    H->>C: 请求调用 search_docs
    C->>S: tools/call + 参数
    S->>D: 执行真实查询
    D-->>S: 查询结果
    S-->>C: 结构化结果或错误
    C-->>H: 交给模型继续推理

这条链路可拆成四个阶段：

  1. 初始化：协商协议版本与双方能力；
  2. 发现：Client 查询 Server 提供哪些 tools、resources、prompts；
  3. 使用：读取资源、获取提示模板或发起工具调用；
  4. 关闭：会话结束，释放子进程、网络连接与临时资源。

MCP 消息通常采用 JSON-RPC 2.0 风格。一个工具调用在协议层可能长这样：

{
  "jsonrpc": "2.0",
  "id": 42,
  "method": "tools/call",
  "params": {
    "name": "search_docs",
    "arguments": {
      "query": "什么是 MCP？",
      "limit": 5
    }
  }
}

重点不是字段长什么样，而是：调用有唯一 ID、明确方法、结构化参数，以及与请求对应的结果或错误。

5. Transport：消息怎样从 Client 到 Server

MCP 把“消息语义”和“传输方式”分开：

  • stdio：Host 启动本地 Server 子进程，通过标准输入/输出通信；适合本地工具，部署简单，权限边界要谨慎。
  • Streamable HTTP：通过 HTTP 支持远程服务与流式响应；适合集中部署、跨网络访问、统一鉴权与审计。

因此，MCP 不是“只能跑本地”的协议，也不是某个固定网络服务。Transport 决定消息怎么运送，协议决定消息表达什么。

6. 能力发现为何重要

传统工具集成常把工具列表写死在应用代码里。MCP 允许 Client 在运行时询问 Server：

flowchart TD
    A["连接 Server"] --> B["协商 capabilities"]
    B --> C["tools/list"]
    B --> D["resources/list"]
    B --> E["prompts/list"]
    C --> F["把名称、描述、Schema 提供给模型"]
    D --> G["按 URI 选择上下文"]
    E --> H["按需获取工作模板"]

这使工具可以独立升级，但也带来一个工程要求：**描述与 Schema 必须稳定、精确、可理解。**如果两个工具描述含糊，模型就可能选错；如果 Schema 太宽松，错误会延迟到真实执行阶段。

7. 安全边界：标准连接不等于自动可信

MCP 统一了接口，却不会自动解决所有安全问题。至少要控制：

  • 最小权限：Server 只能访问完成任务必需的目录、表或 API；
  • 用户同意：发送消息、删除数据、付款等高风险操作需要清晰确认；
  • 输入校验：Server 不应因为参数来自模型就默认安全；
  • 输出隔离：来自 Resource 或 Tool 的内容可能包含提示注入；
  • 凭证管理：令牌由受控运行时保存，不写进提示词、日志或返回结果；
  • 审计追踪：记录谁在何时调用了什么能力，但对敏感参数做脱敏；
  • 网络防护：远程 Server 要防 SSRF、越权访问、重放与会话劫持。

‼️ 最常见的误解

“接入了 MCP”只表示双方能按共同协议通信，不表示 Server 是可信的，也不表示工具可以跳过审批直接执行。

8. 什么时候值得使用 MCP

适合：

  • 同一能力要被多个 AI Host 使用；
  • 一个 Host 要连接许多不同系统；
  • 希望能力能被动态发现、独立部署和升级；
  • 需要统一鉴权、审计、错误与生命周期语义。

不一定适合：

  • 应用里只有一个不会复用的简单函数；
  • 调用完全发生在同一进程，且没有协议隔离需求；
  • 极端低延迟路径无法接受序列化、进程或网络开销。

此时普通函数调用或内部 Tool API 可能更直接。

9. 常见误区

❓ - MCP 是一个 Agent 框架吗？

不是。它不规定 Agent 怎样规划、记忆或反思，只规定应用与能力提供方怎样交换上下文和调用能力。

❓ - MCP Server 自己一定包含大模型吗？

不一定。多数 Server 只是把外部系统包装成协议能力，本身可以完全不运行模型。

❓ - MCP Tool 和普通 Tool 是两种完全不同的东西吗？

语义上都表示可调用能力；区别在于 MCP Tool 通过 MCP 的发现、Schema 和调用消息暴露，普通 Tool 可能只是进程内函数或框架私有接口。

❓ - 模型会直接连接 MCP Server 吗？

通常不会。Host/Client 才负责连接、权限与真实 I/O；模型看到的是整理后的工具描述、上下文与调用结果。

10. 协议层深挖：Request、Response 与 Notification

截至 2026-08，MCP 当前正式协议修订版是 2025-11-25。它以 JSON-RPC 2.0 为消息基础，但面试时不能只回答“就是 JSON-RPC”：JSON-RPC 解决消息相关性，MCP 在其上定义了生命周期、能力、领域方法和安全语义。

消息类型是否有 id是否期待响应示例
Request是是initialize、tools/list、tools/call
Response与 Request 相同—result 或协议级 error
Notification否否notifications/initialized、notifications/tools/list_changed

10.1 协议错误与工具执行错误必须分开

这是高级面试的高频点：

  • Protocol Error：方法不存在、JSON-RPC 参数结构不合法、协议状态不允许。调用方通常不应让模型“猜着重试”。
  • Tool Execution Error：工具已被正确路由，但业务参数、权限、依赖或执行过程失败。应以工具结果中的错误语义返回，让模型能够修正参数、换策略或向用户解释。

例如，tools/call 缺少协议要求的 name 属于协议/参数错误；name=book_flight 合法，但座位售罄属于工具执行错误。把两者都返回 -32603 Internal error 会损害可恢复性和可观测性。

10.2 Notification 不是“无所谓的消息”

通知没有响应通道，因此适合表达状态变化，而不适合需要确认的关键业务动作。典型用途包括：

  • 工具、资源、Prompt 列表变化；
  • 资源内容变化；
  • Roots 变化；
  • 长请求进度；
  • 取消信号。

Server 声明 listChanged 后才应发送对应列表变化通知；Client 收到后重新拉取并更新缓存。==Capability 是契约，Notification 是契约允许后的事件。==

11. 初始化状态机与能力协商

MCP 连接不是“连上就调用”，而是一个严格状态机：

stateDiagram-v2
    [*] --> Disconnected
    Disconnected --> Initializing: 建立 transport
    Initializing --> Negotiated: initialize / InitializeResult
    Negotiated --> Ready: notifications/initialized
    Ready --> Ready: requests / notifications
    Ready --> Closing: EOF / DELETE / fatal error
    Closing --> [*]

initialize 至少交换：

  • protocolVersion：Client 提议版本，Server 返回希望采用的版本；Client 不支持则断开；
  • clientInfo / serverInfo：实现名称与版本；
  • capabilities：双方承诺支持的功能；
  • Server 可返回 instructions，作为 Host 理解该 Server 的提示，但它不是更高优先级的安全策略。

能力协商的工程原则：

  1. 只调用对方明确声明的能力，不要根据 SDK 是否有方法来推测；
  2. 未知能力向前兼容，记录但不崩溃；
  3. 实验能力显式隔离，不要把它当稳定契约；
  4. 版本与能力都进入连接缓存键，避免复用错误结果；
  5. Server instructions 与 Tool annotations 都视为不可信输入，不能覆盖 Host 安全规则。

12. MCP 是双向协议，不只是“Server 给模型工具”

基础介绍容易只讲 Server Features。完整心智模型还包括 Client 向 Server 提供的能力：

flowchart LR
    subgraph ServerFeatures["Server → Client"]
        T["Tools"]
        R["Resources"]
        P["Prompts"]
        L["Logging"]
    end
    subgraph ClientFeatures["Client → Server"]
        RO["Roots"]
        S["Sampling"]
        E["Elicitation"]
    end
    Srv["MCP Server"] --> ServerFeatures --> Cli["MCP Client / Host"]
    Srv --> ClientFeatures --> Cli

12.1 Roots

Roots 告诉 Server：Host 愿意暴露哪些文件系统边界。它是可见范围提示与协作边界，不是操作系统级沙箱。Server 仍应被进程权限、容器挂载和路径校验限制；不能因为 URI 在 Root 下就跳过授权。

12.2 Sampling

Sampling 允许 Server 请求 Client 侧模型生成内容。好处是 Server 不必绑定某个模型供应商，模型选择与凭证仍由 Host 控制。风险是递归调用、成本失控和数据泄露，因此要限制：最大递归深度、token 预算、可用工具、可见上下文和用户审批。

12.3 Elicitation

Elicitation 允许 Server 请求额外用户输入。适合缺少字段或需要业务确认的场景。敏感凭证不应通过普通表单随意收集；URL 模式需要防止钓鱼、开放重定向与不可信域跳转。

12.4 Tasks（实验能力）

2025-11-25 引入实验性 Tasks，用于长耗时、可轮询、可延迟取结果的请求。典型状态是：

stateDiagram-v2
    [*] --> working
    working --> input_required
    input_required --> working
    working --> completed
    working --> failed
    working --> cancelled
    input_required --> cancelled

面试时应强调：Tasks 不是把所有同步 Tool Call 自动变成异步任务。双方先协商 task capability，具体 Tool 还可声明 required、optional 或 forbidden；同时要处理 TTL、任务 ID 授权、轮询退避和结果清理。

13. Tool、Resource、Prompt 的高级建模

三类原语的差异不只在“动词/名词”：

设计维度ToolResourcePrompt
控制模型倾向模型选择倾向应用选择倾向用户选择
寻址方式工具名URI / URI TemplatePrompt 名称 + 参数
副作用可能有应以读取上下文为主无直接副作用
更新模型tools/list_changedlist changed、subscribe/updateprompts/list_changed
返回形态text/image/audio/resource/structuredContenttext 或 blob一组角色消息
典型缓存工具清单与 Schema内容按 URI/etag/版本模板按名称/版本

13.1 什么应建模成 Resource，而不是 Tool

若核心语义是“按稳定标识读取上下文”，优先 Resource，例如 repo://project/README.md。如果建成 read_file(path) Tool，模型需要生成路径，权限和缓存都更难做；但当读取过程需要复杂查询、权限决策或计算时，Tool 可能更合适。

13.2 Tool 的输入与输出 Schema

生产级 Tool 不只定义 inputSchema，还应在适用时定义 outputSchema 并返回 structuredContent。结构化输出可让 Host 做二次校验、UI 渲染和下游组合。为兼容旧 Client，Server 可能还需返回序列化后的 text content。

Tool annotations（例如只读、破坏性、幂等倾向）只能帮助 UI 与调度，不能当作安全证明。真正权限必须在执行路径验证。

14. Transport 与生产级会话设计

14.1 stdio 的真实边界

stdio 适合本地进程：Client 启动 Server，stdout 只能输出合法协议消息，日志走 stderr。其风险不是互联网攻击面，而是本地进程继承了过多环境变量、文件权限或网络权限。

14.2 Streamable HTTP 的状态模型

Streamable HTTP 使用单一 MCP Endpoint 支持 POST/GET，可借 SSE 传递流式消息。Server 可在初始化响应中签发 MCP-Session-Id；后续请求携带该 ID。生产实现需考虑：

  • Session ID 高熵、不可预测、禁止写入 URL；
  • 多实例部署时使用粘性路由或共享状态；
  • 404 Session Not Found 触发重新初始化，而不是无限重试旧会话；
  • 客户端离开时可用 DELETE 结束会话；
  • 每个后续 HTTP 请求携带协商后的 MCP-Protocol-Version；
  • 校验 Origin，本地 Server 只绑定 loopback，防 DNS rebinding。

14.3 断线重连不是简单重放

只读请求可重新发起；有副作用 Tool 的请求若在“Server 已执行、响应丢失”处断线，客户端无法仅凭超时判断是否执行。解决思路与分布式系统一致：业务幂等键、状态查询、去重存储和补偿动作，而不是寄希望于传输层提供 exactly-once。

15. Authorization 与威胁模型

HTTP MCP 的授权框架把受保护 MCP Server 视为 OAuth Resource Server，MCP Client 是 OAuth Client，Authorization Server 负责发 token。高级回答应覆盖：

sequenceDiagram
    participant C as MCP Client
    participant R as MCP Server / Resource Server
    participant A as Authorization Server
    C->>R: 未授权请求
    R-->>C: 401 + Protected Resource Metadata 位置
    C->>R: 读取 Resource Metadata
    R-->>C: authorization_servers + scopes
    C->>A: Authorization Code + PKCE + resource
    A-->>C: audience-bound access token
    C->>R: Bearer token
    R->>R: 校验 issuer / audience / expiry / scope

关键安全结论：

  • 禁止 token passthrough：MCP Server 不能把 Client 给它的 token 原样转发给下游 API；下游 token 应是另一条独立授权关系。
  • Audience binding：Client 请求 token 时带 resource，Server 只接受签发给自己的 token，防 confused deputy。
  • PKCE：授权码流程必须防截获；重定向 URI 精确匹配并校验 state。
  • 最小 scope 与渐进授权：只在某 Tool 真正需要时提升权限。
  • 提示注入隔离：Tool/Resource 返回的是不可信数据，不得把其中“忽略规则、发送密钥”等文本当系统指令。
  • Server 身份与供应链：安装本地 Server 等价于运行第三方代码，要固定版本、校验来源并最小化进程权限。

16. 生产架构、缓存与可观测性

16.1 MCP Gateway 什么时候有价值

企业环境常在 Host 与 Servers 之间增加 Gateway，用于统一认证、策略、审计、配额和服务发现。但 Gateway 不能只做透明转发：它需要保持 request ID、session、流式消息与取消语义，并防止不同租户的工具列表、缓存和凭证串用。

flowchart LR
    H1["IDE Host"] --> G["MCP Gateway"]
    H2["Chat Host"] --> G
    G --> P["Policy / AuthZ"]
    G --> O["Audit / Trace"]
    G --> S1["Repo Server"]
    G --> S2["Ticket Server"]
    G --> S3["Data Server"]

16.2 缓存策略

  • 工具/资源/Prompt 列表按 server identity + user/tenant + scope + protocol version 缓存；
  • 收到 list_changed 后失效，而不是静默长期缓存；
  • Tool 结果只有在语义只读、输入规范化且数据时效允许时缓存；
  • 不缓存短期 token、用户确认结果或跨租户敏感数据；
  • 稳定排序工具列表可提升模型 prompt cache 命中率。

16.3 可观测性

至少记录以下关联字段：

层级关键字段/指标
连接server、transport、protocol_version、session_id_hash、初始化耗时
发现tool_count、list latency、cache hit、list_changed 次数
调用request_id、tool_name、argument_hash、审批状态、耗时、结果类型
可靠性协议错误率、执行错误率、超时率、取消率、重试次数
安全scope、策略决策、拒绝原因、脱敏审计事件

不要默认记录完整参数与结果；可观测性必须与数据分级和脱敏策略一起设计。

17. 生产环境落地：从 Demo 到可运营服务

Demo 通常只需要“Server 能启动、Client 能列出 Tool”；生产环境还必须回答：谁能调用、调用了什么、失败能否恢复、版本是否兼容、资源是否隔离。

17.1 本地 stdio Server 的部署经验

stdio 最常见的问题不是协议，而是进程生命周期：

  • Host 启动 Server 时设置启动超时，例如 10 秒；超过阈值杀掉整个进程组，避免残留子进程；
  • Server 崩溃采用有上限的指数退避，避免错误配置导致每秒重启；
  • stdout 只允许 MCP JSON-RPC，任何启动 Banner、debug print 都写 stderr；
  • 不把 Host 的完整环境变量透传给 Server，只注入明确 allowlist；
  • 限制 Server 可见目录、网络和系统调用；“配置了 roots”不能替代操作系统沙箱；
  • Host 退出时先发送正常关闭信号，超时后再强制终止；
  • 每个 Server 进程设置 RSS、CPU 和打开文件数上限。

一个实用的监督策略：

项目建议起始值说明
启动超时10s超时视为不可用，不无限等待
连续崩溃阈值5 次/5min触发熔断并提示用户修配置
重启退避1s → 30s加随机抖动
单次调用默认超时30s每个 Tool 可单独覆盖
stdout 单消息上限8–16 MiB防内存爆炸，按业务调整
优雅退出窗口5s随后杀进程组

这些不是协议强制值，而是上线时可讨论、可压测的基线。

17.2 远程 Streamable HTTP 的部署经验

远程 MCP 常被普通 API Gateway 或负载均衡器“好心破坏”：

  • 代理缓冲 SSE，导致 Server 已发送进度但 Client 长时间收不到；
  • LB idle timeout 小于长任务时长，流被中途切断；
  • POST 与后续 GET 被分配到不同实例，但 Session 只存在进程内；
  • WAF 拦截 MCP-Session-Id 或 MCP-Protocol-Version 自定义 Header；
  • 自动重试 POST，重复触发有副作用 Tool；
  • 压缩或响应大小限制截断大 Tool Result。

上线前要验证整条链路，而不只直连 Pod：

真实 Client
  → DNS/CDN
  → WAF
  → Load Balancer
  → API Gateway
  → MCP Server
  → 下游系统

如果 Session 存内存，使用粘性路由且明确实例摘除行为；更稳妥的是把必要会话状态放共享存储，但不要把完整敏感上下文无期限持久化。扩容、滚动升级和故障迁移时必须测试 Session 404 后的重新初始化。

17.3 工具目录不能无界增长

生产系统常在 tools/list 堆积几百个工具，结果是 prompt 成本上涨、模型选错、缓存频繁失效。经验上应：

  1. 按用户 scope 过滤，不把无权限工具暴露给模型；
  2. 按当前任务域或产品模块过滤；
  3. 对描述相近的 Tool 做离线混淆测试；
  4. 保证列表稳定排序，非必要不改变 Schema 文本；
  5. 列表变化使用通知失效缓存，不让 Client 每轮全量拉取；
  6. 对大工具集使用分层发现或 tool search；
  7. 记录每个 Tool 的曝光次数、选择次数、成功率和误选率，长期不用的 Tool 下线。

17.4 下游依赖必须做隔离

一个 Server 往往连接多个下游。不要让慢数据库拖死所有 Tool：

  • 每个下游独立连接池、超时、并发上限和熔断器；
  • Tool 入口做 bulkhead 隔离，高成本 Tool 使用独立队列；
  • 下游 429 尊重 Retry-After，不要所有实例同步重试；
  • 只读 Tool 可短期缓存，写 Tool 不做模糊缓存；
  • 取消信号尽量传播到下游，避免 Client 已离开但任务继续消耗资源；
  • 对长任务使用 Tasks 或业务异步任务，不长期占用 HTTP 请求。

18. 生产事故模式与排障 Runbook

18.1 Server 一直显示“连接失败”

按层排查：

  1. 进程是否启动、工作目录和可执行文件是否正确；
  2. stdout 是否混入日志或 Banner；
  3. 第一条 initialize 是否到达；
  4. 协议版本是否能协商；
  5. initialized 通知后再调用业务方法；
  6. 远程链路是否被代理、TLS、Origin、WAF 拦截；
  7. 用 request ID 对齐 Client 与 Server 日志。

🐛 高频事故：stdout 污染

Python/Node 依赖在启动时输出一行提示，Client 把它当 JSON-RPC 解析，表现为“初始化随机失败”。修复是日志统一走 stderr，并在 CI 做协议流纯净性测试。

18.2 调用偶发重复执行

典型链路：Tool 已完成写操作 → 响应在代理层丢失 → Client 超时重试 → 重复创建。排查时不要只看 Client timeout；用业务幂等键、MCP request ID 与下游 transaction ID 串联日志。

修复优先级：

  1. 写 Tool 增加业务幂等键；
  2. Server 保存幂等结果并检测同键不同参数；
  3. Client 对非幂等 Tool 默认不自动重试；
  4. 超时后先查询业务状态；
  5. 为无法幂等的动作提供补偿与人工处理入口。

18.3 SSE 在测试环境正常、生产环境卡住

检查 LB/Ingress 是否启用响应缓冲、idle timeout、最大连接时长、HTTP/2 转换和压缩。用定期进度或 ping 验证连接存活，但 heartbeat 不能掩盖真正卡死的下游。监控“Server 写出时间”和“Client 收到时间”的差值，才能定位缓冲发生在哪一层。

18.4 更新 Server 后模型仍调用旧参数

原因通常是 Tool Schema 缓存、prompt cache 或滚动升级期间新旧实例并存。处理方式：

  • 兼容期内新增字段而不立刻删除旧字段；
  • Tool 名或 Schema 发生破坏变化时创建新版本，例如 create_ticket_v2；
  • 让 list change 通知和缓存 TTL 配合；
  • 确保同一服务池实例返回一致工具清单；
  • 灰度时按 Host/tenant 固定版本，不让一次会话跨版本漂移。

18.5 返回“没有数据”，其实是下游失败

不要把 timeout、403、解析失败统一转换为空数组。Dashboard 上“Tool 调用成功率 99.9%”可能只是错误被吞掉。Tool Result 必须区分：

  • success + empty：真实空数据；
  • business_error：业务不允许；
  • dependency_error：下游失败；
  • cancelled/timeout：执行未完成；
  • partial：只得到部分数据。

19. 发布、灰度、SLO 与上线检查单

19.1 推荐发布顺序

  1. 在 CI 校验 Schema、协议用例和安全扫描；
  2. 用录制的 Client 会话做兼容回放；
  3. 部署影子实例，只接发现/只读流量；
  4. 按内部账号或 tenant 灰度 1% → 10% → 50%；
  5. 观察 Tool 选择、协议错误、执行错误、p95 与下游压力；
  6. 再开放写 Tool；高风险 Tool 单独灰度；
  7. 保留可快速回滚的旧 Server 和 Schema；
  8. 稳定后再清理兼容字段。

19.2 建议 SLO

SLO 必须按 Tool 类型拆分，不能用一个平均值掩盖长任务：

SLI示例目标备注
initialize 成功率≥ 99.9%排除用户主动取消
tools/list p95< 500ms命中缓存时应更低
只读 Tool 可用性≥ 99.9%以业务成功定义
写 Tool 重复副作用率接近 0单独作为安全指标
Tool p95按工具设定不用全局平均
非用户原因取消率< 0.1%反映代理/会话稳定性

错误预算耗尽时，停止扩大发布，优先修复可靠性；不要通过放宽“成功”定义维持漂亮数字。

19.3 上线前检查单

  • 协议版本和 capabilities 在连接日志中可见；
  • stdio stdout 纯净，日志只走 stderr；
  • HTTP Origin、TLS、OAuth audience、scope 校验完成；
  • 每个 Tool 明确只读/写入、幂等、超时、取消和重试语义；
  • 非幂等 Tool 有幂等键或状态查询方案；
  • tools/list 按 tenant/user/scope 隔离并稳定排序；
  • Session 在扩容、摘除、重启后行为已压测；
  • SSE 穿过真实 LB/WAF/Ingress 验证过；
  • 日志可按 request/call/session/业务 ID 串联且已脱敏；
  • 下游有超时、熔断、bulkhead 和容量保护；
  • 高风险 Tool 有明确审批 UI 与审计；
  • 有灰度、回滚、故障演练和 On-call Runbook。

20. 一些额外的QA

❓ - Q1：MCP 与 REST API 的本质区别是什么？

REST 主要规范资源型 HTTP 接口；MCP 是面向 AI Host 的有状态能力协议，包含初始化、能力发现、双向请求、通知、上下文原语与多种 Transport。MCP Server 背后仍可调用 REST。若只有一个固定服务和明确调用方，REST 更简单；若要让多个 AI Host 动态发现并统一使用能力，MCP 更有价值。

❓ - Q2：为什么 MCP 不能替代 Agent Framework？

MCP 不负责计划、记忆、停止条件、模型选择和多 Agent 协作。它提供能力与上下文的标准边界；Agent Framework 决定何时使用这些能力以及如何形成执行循环。

❓ - Q3：如何做多租户 MCP Server？

身份必须来自经过验证的请求凭证，而不是模型参数；工具列表、Resource、缓存和限流都以 tenant/user/scope 分区；下游凭证独立交换；审计保留 request/session 关联；任何连接级状态都不能成为跨租户身份来源。

❓ - Q4：如何处理 tools/list 很大导致上下文昂贵？

先按权限和任务域裁剪，再做分层发现或工具搜索；Schema 保持短而精确、排序稳定；缓存清单但响应 list_changed；用离线 eval 评估召回率与误选率，而不是简单把几百个工具全塞给模型。

❓ - Q5：一次 tools/call 超时，能否直接重试？

先区分只读、幂等写和非幂等写。非幂等动作可能已经生效但响应丢失，应使用业务幂等键或查询状态；只有明确可重试的暂时性错误才指数退避，并设置次数和总预算。

❓ - Q6：Capability negotiation 和 API versioning 各解决什么？

协议版本描述消息契约的共同基线；Capability 描述该连接上双方实际支持的可选功能。相同协议版本的两个实现仍可能拥有不同能力，因此两者都必须检查。

❓ - Q7：MCP 最危险的安全误区是什么？

把“协议兼容”误认为“服务可信”。Server 描述、Tool annotation 和返回内容都可能恶意；Host 仍需建立来源信任、沙箱、最小权限、用户确认、token audience 校验与提示注入隔离。
