垃圾收集器：Go 1.26.5 源码分析

Go 1.26.5 默认使用 Green Tea GC。当前 GC 的总体语义是并发、精确、非分代、不压缩；Green Tea 通过重新组织小对象的标记与扫描工作，提高内存访问局部性和多核扩展性。

IMPORTANT

本文的结论 Go 1.26.5 的 GC 仍然是 concurrent mark-and-sweep；Green Tea 优化的是 mark/scan 的局部性与扩展性，不是把 Go 改成分代 GC，也不是让对象移动或压缩。

一、GC 的基本问题

可达性，而不是“出了作用域”

GC 从 root 集合出发，沿指针图寻找可达对象；不可达对象才有资格在 sweep 阶段被回收。

即使 D 与 E 互相引用，只要 root 到不了它们，整个环仍可回收。反过来，函数返回不保证其对象立即死亡：只要被全局 cache、goroutine、closure、channel buffer 等继续引用，它仍然存活。

三色抽象仍有用，但不是数据结构说明书

  • 白色：尚未确认存活；
  • 灰色：已发现，但其引用尚未全部扫描；
  • 黑色：已发现且引用已扫描。

三色是正确性推理模型。Go 1.26 的 Green Tea 并不一定把每个灰对象都作为独立队列元素；对小对象，它可用 mark bit 已设、scan bit 未设 表示“灰”，再把整个 span 入队。

NOTE

弱三色不变式 并发标记期间必须避免黑对象指向一个无法再被发现的白对象。Go 的混合写屏障通过 shade 被覆盖的旧指针和写入的新指针，加上栈处理规则，维持这一不变式。

二、一个完整 GC cycle

mgc.go 顶部注释 给出了权威阶段划分：

1. Sweep termination：STW

新一轮 mark 不能与旧一轮尚未完成的 sweep 混在一起。runtime 停止世界，完成必要的 unswept span，并让所有 P 在一致的阶段边界开启写屏障。

2. Concurrent mark：主要并发阶段

进入 _GCmark 后：

  • 写屏障开启；
  • scheduler 调度 dedicated/fractional/idle mark worker；
  • 分配者按照 assist debt 帮忙扫描；
  • 扫描 goroutine stack、globals 和 runtime roots；
  • 标记期新分配对象直接为黑色。

root 扫描任务入口是 markroot。扫描 goroutine stack 时会短暂停止目标 G，完成精确指针扫描后恢复。

3. Mark termination：STW

当所有 root job 和灰对象工作都耗尽，gcMarkDone 执行分布式终止检测，见 mgc.go#L1015-L1095。随后 STW 进入 mark termination，完成 cache flush、统计和 sweep generation 切换。

4. Concurrent sweep

sweep 逐 span 比较本轮 mark bits 与 allocation bits：

  • 未标记 slot 变为空闲；
  • span 仍有存活对象则回到对应 mcentral；
  • span 完全空闲则 page 返回 mheap；
  • 后台 sweeper 与 allocation-time sweep 共同推进。

这里回收的是 可复用地址空间，不保证物理页立刻归还 OS。后者由 scavenger 处理。

三、写屏障：并发正确性的核心

Go 1.26.5 的指针写入逻辑可用下面的伪代码理解：

writePointer(slot, ptr):
    shade(*slot) // Yuasa deletion barrier：保住旧引用
    if currentStackIsGrey {
        shade(ptr) // Dijkstra insertion barrier：保住新引用
    }
    *slot = ptr

实际说明见 mbarrier.go#L24-L131。源码进一步优化为通常不检查当前栈是否灰，直接同时 shade 两者，以减少热路径条件判断。

为什么栈写通常不走写屏障

栈属于当前 goroutine 私有，GC 通过停止该 G 并扫描整个栈来获得一致视图。heap/global 的指针写才是并发 mutator 与 marker 最危险的交叉点。

批量写也必须有 barrier

typedmemmove、slice copy、map 更新等可能批量写指针，runtime 使用 bulkBarrierPreWrite 等路径在真正复制前处理指针，见 mbarrier.go#L150-L220。这也是为什么 runtime 源码中的 //go:nowritebarrier///go:nowritebarrierrec 是严格约束。

四、Green Tea：Go 1.26 默认的新标记扫描路径

Green Tea 要解决的局部性问题

以对象为单位组织扫描工作时，处理过程是：发现对象 -> 标记对象 -> 把对象指针压入 work buffer -> 之后弹出并扫描。若对象很小且分散，扫描会频繁访问不同 span、不同 metadata 与不同 cache line，局部性较差。

Green Tea 的核心注释位于 mgcmark_greenteagc.go#L5-L33：延迟扫描，在同一 span 上积累多个待扫描对象，再批量扫描。

marks 与 scans

符合条件的小对象 span 尾部有一个 spanInlineMarkBits：

type spanInlineMarkBits struct {
    scans [63]uint8
    owned spanScanOwnership
    marks [63]uint8
    class spanClass
}
  • marks[i] = 1：对象已被发现；
  • scans[i] = 1：对象已经扫描；
  • marks=1, scans=0：该对象等价于灰色；
  • owned：控制 span 是否已被某个 worker 获取/入队。

gcUsesSpanInlineMarkBits 当前要求 metadata 可放 span 且对象大小至少 16 B，见 #L252-L260。不满足条件的大对象或其他特殊对象仍走对象级 workbuf 路径。

发现指针：标记对象，排队 span

tryDeferToSpanScan 的步骤是：

  1. 用 arena bitmap 快速判断地址所在 span 是否支持 inline mark bits；
  2. 计算对象索引；
  3. 原子设置 marks；
  4. noscan 对象直接记为完成；
  5. scan 对象尝试获取 span ownership；
  6. 把代表该 span 的条目放入当前 P 的 FIFO span queue。

为什么 span queue 用 FIFO

源码说明 FIFO 比传统 workbuf 的 LIFO 更有利于“让同一 span 继续积累对象”，见 mgcmark_greenteagc.go#L19-L28。每个 P 有本地可窃取的 spanQueue，减少全局争用；工作不足时可从其他 P steal。

GC work 的优先级也经过设计：先消费 P-local 对象 workbuf，再消费 P-local span queue，然后才访问全局/窃取，见 mgcwork.go#L51-L68。优先对象级工作可以给 span 更多时间积累待扫对象。

批量扫描 span

scanSpan 会：

  1. 释放 span ownership；
  2. 若期间只有一个 mark，直接 fast-track 单对象扫描；
  3. 否则计算 marks - scans，得到本轮待扫对象集合；
  4. 稀疏时按对象扫描；
  5. 密度足够且平台支持时调用 packed/vectorized span scan；
  6. 把发现的新指针继续送入 span queue 或传统 object queue。

TIP

Green Tea 没有消灭三色标记 它把“灰对象队列”部分改写为“mark bit 与 scan bit 的差集 + span queue”。可达性、安全屏障、root scan、assist、mark termination、sweep 等总体协议仍然存在。

五、并行标记、work buffer 与 assist

GC worker

调度器会运行三类 mark worker：

  • dedicated：专用执行标记；
  • fractional：按 pacer 目标使用部分 CPU；
  • idle：只利用本来空闲的 P。

本地 gcWork 持有两个 object workbuf、一个 Green Tea span queue、临时 pointer buffer 与统计字段，见 mgcwork.go#L70-L137。双 workbuf 提供迟滞，降低频繁访问全局 full/empty 列表的竞争。

Allocation assist：谁制造垃圾，谁帮助清扫

GC 期间分配会产生 assist debt。mallocgc 先扣减 credit；债务过高时当前 goroutine 进入 gcAssistAlloc，执行一部分标记工作后才能继续大量分配。

它既限制 GC 期间的无限制 heap 增长，也把扫描成本按分配速率反馈给 mutator。因此延迟尖刺不一定全来自 STW，也可能是业务 goroutine 在做 assist。

六、Pacer：决定何时开始、用多少 CPU

GOGC 的堆目标

稳态下可用近似模型理解：

TargetHeap≈LiveHeap+GOGC100×(LiveHeap+ScanStacks+ScanGlobals)TargetHeap \approx LiveHeap + \frac{GOGC}{100} \times \left(LiveHeap + ScanStacks + ScanGlobals\right)TargetHeap≈LiveHeap+100GOGC​×(LiveHeap+ScanStacks+ScanGlobals)

GOGC=100 不是简单地承诺“内存翻倍才 GC”，因为当前 pacer 还纳入可扫描栈、全局、memory limit、预测误差和最小 heap goal。源码控制器结构见 gcControllerState。

GOMEMLIMIT 是 soft limit

memory limit 覆盖 runtime 管理的大部分内存，可用官方定义近似理解：

runtime memory = /memory/classes/total:bytes
               - /memory/classes/heap/released:bytes

它不包含 binary mapping、cgo/C 自己分配的内存等外部来源。配置方式：

GOMEMLIMIT=1500MiB ./app

或：

debug.SetMemoryLimit(1500 << 20)

limit 是软的：当配置过低导致 GC thrashing 时，runtime 宁可暂时超过 limit，也要保证程序继续前进。内部 gcCPULimiter 使用 leaky bucket，将 GC CPU 保守限制在大约 50%，见 mgclimit.go#L9-L30。完整调优模型见 A Guide to the Go Garbage Collector。

WARNING

容器里不要直接把 GOMEMLIMIT 等于 pod limit 给 thread stack、runtime metadata、cgo、共享库、profile、内核缓冲和瞬时峰值留余量。soft limit 也不是 OOM 的绝对防线。

触发条件

gcTrigger.test 支持：

  • heap 达到 controller trigger；
  • 距离上次 GC 超过强制周期；
  • runtime.GC() 要求进入指定 cycle。

runtime.GC() 会等待一次完整 cycle 的 mark 和 sweep，而不是“发个信号立即返回”，实现见 mgc.go#L519-L592。

七、栈扫描与 GC

goroutine stack 是 root 的重要组成部分。GC 获得目标 G 的 stack ownership，依据编译器生成的 stack map 精确识别指针；若 G 停在异步安全点，最内层 frame 可能需要保守扫描。结构见 mgcstack.go#L166-L198。

栈越多、越大、指针越密集，root scan 成本越高。goroutine 数量不仅是 scheduler 指标，也直接影响 GC 与内存，详见 栈空间管理。

八、Sweep 与 Scavenger

Sweep generation

mspan.sweepgen 与 mheap_.sweepgen 共同表示 span 未 sweep、正在 sweep、已 sweep 或被 mcache 缓存等状态，字段规则写在 mheap.go#L494-L500。每轮 GC sweepgen 增加 2，让 mcentral 的两套 spanSet 交换 swept/unswept 角色。

这是一种代际编号，不是“分代 GC”。

Scavenger 为什么独立

GC/sweep 决定对象和 page 是否可复用；scavenger 决定空闲 page 的物理 backing 是否应该释放。后台 scavenger 默认只愿意消耗约 1% mutator 时间，源码见 mgcscavenge.go#L100-L126。

在 memory limit 压力、heap grow 或 debug.FreeOSMemory 场景，还可能同步、更积极地 scavenging。

九、Finalizer、Cleanup 与泄漏理解

带 finalizer 的对象不会在第一次发现不可达时立刻完全释放；runtime 需要排队执行 finalizer，并可能让对象或其引用多活至少一个周期。finalizer 还会带来不可预测调度和依赖顺序，不应作为业务资源释放的主要机制。

工程原则：

  • 文件、连接、锁等资源必须显式 Close/Unlock/Cancel；
  • finalizer/cleanup 只做最后防线；
  • 不在 finalizer 中依赖退出时一定执行；
  • 诊断“泄漏”时区分 heap retention、goroutine leak、外部/C 内存和高分配 churn。

Go 1.26 还提供实验性的 goroutineleak profile。它借助 GC 可达性判断一部分永远无法被唤醒的 goroutine，但对仍被 runnable goroutine 或 global 引用的同步原语可能无法判定。该能力需要构建时开启实验，详情见 Go 1.26 Release Notes。

如何解释常见现象

GC 很频繁但 heap 不大

优先检查：

  • GOMEMLIMIT 是否设置过低；
  • allocation rate 是否很高；
  • GOGC 是否太小；
  • non-heap runtime/cgo 内存是否挤压 limit；
  • live heap 是否接近 limit，导致 pacer 无 runway。

heap profile 看不大但 RSS 很高

检查：

  • goroutine stack；
  • heap free 但未 released；
  • page/span 碎片；
  • cgo 或 mmap；
  • binary/shared library mapping；
  • profile 采样误差。

P99 在 GC 期间抬升

不要只看 STW：还要查看 allocation assist、CPU 被 mark worker 占用、page fault/scavenging、scheduler run queue 与锁竞争。

十一、调优原则

优先优化分配图，而不是先调 GOGC

  1. 减少无意义分配和复制；
  2. 缩小长期存活指针图；
  3. 控制 goroutine、queue、cache 上限；
  4. 再根据 CPU/内存预算调整 GOGC；
  5. 在容器中配置合理 GOMEMLIMIT 并留 headroom；
  6. 用稳定 workload 比较吞吐、P99、GC CPU、peak RSS。

GOGC 与内存的基本权衡

  • 提高 GOGC：通常 GC 更少、CPU 更低、峰值 heap 更高；
  • 降低 GOGC：通常 GC 更频繁、CPU 更高、heap 更低；
  • GOGC=off：关闭比例触发，但若设置 memory limit，limit 仍会推动 GC；
  • 极低 memory limit：可能进入高频 GC，soft limit 最终选择允许超限以避免死亡螺旋。

不要把这些当成单调定律：cache locality、assist、scavenger、kernel page fault 和 workload phase 都会改变结果。

十二、常见误区

误区Go 1.26.5 正确理解
Green Tea 是分代 GC不是；仍是非分代 mark-and-sweep

总结

Go 1.26.5 的 GC 可以压缩为两层认识：

正确性层：root + 混合写屏障 + allocate black + 并发终止检测
性能层：Green Tea span batching + per-P work + pacer + assist + sweep/scavenge

Green Tea 没有推翻 Go GC，而是重新组织小对象扫描：把单个对象的随机访存，尽可能转化为同 span 的批量处理。理解它时必须同时连接 内存分配器 的 span/bitmap 布局和 栈空间管理 的 root scan，才能形成完整内存模型。
