Recall：召回阶段与 Recall@K 指标

NOTE

一句话定义 **Recall 既指“尽量找全相关候选”的系统阶段目标，也指衡量相关对象被找回比例的指标。**它关心的是漏掉了多少，而不是结果是否已经排在最佳位置。

在搜索、推荐和 RAG - 从检索到可信生成的完整系统 中，后续 Ranking - 从候选集合到最优顺序 再强，也无法挽回召回阶段从未提供的正确证据。因此高级工程师讨论 Recall 时，必须同时讲清：分母如何定义、标签是否完整、K 取多少、延迟成本多少、哪个业务切片正在漏。

1. 从混淆矩阵理解 Recall

对于二分类：

实际相关实际不相关
系统返回TPFP
系统未返回FNTN
Recall=TPTP+FNRecall=\frac{TP}{TP+FN}Recall=TP+FNTP​

Recall 高表示漏掉的相关对象少。与它互补的是 Precision：

Precision=TPTP+FPPrecision=\frac{TP}{TP+FP}Precision=TP+FPTP​

如果把整个知识库都返回，Recall 可能接近 1，但 Precision、延迟和上下文成本会崩溃。生产系统追求的是约束下的高 Recall，而非无成本最大化。

2. 排序场景中的 Recall@K

对于查询 qqq，设相关集合为 RelqRel_qRelq​，系统前 KKK 个结果为 TopKqTopK_qTopKq​：

Recall@K(q)=∣Relq∩TopKq∣∣Relq∣Recall@K(q)=\frac{|Rel_q\cap TopK_q|}{|Rel_q|}Recall@K(q)=∣Relq​∣∣Relq​∩TopKq​∣​

例：某问题有 4 个相关段落，Top-10 找到其中 3 个，则 Recall@10 = 0.75。

WARNING

分母决定指标含义 如果只标了一个“标准答案段落”，Recall@K 可能退化成是否命中的 0/1；如果真实还有多个未标注相关段落，系统返回它们反而会被错误当作无关结果。

3. 容易混淆的几个指标

指标定义适合回答
Recall@KTop-K 找到的相关项 / 全部相关项相关证据找全多少？
Hit@K / Success@KTop-K 是否至少有一个相关项能否命中任一可用答案？
Precision@KTop-K 中相关项比例返回结果有多干净？
MRR第一个相关结果名次倒数的均值第一个正确结果来得多早？
nDCG@K考虑等级相关性与位置折损高价值结果排序是否合理？
ANN Recall@K近似向量结果覆盖精确向量 Top-K 的比例ANN 索引损失多少？
Coverage有结果的查询、实体或目录覆盖比例系统是否遗漏一整类内容？

Hit@5 = 1 只说明前 5 至少命中一个；如果回答需要同时找到“配置说明”和“版本限制”两个证据，它仍可能不足。

4. 召回阶段不是单一算法

候选可以来自多条并行通路：

因此“召回模型”可能是关键词检索、向量双塔、协同过滤、规则、知识图谱、多查询扩展或它们的组合。它们共同目标是在可接受预算内扩大正确候选的覆盖面。

5. K 是一个系统参数，不是随手填的数字

增大 K 通常能提高 Recall，但会带来：

  • 检索与网络传输成本上升；
  • reranker 计算量上升；
  • 去重和 ACL 检查负担上升；
  • RAG Context 噪声与 token 成本上升；
  • 尾延迟变差。

应分别定义多个 K：

  • K_retrieval：每路检索返回多少；
  • K_union：融合后保留多少；
  • K_rerank：送入昂贵精排多少；
  • K_context：最终装入模型多少。

不要用一个 top_k 参数贯穿所有层，否则很难诊断是哪一层截断了正确证据。

6. Macro、Micro 与分层聚合

假设不同查询的相关文档数量不同：

MacroRecall@K=1∣Q∣∑q∈QRecall@K(q)MacroRecall@K=\frac{1}{|Q|}\sum_{q\in Q}Recall@K(q)MacroRecall@K=∣Q∣1​q∈Q∑​Recall@K(q)

Macro 对每个查询等权。Micro 则先汇总所有 TP/FN：

MicroRecall@K=∑qTPq∑q(TPq+FNq)MicroRecall@K=\frac{\sum_q TP_q}{\sum_q(TP_q+FN_q)}MicroRecall@K=∑q​(TPq​+FNq​)∑q​TPq​​

Micro 会让相关文档多的查询权重更大。生产评估通常同时报告：

  • macro：普通用户的一次查询体验；
  • micro：所有相关证据的总体覆盖；
  • business-weighted：按收入、风险或流量加权；
  • sliced：按语言、租户、意图、数据源、新旧文档拆分。

7. 真正困难的是 Ground Truth

搜索相关性不是天然标签。构建 qrels（query relevance judgments）的方法包括：

  • 专家或标注员逐项判断；
  • 从客服解决记录、文档引用、点击和任务成功反推；
  • 多个系统结果做 pooling，再统一标注；
  • LLM 预标注 + 人工审核；
  • 基于已知文档反向生成问题，再做质量筛选。

7.1 不完整标注偏差

未标注文档不等于不相关。新系统找到了旧系统从未暴露的好结果时，离线分数可能被低估。

改进方式：

  • 汇聚 BM25、dense、新旧系统的候选后再标注；
  • 对系统间分歧样本优先人工复核；
  • 使用 graded relevance：完全支持、部分支持、仅背景、无关；
  • 定期补充线上失败、零结果和新鲜内容；
  • 记录标注准则版本与标注一致性。

7.2 点击不是纯相关性标签

点击受到位置、标题、UI、品牌和曝光影响。未点击结果可能只是没被看到。可使用随机化、interleaving、逆倾向加权或人工集校准，但不能把日志直接当真值。

8. 多证据问题的 Recall

一些问题只需任意一个证据，另一些问题要求完整证据集合：

  • Any-evidence success：至少命中一个足以回答的片段；
  • All-evidence recall：所需证据都被找到；
  • Entity coverage：关键实体是否全部覆盖；
  • Hop coverage：多跳推理每一跳是否找到依据。

例如“版本 A 到 B 的行为变更和回滚方法”同时需要 release note 与 runbook。只找到一个，Hit@K 是成功，但端到端回答仍可能缺失。

9. 提升 Recall 的主要杠杆

9.1 检索算法层

  • 增大 HNSW efSearch、IVF nprobe 或 ANN 候选数；
  • 混合 BM25、dense、精确字段和实体检索；
  • 训练领域 embedding，加入 hard negatives；
  • 对短查询、代码、数字、跨语言采用不同路由；
  • query expansion、multi-query 与拼写纠正。

9.2 数据与索引层

  • 修复解析失败、OCR、表格和代码块丢失；
  • 调整 chunk 大小、overlap 与 parent-child；
  • 补全标题、层级、时间和实体元数据；
  • 缩短索引新鲜度和删除传播延迟；
  • 避免新旧 embedding 混用。

9.3 候选融合层

  • 每个通路保留独立 quota，避免强势通路挤掉长尾；
  • 使用 RRF 或校准后的学习融合；
  • 去重时保留最佳 chunk，也保留 parent 关系；
  • 过滤感知 ANN，避免过滤后候选耗尽。

10. Recall 与 Precision 的工程权衡

候选生成阶段通常偏向 Recall，精排和 Context 阶段逐步提高 Precision：

若最终答案错误，不应盲目增大 Context K。先定位 gold evidence 在哪一层消失：

  1. 未进入 Top-1000：召回问题；
  2. 进入候选但未进 Top-30：排序问题；
  3. 进 Top-30 但 Context 未选中：上下文装配问题；
  4. 已在 Context 却未正确使用：生成或提示问题。

11. 线上指标与 SLO

建议至少建立四组仪表盘：

组别指标
质量Recall@K、Hit@K、分通路贡献、zero-result rate
系统p50/p95/p99、timeout、fallback、候选数分布
数据index lag、解析失败、无向量文档、删除传播时间
下游rerank 入选率、context evidence coverage、答案支持率

Recall 无法对每次线上查询实时计算，因为通常不知道全部相关项。线上代理信号包括：

  • 用户改写同一查询；
  • 零结果后转人工或打开目录浏览；
  • 答案“无依据”或低置信度比例；
  • 被引用文档的最终任务成功率；
  • 抽样查询的持续人工评审。

12. 生产事故模式

12.1 总 Recall 很高，关键租户却完全失效

大租户或主流语言掩盖小切片。必须按租户、语言、数据源和权限组设最低门槛，而不只是全局均值。

12.2 Offline Recall 上升，线上任务成功下降

可能原因：K 增大导致精排超时、Context 噪声增加；离线标签过时；新增召回结果不可访问；或指标与业务只需的“可回答证据”不一致。

12.3 ANN Recall 很高，业务 Recall 很低

ANN 忠实找到了 embedding 认为最近的向量，但 embedding 本身不理解领域语义，或相关文档未被正确解析和切分。

12.4 去重后 Recall 降低

用文档 ID 粗暴去重可能只保留一个段落，丢失同文档内其他必要证据。应区分近重复去除与多证据保留。

12.5 权限过滤让候选数骤降

后过滤把 ANN Top-K 大量剔除。应使用 pre-filter/filter-aware ANN，或按可见语料动态扩大 num_candidates，同时保持严格 ACL。

13. 实验与发布方法

一次 Recall 优化应保留证据链：

  1. 明确要改善的查询切片和失败类型；
  2. 冻结带版本的离线评估集；
  3. 比较 Recall-延迟-成本 Pareto 曲线；
  4. shadow 新通路，观察候选差异和资源消耗；
  5. 小流量 canary，检查下游排序、答案与超时；
  6. 保留旧参数/旧索引的即时回滚能力；
  7. 将新增失败样本回灌评估集。

不要只报告“Recall@20 +3%”，还要报告每查询候选成本、p99、受益切片、退化切片和统计置信度。

14. 高级工程师面试题

TIP

- Recall@K 和 Hit@K 有什么区别？ Recall@K 关心找到全部相关项中的多少；Hit@K 只关心是否至少命中一个。单证据问答可能用 Hit@K，多证据或合规检索更需要 Recall@K 和完整证据覆盖。

TIP

- 为什么 Recall@100 提高，RAG 反而变差？ 正确证据可能虽进入候选但排名靠后；更大候选导致 reranker 超时或 Context 噪声；评估标签与可回答性不一致。需要追踪 evidence 在检索、排序、装配和生成每层的生存率。

TIP

- 没有完整相关集合，如何评估 Recall？ 用多系统 pooling + 人工标注扩大 qrels，对差异结果主动采样；同时报告 Hit@K、任务成功和持续人工审计，并明确指标是对“已知相关集合”的估计，不冒充绝对 Recall。

TIP

- 如何选择 K？ 在代表性切片上绘制 Recall、下游 nDCG/答案质量、p99 与成本曲线；选择边际 Recall 收益开始变小且 SLO 可满足的点。不同意图可用不同 K。

TIP

- 召回下降如何快速定位？ 先区分数据缺失、过滤、检索模型与 ANN 近似损失；检查 source→parse→chunk→embed→index 每层计数，再比较 exact vector 与 ANN、无过滤与有过滤、旧索引与新索引的差异。

15. 上线检查清单

  • 指标明确区分 Recall、Hit Rate 和 ANN Recall
  • qrels 来源、完整性与版本可追踪
  • 关键业务采用分层指标与最低门槛
  • 各阶段 K 独立配置和观测
  • Recall 改动同时评估 p99、成本和下游质量
  • 多证据问题使用 evidence-set coverage
  • 过滤、去重和新鲜度进入回归测试
  • shadow、canary、回滚参数已经准备

17. 与 Memory、Retrieval、Ranking、RAG 的对比

概念核心产物主要问题代表指标
Memory - Agent 如何记住、更新与遗忘可复用的长期状态什么值得记、如何更新与遗忘写入准确率、检索命中、陈旧率
Retrieval - 从大规模信息中找到候选候选集合用什么索引和算法找到候选Recall@K、延迟、新鲜度
Recall候选覆盖度或候选阶段目标漏了多少，分母是否可信Recall@K、Hit@K、Coverage
Ranking - 从候选集合到最优顺序有序候选正确结果是否排在前面nDCG、MRR、MAP
RAG - 从检索到可信生成的完整系统基于外部证据的回答检索证据能否被正确装配和使用Faithfulness、Citation、Answer Quality

最关键的边界是：Retrieval 是过程，Recall 是这一过程的重要目标与度量；Ranking 优化顺序；RAG 消费结果；Memory 决定某类长期状态是否进入可检索集合。
