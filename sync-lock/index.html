同步和锁：Go 1.26.5 源码分析

Go 通过 goroutine 和 channel 提供了高层并发抽象，但只要多个 goroutine 共享可变内存，就仍然需要同步原语来建立互斥与可见性边界。本文不只介绍 API，而是沿着源码路径阅读 Go 1.26.5 中 sync 包的实现。

版本与同步原语相关的重要变化
Go 1.18Mutex.TryLock、RWMutex.TryLock、RWMutex.TryRLock
Go 1.19sync/atomic 加入 Bool、Int32、Int64、Pointer[T] 等类型化原子值
Go 1.21OnceFunc、OnceValue、OnceValues
Go 1.23sync.Map.Clear
Go 1.24sync.Map 改用 16 路并发 Hash-Trie；旧版 read/dirty/misses 模型不再是当前实现
Go 1.25WaitGroup.Go；go vet 新增 WaitGroup 误用检查
Go 1.26本文基线；sync.Mutex 公开层已是对 internal/sync.Mutex 的轻量包装

**快速理解

所有 sync 原语表面上是不同 API，底层共享一套机制：原子指令（CAS）走快路径，竞争失败就靠 runtime 信号量把 goroutine park 掉，被唤醒后重新竞争。理解这一条，剩下的都是数据结构设计问题。

可以把它们按用途分四类：

  1. 互斥：Mutex（互斥锁）、RWMutex（读写锁）。前者是地基，其他所有阻塞原语几乎都在内部用它。
  2. 协同等待：WaitGroup（等 N 个任务完成）、Once（一次性初始化）、Cond（条件变化广播）。它们不在锁竞争路径上，解决的是”什么时候可以继续”。
  3. 并发容器与复用：sync.Map（1.24 起换成 16 路 Hash-Trie）、sync.Pool（per-P 临时对象缓存，GC 会清）。
  4. 原子操作：sync/atomic 的 typed atomic，单变量无锁；但原子性不等于业务不变式，多字段一致性仍然要锁。

记忆 Mutex 时抓住三件事：快路径一条 CAS；慢路径短暂自旋后走 runtime 信号量休眠；等待超过 1ms 进入饥饿模式直接 handoff。其他原语大多在这三件事上叠加自己的状态编码。

阅读顺序建议：内存模型 → Mutex（重点） → RWMutex → WaitGroup/Once/Cond → Map/Pool → atomic → 选型实践。源码地图见文末参考资料。

一、基础：内存模型与原语地图

同步的根基：happens-before

锁不只用于”同一时刻只允许一个 goroutine 进入”，它还要建立 happens-before（Go 文档中称 synchronizes before）关系，保证一个 goroutine 在临界区内的写入对后续获锁者可见。

happens-before 不是时间上的先后，是内存可见性的承诺。 编译器和 CPU 会重排内存操作，多核各自有缓存。语句 A 在源码里写在 B 前面，不代表 B 执行时一定能看到 A 写入的值。happens-before 是语言规范定义的偏序关系：如果 A happens-before B，A 及 A 之前的所有写入对 B 都可见，且 B 看到的内存顺序与程序顺序一致。

没有同步时的反例：

var done bool
var msg string

// goroutine A
go func() {
    msg = "hello"   // (1)
    done = true     // (2)
}()

// goroutine B
for !done {}        // (3)
println(msg)        // (4) 可能打印空字符串，甚至 B 永远看不到 done=true

源码顺序 (1)→(2)，但没有同步边：编译器/CPU 可能把 (2) 重排到 (1) 前面；(1) 的写可能还停在 A 的 store buffer 没刷到共享缓存；B 的 (3) 可能一直读自己缓存里的旧值。所以 (4) 即使看到 done=true，也不保证看到 msg="hello"。这就是数据竞争，go test -race 会直接报。

Go 内存模型定义的常用 happens-before 规则（也即各原语提供的同步保证）：

操作建立的边
Mutex.Unlockhappens-before 后续任何 Lock 返回（第 n 次 Unlock synchronizes before 第 m 次 Lock，n < m）；TryLock 成功等价于 Lock，失败不建立任何边
ch <- xhappens-before 对应的 <-ch 完成
close(ch)happens-before 收到零值的接收
WaitGroup.Done / WaitGroup.Go 中 f 返回happens-before 被解除阻塞的 Wait 返回
Once.Do(f) 里 f 返回happens-before 任何 Do 返回
Cond.Signal/Broadcasthappens-before 被唤醒的 Wait 返回
sync.Map 写happens-before 观察到该写入的读
sync.Pool.Put(x)happens-before 返回同一个 x 的 Get
atomic.Store对观察到该值的 atomic.Load 可见（Go 原子操作顺序一致）
go f() 语句happens-before f 开始执行（反向不成立：f 退出不 happens-before 任何事件，要等它完成必须用 WaitGroup/channel）

修上面的例子，用锁建立同步边：

var mu sync.Mutex
go func() {
    mu.Lock()
    msg = "hello"
    done = true
    mu.Unlock()       // (1)(2) happens-before 下次 Lock 返回
}()
mu.Lock()
for !done {
    mu.Unlock()
    time.Sleep(time.Millisecond) // 实际用 sync.Cond 或 channel
    mu.Lock()
}
mu.Unlock()
println(msg)        // 一定看到 "hello"

三个易混点：

  1. happens-before 是偏序，不是全局时钟。没有同步关系的两个事件之间顺序未定义，不要假设。
  2. “看见一个写”不等于”看见所有写”。B 看到 A 的某个写，不保证看到 A 其他没有 happens-before 关系的写——必须边覆盖到。
  3. atomic 单操作可见 ≠ 多字段一致。一个 atomic.Bool 做 ready flag，另一个普通字段写数据，ready 被 Load 看到并不自动让数据写可见；要么数据写也走原子发布（比如 atomic.Pointer[T] 发布整个结构体），要么用 Mutex 保护。

所以锁干两件事：互斥（同一时刻只有一个 goroutine 进临界区）加可见性（Unlock 与下一次 Lock 之间建立 happens-before，把前一个持有者的写发布给下一个持有者）。第二点常被忽略，但它才是不能用 if flag {} 瞎等的根本原因。

WARNING

不要拷贝已使用的同步原语 Mutex、RWMutex、WaitGroup、Once、Cond、Map、Pool 以及 typed atomic 都不应在首次使用后被拷贝。优先使用指针接收者，并运行 go vet 的 copylocks 检查。

二、互斥：Mutex 与 RWMutex

IMPORTANT

这一章是整个 sync 包的地基 RWMutex、WaitGroup、Once、Cond、sync.Map 的内部都依赖 Mutex 或它底层的 runtime 信号量。把 Mutex 的状态位、快慢路径、正常/饥饿模式看明白，后面所有原语只是在它上面叠加各自的状态编码。

sync.Mutex：互斥锁

公开结构已经变成包装层

Go 1.26.5 的 sync.Mutex 不再直接声明 state 和 sema：

type Mutex struct {
	_  noCopy
	mu isync.Mutex
}

公开的 Lock、TryLock 和 Unlock 都委托给 internal/sync.Mutex。这样 Go 内部包即使不能依赖公开 sync 包，也能复用同一套互斥锁实现。

真实数据结构

真正实现位于 src/internal/sync/mutex.go#L20-L55：

type Mutex struct {
	state int32
	sema  uint32
}

state 将锁标志、唤醒标志、饥饿标志和等待者数量压缩在一个 32 位整数中：

字段/状态含义
mutexLocked逻辑上已加锁
mutexWoken已有一个等待者被唤醒，解锁者不要重复唤醒
mutexStarving饥饿模式，所有权直接交给队首等待者
state >> mutexWaiterShift已进入等待队列的 goroutine 数
semaruntime 休眠/唤醒原语使用的 32 位信号量地址

Lock：快路径与慢路径

internal/sync.Mutex.Lock 先尝试一次 CAS：只有 state == 0 时才能在快路径直接取得锁。

if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
	return
}
m.lockSlow()

慢路径里会短暂自旋。runtime_canSpin 非常保守，需要同时满足：自旋次数小于 active_spin；启动时 CPU 数大于 1，GOMAXPROCS > 1；除当前 P 外还有正在运行的 P；当前 P 的本地运行队列为空。实际自旋由 runtime_doSpin 调用 procyield(active_spin_cnt)（PAUSE 指令空转）。目标是在临界区极短时避免 goroutine 停放/唤醒的成本，而不是无上限忙等。

注意慢路径不等于自旋。慢路径分两步：先按上面的条件尝试短暂自旋，自旋条件不满足或自旋后仍拿不到锁，就把自己 park（休眠）挂到等待队列，Unlock 时再被唤醒。所以 GOMAXPROCS=1 时慢路径照样工作——此时 canSpin 直接返回 false（没有第二个 P 能并行跑持锁者，空转只会卡死唯一的 P），锁竞争会跳过自旋、直接 park：当前 G 让出 P，持锁 G 得以继续运行并在 Unlock 时唤醒等待者。自旋只是多核场景下省一次调度开销的优化，park/唤醒才是让单核也不致死锁的保底机制。

正常模式与饥饿模式

源码在 mutex.go#L31-L55 定义了两种模式：

  • 正常模式偏向吞吐。被唤醒者并不直接拥有锁，需要与已在 CPU 上运行的新 goroutine 竞争。
  • 饥饿模式偏向尾延迟。等待超过 1ms 后，Unlock 使用 handoff 直接把信号量交给队首。
  • 慢路径完整循环位于 lockSlow#L95-L182。

一个常见疑问：正常模式下，Unlock 是先原子清 mutexLocked、再 semrelease 唤醒 waiter，两步不是原子的；那会不会有新协程恰好 CAS 抢走锁，导致 park 的协程永远拿不到？

会发生”白醒一次”，但不会永远饥饿。窗口确实存在——Unlock 清位后、唤醒 waiter 前，新协程 CAS 成功抢走锁；被唤醒的 waiter 发现锁又被占，会重新进入慢路径继续竞争，而不是永久阻塞。但如果新协程源源不断、每次都恰好插队，某个等待很久的 waiter 就可能反复抢空。Go 的兜底正是饥饿模式：当某个 waiter 从 park 到被唤醒累计等待超过 starvationThresholdNs（1ms），它在慢路径里置上 mutexStarving 位，锁切到饥饿模式——此时新协程的快路径 CAS 直接失败、不自旋、排到队尾，Unlock 直接把锁 handoff 给队首 waiter，不再”解锁后大家抢”。等队列为空或交接完成再切回正常模式。所以正常模式追求吞吐（允许新协程竞走、减少停放开销），饥饿模式追求尾延迟（强制把锁交给等最久的人），两者配合既不无限饥饿也不牺牲常见场景性能。

饥饿模式何时切回正常模式：每次 handoff 时检查，满足任一条件就清掉 mutexStarving 位——①交接后等待队列为空（没人排队了，没有饥饿问题）；②被交接的这个 waiter 本轮等待不足 1ms（说明竞争没那么激烈，不必继续强制交接）。饥饿模式是”一次性救活等太久的人”，不是永久牺牲吞吐：救活之后若没必要继续饿着，下一次 Unlock 就恢复正常模式；若还有人等很久，则保持饥饿继续 handoff 给下一个队首。它由被唤醒、拿到锁的 starving waiter 在 lockSlow/unlockSlow 路径里根据自身等待时长和剩余 waiter 数决定是否清除该位。

Unlock：先清位，再决定是否唤醒

Unlock 先用原子减法清除 mutexLocked。若新状态不为 0，进入 unlockSlow：

  • 解锁未加锁的 Mutex 会触发 fatal("sync: unlock of unlocked mutex")；
  • 正常模式仅在”有 waiter，且没有其他 goroutine 已被唤醒/抢到锁”时唤醒一个等待者；
  • 饥饿模式调用 runtime_Semrelease(..., handoff=true, ...)，直接交接所有权和当前 P 的时间片。

WARNING

Mutex 没有 goroutine 所有权 Go 允许 goroutine A Lock，由 goroutine B Unlock。但这不意味着这种设计容易维护；如果所有权转移没有明确的协议，优先用 channel 表达。

runtime 信号量：不是业务计数信号量

Mutex.sema 使用 runtime/sema.go 的休眠/唤醒机制。它的目标类似 futex：保证每次 sleep 都能与一次 wakeup 配对，即使 wakeup 因竞争而先发生也不丢失。

semaRoot 是两级结构：外层 treap 按信号量地址组织，同一地址的等待者在内层链表中排队。semacquire1 负责停放，semrelease1 负责唤醒与饥饿模式的直接 handoff。

sync.RWMutex：读写锁

RWMutex 允许多个读者并发，但写者与任何读/写者互斥。它不是”更快的 Mutex”；当临界区很短、读写比不高或竞争很低时，普通 Mutex 可能更快。

数据结构

RWMutex 包含一个用来串行化写者的 Mutex、两个 runtime 信号量和两个原子计数器：

type RWMutex struct {
	w           Mutex
	writerSem   uint32
	readerSem   uint32
	readerCount atomic.Int32
	readerWait  atomic.Int32
}

const rwmutexMaxReaders = 1 << 30

读锁路径

RLock 只需将 readerCount 加 1。如果结果为负，说明有 pending writer，当前读者在 readerSem 上休眠。

要注意 RLock 不直接判断 writerSem：两个信号量是分工的——writerSem 给写者睡，readerSem 给读者睡，RLock 阻塞时用的是后者。它判断”有没有写者”靠的是 readerCount.Add(1) 的返回值符号：写者到来时会把 readerCount 减去 rwmutexMaxReaders（1<<30）让它变负，相当于挂出”写者等待中”的牌子；RLock 看到负数就知道有写者 pending，于是去 readerSem 排队。这样写者一旦宣告到来，新读者就被挡在外面排队，不会因为读者源源不断而让写者饿死。

RUnlock 将 readerCount 减 1。负数表示写者正在等待；它把 readerWait 减 1，当减到 0（写者要等的旧读者都走光了）就 Semrelease(&writerSem) 唤醒写者——注意这里 RUnlock 释放的是 writerSem，因为它要通知的是写者。写者 Unlock 时则会把 readerCount 加回 rwmutexMaxReaders 并 Semrelease(&readerSem) 批量唤醒排队的读者。读者和写者各睡各的信号量、互相唤醒对方，构成写者优先的协作。

写锁路径与写者优先

Lock 分两步：

  1. rw.w.Lock() 先与其他写者串行；
  2. readerCount -= rwmutexMaxReaders 宣布”有写者等待”，让后续读者看到负数并在 readerSem 上休眠；
  3. 把原有读者数记入 readerWait，若不为 0，写者等待 writerSem。

Unlock 恢复 readerCount，唤醒被写者拦住的新读者，最后释放 w 让下一个写者竞争。

[!danger] RWMutex 不支持可重入，且比 Mutex 更容易卡死 Go 的锁不记录持有者，所以”同一个 goroutine 又来加锁”不会被特殊处理，任何重入都要避免：

  • Lock 再 Lock：死锁。
  • 持有 RLock 时调 Lock：写者要等所有读者退出，包括当前这个，自己等自己。
  • 持有 Lock 时调 RLock：写锁没释放，读锁拿不到。
  • RLock 再 RLock：表面不阻塞，但因为写者优先——一旦有写者 pending，后续 RLock 看到 readerCount 为负就会去 readerSem 休眠，而当前 goroutine 还持有外层 RLock 无法返回去释放，结果自己把自己卡死。

因此没有”读升级为写”或”写降级为读”的原子协议；需要升级就先 RUnlock 再 Lock（中间状态要自己处理）。Go 刻意不做可重入锁：可重入会模糊临界区边界、让锁随调用链扩散，难以推理不变量，常是设计该重构的信号。

TryRLock 和 TryLock 只适合少数有明确退路的算法；失败后不得假设自己观察到了任何最新状态。

三、协同等待：WaitGroup / Once / Cond

这三个原语不直接保护临界区，而是解决”什么时候可以继续”。它们内部都依赖上面讲过的 Mutex 或 runtime 信号量。

sync.WaitGroup：任务计数与等待者

64 位状态压缩

WaitGroup 只有一个 atomic.Uint64 状态和一个 runtime 信号量：

Add(delta) 通过 state.Add(uint64(delta) << 32) 只改变高 32 位；Wait 通过低位 CAS 增加 waiter 数。bit 31 是 Go 1.25 testing/synctest 使用的气泡归属标志。

Add / Done / Wait

Add 执行以下校验：counter 变成负数 panic；counter 从 0 变正与已开始的 Wait 并发 panic；counter 归 0 且存在 waiter 时清空 state，对每个 waiter 调用 runtime_Semrelease。Done 仅是 Add(-1)。

Wait 反复读取 state：

Wait 里的 for 不是自旋。它是一个 CAS 重试循环：Load 看到 counter 未归零，就 CAS 把 waiter 数 +1，成功后调用 runtime_Semacquire 休眠（线程挂起、不占 CPU）；只有在 Load 与 CAS 之间别的 goroutine 改了 state 导致 CAS 失败时，才循环重读一次——这是极短的乐观重试，不是 procyield 那种 PAUSE 空转。counter 已归零时直接返回，不睡。

多个 Wait 都通过 Semacquire 睡在 WaitGroup 同一个信号量地址上，形成一个等待队列。最后一个 Done()（即 Add(-1) 让 counter 归零）发现 waiter 数 > 0 时，会先原子清零 state，再用一次 runtime_Semrelease(addr, handoff=true) 广播唤醒整个队列，而非逐个唤醒——因为”所有人都等的事完成了”，语义上就该全部放行。这与 Mutex 的 Unlock 只唤醒一个等待者不同（锁只能给一个人，避免惊群）。唤醒前清零 state 也保证：之后新来的 Wait 看到 counter=0 直接返回，不会再睡；被唤醒的 Wait 从 Semacquire 返回时 counter 已是 0，直接 return，不会重复等待。

Go 1.25 新增 WaitGroup.Go

WaitGroup.Go 把最常见的 Add(1) + go + Done() 组合成一个 API：

var wg sync.WaitGroup
for _, task := range tasks {
	task := task
	wg.Go(func() {
		process(task)
	})
}
wg.Wait()

[!danger] WaitGroup.Go 的 f 不能 panic Go 1.26.5 的实现会 recover 后立即重新 panic，且故意不调用 Done，防止主 goroutine 的 Wait 抢先返回甚至退出进程。如果任务可能 panic，应在 f 内明确 recover 并转换为错误协议。

常见误用是把 Add(1) 写在新 goroutine 内部，Wait 可能先看到 counter == 0 直接返回。修复方式是把 Add(1) 移到启动 goroutine 之前，或直接用 wg.Go(work)。WaitGroup 可复用，但新一轮 Add/Go 必须在上一轮所有 Wait 返回后开始。

sync.Once：完成之后才发布

Once 由一个热路径优先的 atomic.Bool 和一个 Mutex 组成。done 放在结构体第一个字段，可让某些架构生成更紧凑的指令。

Do 不能只用 CompareAndSwap(false, true)，因为输家会在赢家的 f 完成前返回，破坏”所有 Do 返回时 f 都已完成”的保证。所以慢路径需要 Mutex，而 done.Store(true) 必须在 f 返回之后发生。

注意 Do 里有两次 o.done.Load()，但它们不是同一种检查：

func (o *Once) Do(f func()) {
    if o.done.Load() == 0 {   // ① 快路径
        o.doSlow(f)
    }
}
func (o *Once) doSlow(f func()) {
    o.mu.Lock()
    defer o.mu.Unlock()
    if o.done.Load() == 0 {   // ② 锁内确认
        defer o.done.Store(1)
        f()
    }
}
  • ① 是内联优化：Do 只留一个原子读，函数体极小，编译器能把它内联到调用点；已经执行过的 Once 走这里零函数调用开销。加锁、defer、调用 f 这些”重活”全部 outline 到 doSlow，只有 done==0 才进入。注释 “Outlined slow-path to allow inlining of the fast-path” 说的就是这个。
  • ② 是正确性保证：多个 goroutine 可能同时通过 ① 涌入 doSlow，第一个抢到锁的执行 f 并置 done=1，其余拿到锁后靠②发现已完成，直接跳过。没有②，f 会被执行多次。

去掉①功能仍正确，只是 Once 每次调用都要走函数调用/加锁判断、无法内联；去掉②则破坏”只执行一次”。

  • f panic 时，Once.Do 仍视为已执行，以后的 Do 不会再调用 f；
  • f 中递归调用同一个 Once.Do 会死锁；
  • Go 1.21 提供 OnceFunc、OnceValue 和 OnceValues，可缓存返回值，并让 panic 值在每次调用时都重现。

sync.Cond：条件变量

Cond 用于”条件目前不成立，暂时休眠；状态变化后再重新检查”。对于单次通知，channel 通常更简单；Broadcast 类似关闭 channel，Signal 类似发送一个值。

Cond 持有用户提供的 Locker、runtime notifyList 和拷贝检测器。

c.L.Lock()
for !condition() {
	c.Wait()
}
useCondition()
c.L.Unlock()

Cond.Wait 的次序是协议的核心：

Go 的 Wait 不会无缘无故返回，但被唤醒者重新取得 L 之前，条件可能已被其他 goroutine 消耗或改变，所以仍然必须用 for 而不是 if。

notifyList 使用两个可回绕的 32 位 ticket：wait 是下一个 waiter 领取的号码，notify 是下一个需要通知的号码，head/tail 是已经停放的 sudog 链表。notifyListWait 先检查 ticket 是否已被通知，从而处理”Signal 发生在 waiter 真正 park 之前”的竞争。NotifyAll 一次摘下全部链表再在锁外唤醒；NotifyOne 查找对应 ticket 并唤醒一个 waiter。

NOTE

Signal 不提供调度优先级 Signal 选中某个 waiter 不等于该 waiter 会立即取得 L。已经在 CPU 上运行并竞争 L 的 goroutine 可能先进入临界区。

四、并发容器与对象复用

sync.Map：Go 1.24+ 的并发 Hash-Trie

WARNING

旧的 read/dirty/misses 分析已过时 Go 1.24 替换了 sync.Map 实现。Go 1.26.5 的公开 sync.Map 只包装 internal/sync.HashTrieMap[any, any]。网上大量基于 read/dirty/misses 字段的源码分析对应的是旧实现，看的时候注意版本。

HashTrieMap 保存根节点的原子指针、key 哈希函数、value 比较函数和随机 seed。每个间接节点有 16 个原子子指针，每层消耗哈希值的 4 bit：

16 路分支常量与节点布局见 hashtriemap.go#L530-L569。

读路径完全无锁：Load 从 root 开始按每 4 bit 读取原子子指针，全程不获取 Mutex。

LoadOrStore 先无锁定位候选 slot，然后只锁定父间接节点，在锁下二次确认 slot 未变化，最后原子发布新 entry/子树。不同哈希分支的写入因此可并行。

LoadAndDelete 删除 entry 后会向上清理空节点，通过 dead 位与父子节点锁保证与并发写者协调。Clear 则直接用一个新空根替换旧根。

没有传统扩容，靠路径复制 + CAS 保证安全：这是和内置 map 最不一样的地方。内置 map 扩容时要 bucket 翻倍、增量迁移数据，期间锁持有时间长；Hash-Trie 没有一次性 rehash，树随写入增量增长——每插入一个新 key，只在需要处分叉出新的 branch 节点，树深按 hash 的 4 bit 递增。写入用路径复制（path copying）：从 root 到目标叶子沿途复制节点，在副本上改，最后用 CAS 原子替换 root 指针。已经发布的旧节点永不原地修改，正在读的 goroutine 拿着旧 root 看到的是一棵完整一致的快照——这就是读完全无锁的原因。多个写者各自复制路径生成新 root，靠 CAS 抢着提交，输的人拿最新 root 重试（乐观并发），不是互斥锁。删除同理，复制路径后旧节点失去引用由 GC 回收。

使用边界：

  • sync.Map 适合”写一次、读很多”或”不同 goroutine 主要操作不相交的 key 集合”；
  • 大多数业务代码仍应使用 map[K]V + Mutex/RWMutex，以保留类型安全并与其他字段共同维护不变式；
  • Range 不是一致性快照，并发写入时可以观察到任意时点的值；
  • Load 后再 Store 不是一个原子复合操作，应使用 LoadOrStore、Swap、CompareAndSwap 等方法表达协议。

sync.Pool：每 P 临时对象缓存

Pool 用于降低多 goroutine 共享的短命临时对象分配压力，不是可靠缓存、连接池或有容量保证的对象池。

适用场景是分配频繁、用完即弃、重置便宜、类型固定的临时对象，最常见的是：

  • bytes.Buffer / []byte 拼接缓冲：fmt、net/http、encoding/json、日志库都用它复用请求级 buffer；
  • 高频编解码的临时 struct（JSON / 协议解析）；
  • 高并发路径上反复 new 的短命对象。

判断标准：对象”每次请求都 new、用完就丢、Reset 很便宜”时收益最大。它靠 per-P 本地槽位无锁快取（见下方 private/shared），高并发下比全局池开销低得多。

使用要点：

  • GC 会清空池：poolCleanup 在每次 GC 时把 local 挪到 victim、再清空旧 victim，所以对象随时可能被回收。只适合临时对象，不能放数据库连接、文件句柄等需要长期持有的资源（那是 database/sql 连接池做的事）。
  • Get 后必须 Reset：池里的对象带着上次的数据，取出来先清零/复位再用。
  • 不能限制容量、不保证能取回自己 Put 的对象：它不是有界队列，多 goroutine 共享，对象可能被别人取走。
  • 不要存大对象长期复用：GC 不可靠，省不了内存；大对象长期存活反而该调整设计。

一句话：需要”长期持有/有上限/可靠存活”用专用资源池；需要”高频短命对象降 GC”用 sync.Pool。

Pool 为每个 P 维护一个 poolLocal：

  • private：当前 P 独占的单个快速槽位；
  • shared poolChain：当前 P 在 head 端 push/pop，其他 P 可从 tail 端偷取；
  • pad：将 poolLocal 分隔到 128 字节边界，避免伪共享。

Put 先放 private，否则 push 到本地 shared head。Get 的顺序是：

  1. 本地 private；
  2. 本地 shared head（时间局部性）；
  3. getSlow 从其他 P 的 shared tail 偷取；
  4. 上一轮 GC 的 victim cache；
  5. 若仍为空，调用 New。

poolCleanup 在 GC 开始的 STW 阶段运行：

因此 Pool.Get 随时可以返回 nil/新对象，即使程序之前执行过 Put。不得把必须存活的状态、只能归还一次的资源或带有业务所有权的对象存入 Pool。

五、原子操作：sync/atomic

Go 1.26.5 推荐优先使用 typed atomic，如 atomic.Bool、atomic.Int64、atomic.Uint64、atomic.Pointer[T]。它们的定义与对齐保证见 sync/atomic/type.go。

type Metrics struct {
	requests atomic.Uint64
	ready    atomic.Bool
}

func (m *Metrics) Inc()              { m.requests.Add(1) }
func (m *Metrics) Requests() uint64  { return m.requests.Load() }

sync/atomic 文档 定义 Go 的原子操作为顺序一致，但原子性只覆盖单次操作：

// 逻辑竞争：Load 和 Store 各自原子，组合起来却不原子
if x.Load() == 0 {
	x.Store(1)
}

如果协议要求”仅当仍为 0 时改成 1”，应使用 CompareAndSwap(0, 1)。如果需要同时维护多个字段的关系，通常应使用 Mutex 保护整个不变式，而不是把每个字段都换成 atomic。

TIP

何时使用 atomic 独立计数器、只读配置指针的原子发布、状态位以及经过严格证明的 lock-free 算法是常见场景。业务逻辑若需要轮询多个原子变量才能理解，往往已经应该换成锁或 channel。

六、选型与实践

常见陷阱：

  • 持锁执行网络 I/O、磁盘 I/O、无界回调或向可能阻塞的 channel 发送，会把锁竞争放大成系统尾延迟；
  • defer mu.Unlock() 通常更安全，但临界区边界仍应清晰；不要为了便于 defer 而扩大持锁范围；
  • 不要在一个导出方法中返回受锁保护的 map/slice 底层引用；返回副本或在锁内完成操作；
  • 有多把锁时定义并遵守全局锁顺序；Go 的 Mutex 不会自动检测死锁环；
  • TryLock 往往意味着协议没有定义清楚，不应用 for !TryLock() {} 实现忙等；
  • 锁保护的是不变式，不是某一行赋值。同一组状态的所有读写必须使用同一同步协议。

测试与观测：

# 数据竞争
go test -race ./...

# 拷贝锁、WaitGroup.Add 位置等静态检查
go vet ./...

# 锁竞争与阻塞剖析
go test -run '^$' -bench . -mutexprofile mutex.out -blockprofile block.out ./...
go tool pprof mutex.out
go tool pprof block.out

TIP

看 profile 时先优化临界区，再换锁 缩小锁粒度、把慢 I/O 移出临界区、消除重复计算和减少共享状态，通常比盲目把 Mutex 换成 RWMutex/atomic 更有效。

附录

总结

  1. Mutex 是 CAS 快路径、有限自旋、runtime 信号量停放和 1ms 饥饿交接的组合；
  2. RWMutex 用负的 readerCount 阻止新读者，确保 pending writer 最终获锁；
  3. WaitGroup 在一个 64 位状态中压缩 task counter、synctest 标志和 waiter count，Go 1.25+ 优先使用 WaitGroup.Go；
  4. Once 的关键是”f 完成后才发布 done”，不是简单的 CAS 抢执行权；
  5. Cond 使用 ticket + sudog 通知队列，而用户仍必须在锁下循环检查条件；
  6. Go 1.24+ sync.Map 是 16 路 Hash-Trie，原子读指针配合局部节点锁；
  7. Pool 是 GC 可清理的 per-P 临时对象复用机制，不提供缓存可靠性；
  8. atomic 保证单次操作与内存顺序，不自动保护多字段业务不变式。
