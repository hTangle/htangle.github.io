同步和锁：Go 1.26.5 源码分析

Go 通过 goroutine 和 channel 提供了高层并发抽象，但只要多个 goroutine 共享可变内存，就仍然需要同步原语来建立互斥与可见性边界。本文不只介绍 API，而是沿着以下路径阅读 Go 1.26.5 源码：

flowchart LR
    A["sync 公开 API"] --> B["internal/sync 核心实现"]
    B --> C["runtime 信号量与调度器"]
    C --> D["sudog 等待队列"]
    D --> E["gopark 休眠 / goready 唤醒"]
    A --> F["sync/atomic 原子操作"]
    F --> B

同步的根基：Go 内存模型

锁不只用于“同一时刻只允许一个 goroutine 进入”，它还要建立 happens-before（Go 文档中称 synchronizes before）关系，保证一个 goroutine 在临界区内的写入对后续获锁者可见。

sequenceDiagram
    participant G1 as Goroutine 1
    participant M as Mutex
    participant G2 as Goroutine 2
    G1->>M: Lock
    G1->>G1: 写共享数据 x = 1
    G1->>M: Unlock
    Note over M: Unlock synchronizes before 后续 Lock
    G2->>M: Lock
    G2->>G2: 必须观察到 x = 1
原语同步保证
Mutex第 n 次 Unlock synchronizes before 后续第 m 次 Lock（n < m）
TryLock成功等价于 Lock；失败不建立任何同步关系
Oncef 返回 synchronizes before 任意 Do(f) 返回
WaitGroupDone/Go 中 f 返回 synchronizes before 被它解除阻塞的 Wait 返回
CondSignal/Broadcast synchronizes before 被唤醒的 Wait
Map写操作 synchronizes before 观察到该写入的读操作
PoolPut(x) synchronizes before 返回同一个 x 的 Get
atomic若 B 观察到 A，则 A synchronizes before B；Go 原子操作表现为顺序一致

⚠️ 不要拷贝已使用的同步原语

Mutex、RWMutex、WaitGroup、Once、Cond、Map、Pool 以及 typed atomic 都不应在首次使用后被拷贝。优先使用指针接收者，并运行 go vet 的 copylocks 检查。

sync.Mutex：互斥锁

公开结构已经变成包装层

Go 1.26.5 的 sync.Mutex 不再直接声明 state 和 sema：

type Mutex struct {
	_  noCopy
	mu isync.Mutex
}

公开的 Lock、TryLock 和 Unlock 都委托给 internal/sync.Mutex。这样 Go 内部包即使不能依赖公开 sync 包，也能复用同一套互斥锁实现。

真实数据结构

真正实现位于 src/internal/sync/mutex.go#L20-L55：

type Mutex struct {
	state int32
	sema  uint32
}

state 将锁标志、唤醒标志、饥饿标志和等待者数量压缩在一个 32 位整数中：

flowchart LR
    A["bit 31 ... bit 3<br/>等待者数量"] --- B["bit 2<br/>mutexStarving"]
    B --- C["bit 1<br/>mutexWoken"]
    C --- D["bit 0<br/>mutexLocked"]
字段/状态含义
mutexLocked逻辑上已加锁
mutexWoken已有一个等待者被唤醒，解锁者不要重复唤醒
mutexStarving饥饿模式，所有权直接交给队首等待者
state >> mutexWaiterShift已进入等待队列的 goroutine 数
semaruntime 休眠/唤醒原语使用的 32 位信号量地址

Lock：快路径与慢路径

internal/sync.Mutex.Lock 先尝试一次 CAS：只有 state == 0 时才能在快路径直接取得锁。

if atomic.CompareAndSwapInt32(&m.state, 0, mutexLocked) {
	return
}
m.lockSlow()
flowchart TD
    A["Lock"] --> B{"CAS: state 0 -> locked?"}
    B -->|"成功"| C["获得锁，返回"]
    B -->|"失败"| D{"normal 且允许自旋?"}
    D -->|"是"| E["自旋；必要时设 mutexWoken"]
    E --> F["重读 state 并重试"]
    F --> D
    D -->|"否"| G["增加 waiter 数，CAS 更新 state"]
    G --> H{"CAS 后已获锁?"}
    H -->|"是"| C
    H -->|"否"| I["runtime_SemacquireMutex<br/>gopark 休眠"]
    I --> J{"starving 直接交接?"}
    J -->|"是"| C
    J -->|"否"| F

为什么只短暂自旋

runtime_canSpin 非常保守，需要同时满足：

  • 自旋次数小于 active_spin；
  • 启动时 CPU 数大于 1，GOMAXPROCS > 1；
  • 除当前 P 外还有正在运行的 P；
  • 当前 P 的本地运行队列为空。

实际自旋由 runtime_doSpin 调用 procyield(active_spin_cnt)。目标是在临界区极短时避免 goroutine 停放/唤醒的成本，而不是无上限忙等。

正常模式与饥饿模式

源码在 mutex.go#L31-L55 定义了两种模式：

stateDiagram-v2
    [*] --> Normal
    Normal: 正常模式
    Normal: 唤醒者与新到 goroutine 竞争
    Normal: 允许短暂自旋，吞吐更高
    Normal --> Starving: 等待超过 1ms
    Starving: 饥饿模式
    Starving: Unlock 直接 handoff 给队首
    Starving: 新到 goroutine 不自旋、不抢锁
    Starving --> Normal: 当前者等待少于 1ms
    Starving --> Normal: 当前者是最后一个 waiter
  • 正常模式偏向吞吐。被唤醒者并不直接拥有锁，需要与已在 CPU 上运行的新 goroutine 竞争。
  • 饥饿模式偏向尾延迟。等待超过 1ms 后，Unlock 使用 handoff 直接把信号量交给队首。
  • 慢路径的完整循环位于 lockSlow#L95-L182。

Unlock：先清位，再决定是否唤醒

Unlock 先用原子减法清除 mutexLocked。若新状态不为 0，进入 unlockSlow：

  • 解锁未加锁的 Mutex 会触发 fatal("sync: unlock of unlocked mutex")；
  • 正常模式仅在“有 waiter，且没有其他 goroutine 已被唤醒/抢到锁”时唤醒一个等待者；
  • 饥饿模式调用 runtime_Semrelease(..., handoff=true, ...)，直接交接所有权和当前 P 的时间片。

⚠️ Mutex 没有 goroutine 所有权

Go 允许 goroutine A Lock，由 goroutine B Unlock。但这不意味着这种设计容易维护；如果所有权转移没有明确的协议，优先用 channel 表达。

runtime 信号量：不是业务计数信号量

Mutex.sema 使用 runtime/sema.go 的休眠/唤醒机制。它的目标类似 futex：保证每次 sleep 都能与一次 wakeup 配对，即使 wakeup 因竞争而先发生也不丢失。

flowchart TD
    A["Semacquire"] --> B{"sema > 0 并 CAS -1 成功?"}
    B -->|"是"| C["直接返回"]
    B -->|"否"| D["获取 sudog"]
    D --> E["按 sema 地址哈希到 251 个 semaRoot"]
    E --> F["再检查一次，避免丢失唤醒"]
    F --> G["按地址放入 treap + 内层 waiter 队列"]
    G --> H["goparkunlock 停放 goroutine"]
    I["Semrelease"] --> J["sema +1"]
    J --> K["从 semaRoot dequeue 一个 sudog"]
    K --> L["goready 唤醒"]
    L --> M{"handoff?"}
    M -->|"是"| N["goyield，让 waiter 立即运行"]

semaRoot 是两级结构：外层 treap 按信号量地址组织，同一地址的等待者在内层链表中排队。semacquire1 负责停放，semrelease1 负责唤醒与饥饿模式的直接 handoff。

sync.RWMutex：读写锁

RWMutex 允许多个读者并发，但写者与任何读/写者互斥。它不是“更快的 Mutex”；当临界区很短、读写比不高或竞争很低时，普通 Mutex 可能更快。

数据结构

RWMutex 包含一个用来串行化写者的 Mutex、两个 runtime 信号量和两个原子计数器：

type RWMutex struct {
	w           Mutex
	writerSem   uint32
	readerSem   uint32
	readerCount atomic.Int32
	readerWait  atomic.Int32
}

const rwmutexMaxReaders = 1 << 30
flowchart LR
    A["w: 写者之间互斥"]
    B["readerCount >= 0<br/>当前/即将读者数"]
    C["readerCount < 0<br/>已有 pending writer"]
    D["readerWait<br/>写者仍需等待退出的读者"]
    E["readerSem<br/>阻塞新读者"]
    F["writerSem<br/>最后一个旧读者唤醒写者"]
    A --> C
    C --> E
    B --> D
    D --> F

读锁路径

RLock 只需将 readerCount 加 1。如果结果为负，说明有 pending writer，当前读者在 readerSem 上休眠。

RUnlock 将 readerCount 减 1。负数表示写者正在等待；最后一个离开的旧读者把 readerWait 减到 0，随即释放 writerSem。

写锁路径与写者优先

Lock 分两步：

  1. rw.w.Lock() 先与其他写者串行；
  2. readerCount -= rwmutexMaxReaders 宣布“有写者等待”，让后续读者看到负数并在 readerSem 上休眠；
  3. 把原有读者数记入 readerWait，若不为 0，写者等待 writerSem。
sequenceDiagram
    participant R1 as 已有 Reader 1
    participant R2 as 已有 Reader 2
    participant W as Writer
    participant RN as 新 Reader
    W->>W: w.Lock()
    W->>W: readerCount -= 1<<30
    RN->>RN: RLock 后 readerCount < 0
    RN-->>RN: 在 readerSem 休眠
    R1->>W: RUnlock / readerWait--
    R2->>W: RUnlock / readerWait == 0
    R2->>W: 释放 writerSem
    W->>W: 进入写临界区
    W->>RN: Unlock 释放 readerSem

Unlock 恢复 readerCount，唤醒被写者拦住的新读者，最后释放 w让下一个写者竞争。

‼️ RWMutex 不支持升级、降级和递归读锁

RLock -> Lock 会死锁；Lock -> RLock 也不是受支持的降级协议。当写者 pending 时，新的 RLock 会阻塞，因此同一 goroutine 递归 RLock 也可能把自己卡住。

TryRLock 和 TryLock 只适合少数有明确退路的算法；失败后不得假设自己观察到了任何最新状态。

sync.WaitGroup：任务计数与等待者

64 位状态压缩

WaitGroup 只有一个 atomic.Uint64 状态和一个 runtime 信号量：

flowchart LR
    A["bit 63 ... 32<br/>counter: 未完成任务数"] --- B["bit 31<br/>synctest bubble flag"]
    B --- C["bit 30 ... 0<br/>waiters: Wait 阻塞者数"]

Add(delta) 通过 state.Add(uint64(delta) << 32) 只改变高 32 位；Wait 通过低位 CAS 增加 waiter 数。bit 31 是 Go 1.25 testing/synctest 使用的气泡归属标志。

Add / Done

Add 执行以下校验：

  • counter 变成负数：panic("sync: negative WaitGroup counter")；
  • counter 从 0 变正与已开始的 Wait 并发：误用 panic；
  • counter 归 0 且存在 waiter：清空 state，对每个 waiter 调用 runtime_Semrelease。

Done 仅是 Add(-1)。

Wait

Wait 反复读取 state：

flowchart TD
    A["Wait"] --> B["读取 counter / waiters"]
    B --> C{"counter == 0?"}
    C -->|"是"| D["直接返回"]
    C -->|"否"| E["CAS: waiters + 1"]
    E -->|"失败"| B
    E -->|"成功"| F["runtime_SemacquireWaitGroup"]
    F --> G["被 counter 归 0 的 Add 唤醒"]
    G --> H{"state 已被新一轮重置?"}
    H -->|"是"| I["panic: reused before previous Wait returned"]
    H -->|"否"| D

Go 1.25 新增 WaitGroup.Go

WaitGroup.Go 把最常见的 Add(1) + go + Done() 组合成一个 API：

var wg sync.WaitGroup
for _, task := range tasks {
	task := task
	wg.Go(func() {
		process(task)
	})
}
wg.Wait()

‼️ WaitGroup.Go 的 f 不能 panic

Go 1.26.5 的实现会 recover 后立即重新 panic，且故意不调用 Done，防止主 goroutine 的 Wait 抢先返回甚至退出进程。如果任务可能 panic，应在 f 内明确 recover 并转换为错误协议。

常见误用

// 错误：Add 在新 goroutine 内，Wait 可能先看到 counter == 0
go func() {
	wg.Add(1)
	defer wg.Done()
	work()
}()
wg.Wait()

修复方式是把 Add(1) 移到启动 goroutine 之前，或直接使用 wg.Go(work)。WaitGroup 可复用，但新一轮 Add/Go 必须在上一轮所有 Wait 返回后开始。

sync.Once：完成之后才发布

Once 由一个热路径优先的 atomic.Bool 和一个 Mutex 组成。done 放在结构体第一个字段，可让某些架构生成更紧凑的指令。

flowchart TD
    A["Once.Do(f)"] --> B{"done.Load() == true?"}
    B -->|"是"| C["直接返回"]
    B -->|"否"| D["m.Lock()"]
    D --> E{"double-check done?"}
    E -->|"是"| F["m.Unlock"]
    F --> C
    E -->|"否"| G["执行 f"]
    G --> H["defer done.Store(true)"]
    H --> F

Do 不能只用 CompareAndSwap(false, true)，因为输家会在赢家的 f 完成前返回，破坏“所有 Do 返回时 f 都已完成”的保证。所以慢路径需要 Mutex，而 done.Store(true) 必须在 f 返回之后发生。

  • f panic 时，Once.Do 仍视为已执行，以后的 Do 不会再调用 f；
  • f 中递归调用同一个 Once.Do 会死锁；
  • Go 1.21 提供 OnceFunc、OnceValue 和 OnceValues，可缓存返回值，并让 panic 值在每次调用时都重现。

sync.Cond：条件变量

Cond 用于“条件目前不成立，暂时休眠；状态变化后再重新检查”。对于单次通知，channel 通常更简单；Broadcast 类似关闭 channel，Signal 类似发送一个值。

结构与 Wait 协议

Cond 持有用户提供的 Locker、runtime notifyList 和拷贝检测器。

c.L.Lock()
for !condition() {
	c.Wait()
}
useCondition()
c.L.Unlock()

Cond.Wait 的次序是协议的核心：

sequenceDiagram
    participant G as Waiter
    participant C as Cond.notifyList
    participant L as Locker
    participant S as Signaler
    G->>C: 领取 ticket
    G->>L: Unlock
    G->>C: notifyListWait(ticket)
    C-->>G: gopark
    S->>C: Signal / Broadcast
    C-->>G: goready
    G->>L: Lock
    G->>G: 重新检查 condition

Go 的 Wait 不会无缘无故返回，但被唤醒者重新取得 L 之前，条件可能已被其他 goroutine 消耗或改变，所以仍然必须用 for 而不是 if。

runtime.notifyList

notifyList 使用两个可回绕的 32 位 ticket：

  • wait：下一个 waiter 领取的号码；
  • notify：下一个需要通知的号码；
  • head/tail：已经停放的 sudog 链表。

notifyListWait 先检查 ticket 是否已被通知，从而处理“Signal 发生在 waiter 真正 park 之前”的竞争。NotifyAll 一次摘下全部链表再在锁外唤醒；NotifyOne 查找对应 ticket 并唤醒一个 waiter。

📝 Signal 不提供调度优先级

Signal 选中某个 waiter 不等于该 waiter 会立即取得 L。已经在 CPU 上运行并竞争 L 的 goroutine 可能先进入临界区。

sync.Map：Go 1.24+ 的并发 Hash-Trie

⚠️ 旧的 read/dirty/misses 分析已过时

Go 1.24 替换了 sync.Map 实现。Go 1.26.5 的公开 sync.Map 只包装 internal/sync.HashTrieMap[any, any]。

结构

HashTrieMap 保存根节点的原子指针、key 哈希函数、value 比较函数和随机 seed。每个间接节点有 16 个原子子指针，每层消耗哈希值的 4 bit：

flowchart TD
    R["root: atomic.Pointer"] --> N0["indirect node<br/>16 children + node mutex"]
    N0 -->|"hash[63:60]"| N1["indirect node"]
    N0 -->|"另一个 4-bit 分支"| E1["entry: key/value"]
    N1 -->|"hash[59:56]"| E2["entry: key/value"]
    N1 -->|"同 hash"| O["overflow atomic list"]

16 路分支常量与节点布局见 hashtriemap.go#L530-L569。

读不加锁，写只锁局部节点

Load 从 root 开始按每 4 bit 读取原子子指针，全程不获取 Mutex。

LoadOrStore 先无锁定位候选 slot，然后只锁定父间接节点，在锁下二次确认 slot 未变化，最后原子发布新 entry/子树。不同哈希分支的写入因此可并行。

flowchart TD
    A["Store / LoadOrStore"] --> B["原子读遍历，找候选 slot"]
    B --> C["锁父 indirect.mu"]
    C --> D{"slot 仍是原状态且节点未 dead?"}
    D -->|"否"| E["解锁，从 root 重试"]
    E --> B
    D -->|"是"| F["创建新 entry / 扩展子树"]
    F --> G["atomic slot.Store 发布"]
    G --> H["解锁"]

LoadAndDelete 删除 entry 后会向上清理空节点，通过 dead 位与父子节点锁保证与并发写者协调。Clear 则直接用一个新空根替换旧根。

使用边界

  • sync.Map 适合“写一次、读很多”或“不同 goroutine 主要操作不相交的 key 集合”；
  • 大多数业务代码仍应使用 map[K]V + Mutex/RWMutex，以保留类型安全并与其他字段共同维护不变式；
  • Range 不是一致性快照，并发写入时可以观察到任意时点的值；
  • Load 后再 Store 不是一个原子复合操作，应使用 LoadOrStore、Swap、CompareAndSwap 等方法表达协议。

sync.Pool：每 P 临时对象缓存

Pool 用于降低多 goroutine 共享的短命临时对象分配压力，不是可靠缓存、连接池或有容量保证的对象池。

per-P 分片

Pool 为每个 P 维护一个 poolLocal：

flowchart TD
    P["sync.Pool"] --> L0["P0 local<br/>private + shared chain"]
    P --> L1["P1 local<br/>private + shared chain"]
    P --> LN["Pn local<br/>private + shared chain"]
    G0["P0 上的 goroutine"] -->|"Put/Get 快路径"| L0
    G0 -->|"本地为空时从 tail 偷取"| L1
    V["上一轮 GC 的 victim cache"] --> G0
  • private：当前 P 独占的单个快速槽位；
  • shared poolChain：当前 P 在 head 端 push/pop，其他 P 可从 tail 端偷取；
  • pad：将 poolLocal 分隔到 128 字节边界，避免伪共享。

Put 先放 private，否则 push 到本地 shared head。Get 的顺序是：

  1. 本地 private；
  2. 本地 shared head（时间局部性）；
  3. getSlow 从其他 P 的 shared tail 偷取；
  4. 上一轮 GC 的 victim cache；
  5. 若仍为空，调用 New。

GC 与 victim cache

poolCleanup 在 GC 开始的 STW 阶段运行：

flowchart LR
    A["GC N 前<br/>primary 有对象"] --> B["GC N<br/>primary -> victim"]
    B --> C["GC N+1 前<br/>Get 仍可从 victim 取"]
    C --> D["GC N+1<br/>丢弃旧 victim"]

因此 Pool.Get 随时可以返回 nil/新对象，即使程序之前执行过 Put。不得把必须存活的状态、只能归还一次的资源或带有业务所有权的对象存入 Pool。

sync/atomic：原子性不等于不变式

Go 1.26.5 推荐优先使用 typed atomic，如 atomic.Bool、atomic.Int64、atomic.Uint64、atomic.Pointer[T]。它们的定义与对齐保证见 sync/atomic/type.go。

type Metrics struct {
	requests atomic.Uint64
	ready    atomic.Bool
}

func (m *Metrics) Inc()       { m.requests.Add(1) }
func (m *Metrics) Requests() uint64 { return m.requests.Load() }

sync/atomic 文档 定义 Go 的原子操作为顺序一致，但原子性只覆盖单次操作：

// 逻辑竞争：Load 和 Store 各自原子，组合起来却不原子
if x.Load() == 0 {
	x.Store(1)
}

如果协议要求“仅当仍为 0 时改成 1”，应使用 CompareAndSwap(0, 1)。如果需要同时维护多个字段的关系，通常应使用 Mutex 保护整个不变式，而不是把每个字段都换成 atomic。

💡 何时使用 atomic

独立计数器、只读配置指针的原子发布、状态位以及经过严格证明的 lock-free 算法是常见场景。业务逻辑若需要轮询多个原子变量才能理解，往往已经应该换成锁或 channel。

常见陷阱

  • 持锁执行网络 I/O、磁盘 I/O、无界回调或向可能阻塞的 channel 发送，会把锁竞争放大成系统尾延迟；
  • defer mu.Unlock() 通常更安全，但临界区边界仍应清晰；不要为了便于 defer 而扩大持锁范围；
  • 不要在一个导出方法中返回受锁保护的 map/slice 底层引用；返回副本或在锁内完成操作；
  • 有多把锁时定义并遵守全局锁顺序；Go 的 Mutex 不会自动检测死锁环；
  • TryLock 往往意味着协议没有定义清楚，不应用 for !TryLock() {} 实现忙等；
  • 锁保护的是不变式，不是某一行赋值。同一组状态的所有读写必须使用同一同步协议。

测试与观测

# 数据竞争
go test -race ./...

# 拷贝锁、WaitGroup.Add 位置等静态检查
go vet ./...

# 锁竞争与阻塞剖析
go test -run '^$' -bench . -mutexprofile mutex.out -blockprofile block.out ./...
go tool pprof mutex.out
go tool pprof block.out

💡 看 profile 时先优化临界区，再换锁

缩小锁粒度、把慢 I/O 移出临界区、消除重复计算和减少共享状态，通常比盲目把 Mutex 换成 RWMutex/atomic 更有效。

总结

  1. Mutex 是 CAS 快路径、有限自旋、runtime 信号量停放和 1ms 饥饿交接的组合；
  2. RWMutex 用负的 readerCount 阻止新读者，确保 pending writer 最终获锁；
  3. WaitGroup 在一个 64 位状态中压缩 task counter、synctest 标志和 waiter count，Go 1.25+ 优先使用 WaitGroup.Go；
  4. Once 的关键是“f 完成后才发布 done”，不是简单的 CAS 抢执行权；
  5. Cond 使用 ticket + sudog 通知队列，而用户仍必须在锁下循环检查条件；
  6. Go 1.24+ sync.Map 是 16 路 Hash-Trie，原子读指针配合局部节点锁；
  7. Pool 是 GC 可清理的 per-P 临时对象复用机制，不提供缓存可靠性；
  8. atomic 保证单次操作与内存顺序，不自动保护多字段业务不变式。
