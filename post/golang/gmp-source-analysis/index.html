Go 调度器解决的核心问题是：如何用较少的操作系统线程运行数量巨大的 goroutine，同时在阻塞、系统调用、网络 I/O、抢占和 GC 之间维持吞吐与延迟。G、M、P 不是三个抽象首字母，而是 runtime 中真实存在、长期复用的数据结构。

flowchart LR G1["G：goroutine"] --> P1["P：执行 Go 代码的许可与本地资源"] P1 --> M1["M：OS thread"] M1 --> CPU["CPU"] P1 --> Q["local runq / runnext"] S["全局调度器"] --> P1 NP["netpoll"] --> P1 TM["timers"] --> P1

[!info] 版本与源码基线 本文以 Go 1.26.5 为基准，源码链接固定到提交 c19862e5f8415b4f24b189d065ed739517c548ba。旧笔记 GMP 仅作历史参考，当前实现以 runtime 源码为准。

当前版本需要关注的变化

版本 调度/runtime 相关变化
Go 1.1 引入以 P 和 work stealing 为核心的新调度器
Go 1.14 基于信号的异步抢占投入使用，纯计算循环也能被抢占
Go 1.21 P 本地队列、netpoll、timer 等框架持续演进，GMP 基本模型保持稳定
Go 1.25 默认 GOMAXPROCS 具备容器 CPU 配额感知，并可由 sysmon 周期性更新
Go 1.26 Green Tea GC 默认启用；新增实验性 goroutineleak profile，可发现一类永久阻塞的 G

[!note] GC 不是调度器，但两者高度耦合 P 持有分配缓存与 GC worker 状态，调度循环会优先运行 GC worker；STW、抢占和栈扫描也都需要调度器配合。因此理解 GMP 时不能完全绕开 GC。

G、M、P 分别是什么

G：goroutine 的运行时描述

g 不等于“函数”。它保存一个 goroutine 从创建到退出所需的运行状态：

flowchart TB G["g"] --> ST["stack：动态用户栈范围"] G --> GU["stackguard0/1：栈增长与抢占检查"] G --> SC["sched gobuf：SP / PC / BP 等上下文"] G --> A["atomicstatus：_Grunnable/_Grunning/... "] G --> M["m：当前承载它的线程"] G --> W["waiting：阻塞原语对应 sudog"] G --> P["preempt / preemptStop / asyncSafePoint"] G --> ID["goid / startpc / waitreason"]

G 对象会复用：goroutine 退出后，其 g 进入空闲池，未来可代表另一个 goroutine。G 的用户栈起始很小，按需增长或收缩；运行时还会扫描它来寻找 GC root。

M：操作系统线程

m 是 machine，即 OS thread 的 runtime 表示：

flowchart TB M["m"] --> G0["g0：系统栈上的 runtime 工作"] M --> GS["gsignal：信号处理栈"] M --> C["curg：当前用户 G"] M --> P["p / nextp / oldp"] M --> L["lockedg / lockedm：LockOSThread"] M --> SP["spinning：正在寻找工作"] M --> B["blocked / locks / preemptoff"]

M 可以没有 P，例如阻塞在系统调用、执行 cgo 或处于空闲线程池。M 的数量不等于 GOMAXPROCS；大量系统调用可以让 runtime 创建更多 M，但只有拿到 P 的 M 才能执行普通 Go 代码。

P：执行权与每 P 资源

p 是 processor。它不是 CPU 核心，也不是线程，而是执行用户 Go 代码所需的许可和一组分片资源：

flowchart TB P["p"] --> ID["id / status / m"] P --> RN["runnext：高局部性的下一个 G"] P --> RQ["runq[256]：本地可运行队列"] P --> MC["mcache：每 P 分配缓存"] P --> TM["timers：每 P timer heap"] P --> GC["gcBgMarkWorker / gcAssistTime"] P --> SG["sudogcache / deferpool 等缓存"]

P 的数量等于当前 GOMAXPROCS。把常用调度、分配和 timer 状态放在 P 上，可以让多数操作使用本地分片，减少全局锁竞争。

三者如何组合

sequenceDiagram participant G as Runnable G participant P as P participant M as M / OS Thread P->>P: 从 runnext/runq 取 G P->>M: M 持有 P M->>G: execute，切到 G 用户栈 G->>G: 执行 Go 代码 G-->>M: 阻塞、抢占、退出或主动让出 M->>P: 回到 schedule 寻找下一个 G

可以把关系简化为：

  • G 提供“要运行什么”。
  • M 提供“在哪里运行”，即 OS 执行上下文。
  • P 提供“运行 Go 代码的权利和本地资源”。
  • 调度器持续匹配三者，而不是把 G 永久绑定给某个 M 或 P。

[!warning] 常见误解 GOMAXPROCS=1 不是只有一个 M，也不是程序没有并发；它只限制同时执行普通 Go 代码的 P 数量为 1。阻塞系统调用、runtime 线程和 cgo 仍可能存在多个 M。

G 的状态机

主要状态定义在 runtime2.go：

stateDiagram-v2 [*] --> _Gidle _Gidle --> _Grunnable: newproc 初始化完成 _Grunnable --> _Grunning: execute _Grunning --> _Gwaiting: gopark / Channel / Mutex / timer / netpoll _Gwaiting --> _Grunnable: ready / goready _Grunning --> _Gsyscall: entersyscall _Gsyscall --> _Grunnable: exitsyscall 未立即拿到 P _Gsyscall --> _Grunning: exitsyscall 重新获得 P _Grunning --> _Gpreempted: 异步安全点暂停 _Gpreempted --> _Grunnable: resume/ready _Grunning --> _Gdead: goexit _Gdead --> _Gidle: 复用前准备

_Gscan 是叠加在基础状态上的 GC 扫描位，不是普通独立生命周期状态。状态迁移必须通过 runtime 的原子/CAS 辅助函数完成，调度器、GC 和栈复制都依赖这些不变量。

调度器初始化

程序启动会先在系统栈执行 schedinit，初始化锁、栈、内存分配器、GC、CPU 特征、随机数、P 等 runtime 子系统。

flowchart TD A["runtime 启动"] --> M0["建立 m0 / g0"] M0 --> S["schedinit"] S --> G["读取 GODEBUG / CPU / 内存 / GC 配置"] G --> N["计算初始 GOMAXPROCS"] N --> P["procresize：创建/调整 allp"] P --> R["创建 main goroutine"] R --> W["启动世界，进入调度"] W --> U["runtime.main -> 用户 main.main"]

procresize 必须在 STW 下调整 P 数量，初始化新增 P 的本地资源，并把不再使用 P 上的 runnable G 迁移到可继续调度的位置。

创建 goroutine：从 go f() 到 _Grunnable

编译器把 go f(args) 变成对 runtime 创建入口的调用；当前主体是 newproc/newproc1：

flowchart TD A["go f()"] --> N["newproc"] N --> SS["systemstack(newproc1)"] SS --> C{"P 的 gFree 有可复用 G?"} C -->|是| R["复用 _Gdead 的 g"] C -->|否| G["分配 g 与初始用户栈"] R --> I["初始化 sched.pc/sp、startpc、goid"] G --> I I --> ST["状态 _Gdead -> _Grunnable"] ST --> Q["runqput 到当前 P"] Q --> W["必要时 wakep 启动/唤醒 M"]

新 G 的初始 PC 被安排到 goexit 包装后的入口，使用户函数返回后必然进入 runtime 的 goroutine 退出清理。创建 goroutine 不等于马上新建 OS 线程；通常只是分配/复用 G 并把它放入当前 P 的本地队列。

运行队列：局部性、全局公平与 work stealing

队列层次

flowchart LR RN["P.runnext
1 个高优先局部槽"] --> M["M 当前优先获取"] LQ["P.runq[256]
本地无锁环形队列"] --> M GQ["sched.runq
全局队列"] --> M NP["netpoll 就绪 G"] --> M T["timer 就绪 G"] --> M V["其他 P.runq"] -->|steal 约一半| LQ
  • runnext 适合刚刚被当前 G 唤醒、很可能共享缓存的 G；它继承当前时间片。
  • 本地 runq 容量 256，owner P 从头取、尾部写；窃取者通过原子操作从头部批量取得。
  • 本地队列满时，runqputslow 把约一半旧任务加上新任务批量放到全局队列。
  • 全局队列由 sched.lock 保护；取任务时会按 runqsize/gomaxprocs+1 批量分给本地 P，见 globrunqgetbatch。

Work stealing

空闲 P 不会立刻休眠；findRunnable 会综合检查本地/全局队列、GC worker、timer、netpoll，并尝试从其他 P 窃取工作。

runqsteal 通常窃取 victim P 可运行队列的大约一半，把多数任务留在自己的本地队列并返回一个立即执行：

flowchart LR V["Victim P
G1 G2 G3 G4 G5 G6"] -->|steal half| T["Thief P
G1 G2 G3"] V --> K["Victim 保留
G4 G5 G6"] T --> E["返回一个 G 执行，其余进入 thief.runq"]

窃取一半是在负载均衡开销与缓存局部性之间折中；如果每次只偷一个，空闲 P 会频繁扫描。

调度循环：schedule → findRunnable → execute

schedule 运行在 M 的 g0 系统栈上：

flowchart TD S["schedule"] --> K{"M 锁定某个 G?"} K -->|是| LG["执行 lockedg"] K -->|否| F["findRunnable"] F --> R{"找到 G?"} R -->|否且无工作| P["停止 M / 归还 P / 等待唤醒"] R -->|是| X["execute(gp)"] X --> B["绑定 gp.m、切 _Grunnable->_Grunning"] B --> G["gogo：恢复用户 SP/PC"] G --> Y["G 运行，直到阻塞/抢占/退出/让出"] Y --> S

execute 会把 G 绑定到 M、更新状态和时间片，再通过 gogo 恢复 g.sched 中保存的寄存器上下文。调度器不是普通 Go 函数之间递归调用，而是在用户栈和 g0 系统栈之间切换。

阻塞与唤醒：为什么 G 阻塞不等于线程阻塞

Channel、Mutex、Cond、timer 等 runtime 可感知的阻塞会走 gopark：

sequenceDiagram participant G as 当前 G participant M as M/g0 participant P as P participant Q as 等待队列 G->>Q: 登记 sudog/等待原因 G->>M: gopark -> mcall(park_m) M->>G: _Grunning -> _Gwaiting M->>P: schedule 另一个 runnable G Q-->>M: 条件满足，goready/ready M->>G: _Gwaiting -> _Grunnable，入 runq P->>G: 未来某次 execute

ready 把 waiting G 改为 runnable 并入队；它不是直接让目标 G 在当前线程上继续执行。Channel 的完整阻塞链见 Channel（Go 1.26.5 源码分析）。

系统调用：M 可以被占住，P 必须继续流动

系统调用可能让 OS thread 长时间阻塞。runtime 用 _Gsyscall / _Psyscall 记录它，并允许 P 被其他 M 接管：

sequenceDiagram participant G as G participant M as M participant P as P participant S as sysmon/其他 M G->>M: entersyscall M->>G: G -> _Gsyscall M->>P: P -> _Psyscall，保留快速返回线索 M->>M: 阻塞在内核 S->>P: 长系统调用时 retake P P->>S: 交给其他 M 继续跑 Go 代码 M->>G: syscall 返回，exitsyscall M->>P: 尝试拿回 oldp 或空闲 P alt 获得 P M->>G: _Grunning，继续 else 没有 P M->>G: _Grunnable，放入队列 end

入口和返回路径见 entersyscall/exitsyscall。这解释了为什么 M 数量可能超过 P：被系统调用占住的 M 暂时不能执行其他 G，但它原来的 P 可以继续服务。

网络轮询器：少量线程等待大量 fd

网络 I/O 不会为每个连接长期占一条线程。runtime netpoller 把等待 fd 的 G 停在 poll descriptor 上，OS 多路复用器报告就绪后再把 G 变为 runnable：

flowchart LR G["G 调用 net.Read"] --> P["pollDesc 登记 waiter"] P --> GP["gopark：Gwaiting"] OS["epoll/kqueue/IOCP 等"] --> NP["runtime netpoll"] NP --> R["netpollready"] R --> Q["注入 runnable G"] Q --> E["P/M execute"]

公共逻辑位于 runtime/netpoll.go，平台文件负责具体 OS 接口。findRunnable 会用非阻塞 netpoll 检查就绪事件；所有 P 即将空闲时，也可由一个 M 阻塞在 netpoll 等待。

抢占：协作安全点与异步安全点

Go 1.26 的抢占设计在 preempt.go#L5-L51 明确区分三类安全点：

安全点 场景 做法
blocked safe-point G 已阻塞、在同步原语或系统调用中 本来就不在执行用户代码
synchronous safe-point 函数序言检查栈边界 把 stackguard0 设为 stackPreempt，下次检查转入抢占
asynchronous safe-point 用户代码中的可安全暂停指令 向 M 发 OS 信号，修改上下文进入 asyncPreempt
flowchart TD S["sysmon 发现 P 在同一时间片运行过久"] --> P["preemptone(pp)"] P --> C["gp.preempt=true
stackguard0=stackPreempt"] C --> Q{"G 很快进入同步安全点?"} Q -->|是| SP["函数序言/栈检查进入调度"] Q -->|否且平台支持| M["preemptM：向 M 发信号"] M --> A["信号上下文改到 asyncPreempt"] A --> G["gopreempt_m，G 重新入 runnable"]

retake 当前使用约 10ms 的 forcePreemptNS 判断同一调度时间片是否过长。10ms 不是 goroutine 保证执行时长，也不是固定轮询周期；调度仍受安全点、系统调用、GC、OS 调度和负载影响。

sysmon：没有 P 的后台监督线程

sysmon 不绑定 P，因此在所有 P 忙碌或陷入系统调用时仍能工作。它负责或参与：

  • 检查网络轮询器和长时间阻塞的系统调用。
  • retake 长时间处于 syscall 的 P。
  • 请求抢占运行过久的 G/时间片。
  • 触发周期 GC、调度 trace 等后台动作。
  • Go 1.25+ 周期性检查默认 GOMAXPROCS 是否应随容器 CPU 配额变化。

sysmon 的休眠间隔会动态调整，它不是持续忙轮询。

Spinning M：避免频繁休眠与惊群

当有 P 找不到工作时，runtime 允许少量 M 处于 spinning 状态继续寻找工作；如果全部立刻休眠，新 G 到来需要更昂贵的线程唤醒。反之，过多 spinning M 会浪费 CPU 并争抢同一批 P。

flowchart TD A["P 暂无本地任务"] --> S{"允许成为 spinning M?"} S -->|是| W["检查全局队列/netpoll/timer/偷取"] W -->|找到 G| R["resetspinning，确保还有搜索者"] W -->|仍无工作| I["减少 nmspinning，重新检查后 idle"] S -->|否| I N["新 runnable G 到来"] --> P{"有 idle P 且无 spinning M?"} P -->|是| K["wakep/startm"]

这套协议试图避免“先发布任务、后让最后一个搜索者休眠”之间的丢失唤醒，相关代码分散在 wakep/startm/stopm 和 findRunnable 中。

GOMAXPROCS 与容器 CPU 配额

P 的数量决定同一时刻最多有多少执行普通 Go 代码的执行上下文。Go 1.25 起，未被用户显式设置时，默认值会考虑逻辑 CPU、CPU affinity 和 Linux cgroup CPU 配额，并可动态更新。

sysmonUpdateGOMAXPROCS 的关键约束：

  • 如果程序显式调用 runtime.GOMAXPROCS 或显式配置，runtime 不自动覆盖。
  • sysmon 读取外部限制后，不能自己直接 STW；它唤醒辅助 G 完成 P 数量调整。
  • 修改 P 数量需要 procresize，会影响运行队列、timer、mcache 等 per-P 状态。

[!tip] 性能调优 不要机械地把 GOMAXPROCS 设为宿主机核数。容器中应优先验证默认行为，再结合 CPU 配额、节流指标、延迟和吞吐测量决定是否显式覆盖。

LockOSThread：G 与 M 的例外绑定

普通 G 可在不同 M 之间迁移。runtime.LockOSThread 会建立 lockedg/lockedm 双向关系，使当前 G 后续继续在同一 OS thread 上运行，适用于线程局部状态、GUI 主线程或特定系统 API。

代价是降低调度自由度；锁定的 G 阻塞时，runtime 可能需要额外 M 承载其他 P。每次 LockOSThread 必须匹配 UnlockOSThread，除非 goroutine 设计上永久占用该线程。

调度器不保证什么

  1. 不保证 goroutine 按创建顺序运行。
  2. 不保证 runnext 或 select 的严格公平性。
  3. 不保证每个 G 精确获得固定 10ms 时间片。
  4. 不保证 G 固定在同一个 P/M/CPU 上。
  5. 不保证 goroutine 退出时自动 join；需要显式 WaitGroup/Channel/Context 生命周期。
  6. 不保证增加 goroutine 或增大 GOMAXPROCS 就一定提升吞吐。

诊断调度问题

schedtrace

1

GODEBUG=schedtrace=1000,scheddetail=1 ./app

重点观察 gomaxprocs、idle P、线程数、spinning threads、全局 runqueue 和各 P runqueue。它适合快速看整体失衡，但输出本身会有开销。

执行 trace

1
2

go test -trace=trace.out ./...
go tool trace trace.out

trace 可以回答：G 在哪个 P 上运行、何时被抢占/阻塞、系统调用持续多久、netpoll 何时唤醒、并行度为什么下降。

Go 1.26 还提供实验性 goroutine 泄漏 profile：

1
2

GOEXPERIMENT=goroutineleakprofile go build ./cmd/app
curl -o leaks.pb.gz http://127.0.0.1:6060/debug/pprof/goroutineleak

它利用 GC 可达性识别一类永远无法解除的 Channel、Mutex、Cond 等等待；全局变量仍可达、或逻辑上“很久但可能恢复”的泄漏不一定能被判定。

调度器源码解释现象，但优化应从测量开始。大多数业务性能问题首先是工作量、锁竞争、I/O、分配或并行度设计问题，不应直接归因于“GMP 调度慢”。

总结

  1. G 保存 goroutine 的栈、寄存器上下文和生命周期状态；M 是 OS thread；P 是执行 Go 代码的许可与本地资源。
  2. GOMAXPROCS 决定 P 数，不限制 M 总数；Go 1.25+ 默认值可感知并动态适应容器 CPU 配额。
  3. 新 G 通常进入当前 P 的 runnext 或本地 256 槽运行队列，不会直接创建线程。
  4. 调度循环从本地/全局队列、GC、timer、netpoll 和其他 P 获取 G；空闲 P 通过 work stealing 均衡负载。
  5. runtime 可感知阻塞只 park G，M/P 可继续运行别的 G；阻塞系统调用则可能占住 M，P 可被 sysmon 回收。
  6. 抢占同时使用同步安全点和基于信号的异步安全点；约 10ms 是 sysmon 请求抢占的阈值，不是严格时间片保证。
  7. 调度问题应使用 trace、schedtrace 和 pprof 建立证据，再决定是否调整并发结构或 GOMAXPROCS。
