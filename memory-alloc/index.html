内存分配器：Go 1.26.5 源码分析

Go 的内存分配器不是一个独立的 malloc 包装器，而是编译器、每 P 缓存、全局页分配器、垃圾收集器和操作系统虚拟内存共同组成的一条路径。本文固定在 Go 1.26.5，沿着一次对象分配向下阅读：

IMPORTANT

阅读边界 本文讨论的是 逃逸到 Go heap 的对象如何被 runtime 分配。变量最终放在栈还是堆上，首先由编译器逃逸分析决定，参见 栈空间管理；对象何时死亡、span 如何 sweep，参见 垃圾收集器。

Go 1.26.5 实现概览

主题当前实现
堆布局使用稀疏、分层的 arena map；堆可从地址空间不同区域增长
堆基址64 位平台默认启用 heap base address randomization
GC 元数据Green Tea GC 会在符合条件的小对象 span 尾部内联 marks/scans
小对象中心缓存使用 partial/full × swept/unswept 的 spanSet 体系
分配入口mallocgc 按 noscan/scan、header/no-header、tiny/small/large 细分路径

Go 1.26 的官方发布说明明确指出：64 位平台默认随机化堆基址，Green Tea GC 默认启用。两项都会影响理解 allocator 的地址空间与 span 元数据布局：Go 1.26 Release Notes。

一、分配前：变量为什么来到堆上

编译器逃逸分析保证两个不变量：指向栈对象的指针不能被存入堆；栈对象不能被可能活得更久的引用持有。分析入口和解释写在 cmd/compile/internal/escape/escape.go#L21-L47。

func stackValue() int {
    x := 1
    return x
}

func heapValue() *int {
    x := 1
    return &x
}

第二个 x 通常需要在 heap 上拥有足够长的生命周期。查看编译器判断：

go build -gcflags='all=-m=2' ./...

WARNING

new 就在堆上”是错的 new(T)、make([]T, n)、闭包捕获都只是分析输入。只要编译器能证明生命周期和大小安全，它们仍可能完全在栈上；反之，一个普通局部变量也可能逃逸。

逃逸对象经过 SSA lowering 后调用 runtime.newobject，最终进入 mallocgc。零大小对象直接返回共享的 zerobase，见 mallocgc#L1074-L1077。

二、分配器的物理层次

1. Page、span、size class

Go runtime 的逻辑页大小是 8 KiB，常量来自 PageShift = 13；小对象上限是 32 KiB；共有 68 个 size class（含 0 号），见 sizeclasses.go#L84-L100。

mspan 管理一段连续 page。同一 small-object span 中的对象大小相同：

常见 class 示例：

请求大小对齐后的 slot每 span 页数每 span 对象数
1～8 B8 B11024
9～16 B16 B1512
257～288 B288 B128
1025～1152 B1152 B17
28673～32768 B32768 B41

请求大小会向上舍入，因此 24 B 对象落入 24 B class，而 25 B 会落入 32 B class。差额就是内部碎片。完整表格直接看 sizeclasses.go#L6-L73。

2. spanClass：大小与扫描属性的乘积

一个 size class 又分成 scan 和 noscan 两类，所以 mcache.alloc 按 spanClass 索引。没有指针的对象无需 GC 扫描，可以减少 scan work：

spanClass = sizeClass * 2 + noscanBit

这就是为什么同样大小的 []byte backing array 与 []*T backing array可能进入不同 span。

3. mcache：绑定 P，不是绑定线程

mcache 是 per-P cache。热字段包括：

  • alloc[spanClass]：当前用于小对象分配的 span；
  • tiny/tinyoffset：当前 16 B tiny block；
  • nextSample：下一次 heap profile 采样阈值；
  • scanAlloc：本 P 新增的可扫描字节；
  • stackcache：小 goroutine stack 的缓存，供 栈空间管理 使用。

执行分配时 runtime 暂时禁止抢占，保证当前 M 持有的 P 与 mcache 不会在中途变化。因此 fast path 不需要锁。

每个 span class 有一个 mcentral。Go 1.26.5 使用以下四类 spanSet 组织 span：

具体结构见 mcentral#L21-L46。cacheSpan 优先取 partial swept，然后尝试 sweep unswept span；最多尝试一定预算，最后才调用 grow 从 mheap 获取新 span，见 cacheSpan#L81-L198。

5. mheap 与 pageAlloc

mheap 是全局堆状态容器，内部真正负责空闲 page 区间的是 pageAlloc。分配 span 时优先尝试当前 P 的 page cache；失败再加 mheap.lock 访问全局页分配器，见 allocSpan#L1224-L1314。

三、mallocgc 分流

总入口做了什么

mallocgc 的职责可以压缩为：

  1. 处理零大小对象；
  2. GC 标记阶段扣除 assist credit；
  3. 根据大小、是否包含指针、是否需要 malloc header 选择路径；
  4. 初始化对象、类型/bitmap 元数据；
  5. 用 publication barrier 保证 GC 不会看见半初始化对象；
  6. 标记期把新对象直接分配为黑色；
  7. 更新 profile 与 GC 触发统计。

1. Tiny：小于 16 B 且 noscan

Tiny allocator 把多个无指针小对象塞进一个 16 B block；只有当 block 内所有子对象都不可达时，整块才会被回收。源码限制与设计解释见 mallocgcTiny#L1218-L1246。

关键约束：

  • 必须 noscan，因为内部子对象没有各自独立的 GC 元数据；
  • 分配时按 2/4/8 字节对齐；
  • 最坏情况下一个仍存活的子对象会让整块 16 B 保持存活；
  • race detector 下会关闭一部分合并行为以便准确追踪。

2. Small：不超过 32 KiB

小对象热路径是：根据 size class 找到 mcache.alloc[spc]，从 allocCache 找一个空 bit，计算 slot 地址并返回。mspan.allocCache 保存 allocBits 的反码，使 CPU 可以用 trailing-zero 指令快速找第一个空位，字段解释见 mspan#L433-L466。

objectAddress = span.base + freeIndex * span.elemsize

若 span 已满，mcache.refill 把旧 span 归还 central，再调用 mcentral.cacheSpan，完整代码见 mcache.refill#L155-L221。

scan 与 noscan 为什么分开

无指针对象不需要写类型位图；含指针对象必须先清零并建立扫描元数据，避免 GC 把未初始化字节误认为指针。当前代码甚至继续区分：

  • mallocgcSmallNoscan；
  • mallocgcSmallScanNoHeader：小到可以把 heap bits 放在 span 尾部；
  • mallocgcSmallScanHeader：slot 前放 mallocHeaderSize 类型头。

SmallScanNoHeader 初始化类型位图、执行 publication barrier、标记期 allocate-black 的顺序可见 malloc.go#L1503-L1568。

3. Large：大于 32 KiB

大对象不经过 mcache.alloc 与 mcentral，而是按 page 数直接从 mheap 分配独占 span。见 mallocgcLarge#L1687-L1724。

这意味着一个 32769 B 请求至少需要 5 个 8 KiB page，并承担 page 粒度的内部碎片。大 buffer 对 RSS、GC 扫描与 scavenger 都可能有明显影响。

四、虚拟内存与 arena

稀疏 arena map

Go 1.26.5 的 heap 由多个 arena 组成：典型 64 位平台每个 arena 为 64 MiB。arena 起始地址对齐，mheap_.arenas 使用 L1/L2 两级映射从地址快速定位 heapArena。源码总览在 malloc.go#L77-L99。

heapArena 的 page map、page mark 与 Green Tea inline-mark 标志位见 mheap.go#L268-L321。它不是“实际对象都连续存放”的承诺，而是一个从地址到元数据的索引框架。

Go 1.26：堆基址随机化

64 位平台第一次 grow heap 时会随机化一部分地址位，相关逻辑见 mheap.grow#L1607-L1615。这是安全加固，不改变 Go 的语言语义，但说明：

  • 不要依赖多次运行中的 heap 地址稳定性；
  • uintptr 不是可持久化对象标识；
  • 调试笔记中的固定地址只代表一次进程实例。

Reserved、Prepared、Ready、Released

runtime 把虚拟地址保留、映射可用、实际物理页以及归还 OS 分成不同状态。对应用开发者最重要的结论是：

VSS 很大不等于实际占用了同样多的物理内存；观察容器内存时应结合 RSS、runtime metrics 与 heap profile。

五、分配、GC 与回收如何闭环

这里有三个常被混淆的“释放”：

  1. 对象不可达：只是 GC 可以回收的条件；
  2. sweep 释放 slot/span：runtime 可再次分配；
  3. scavenge 归还物理页给 OS：才会直接推动 RSS 下降。

scavenger 同时有后台异步和分配期同步两条路径，目标是控制估算 heap RSS，见 mgcscavenge.go#L5-L71。所以“GC 完成后 RSS 必须立刻等比例下降”不是正确预期。

Green Tea 对 allocator 元数据的影响

Green Tea 对符合条件的小对象 span，把 marks 与 scans 放在 span 尾部。初始化入口在 mspan.initHeapBits，布局调整在 spanHeapBitsRange#L569-L575。

这会轻微减少某些 span 可放对象/位图的空间，但换来按 span 批量扫描的局部性。详细算法见 垃圾收集器。

六、生产诊断与优化

先区分四类问题

现象优先证据常见原因
allocs/op 高benchmark -benchmem、alloc profile逃逸、字符串/切片临时对象、接口装箱
inuse_space 持续涨heap profile 对比、对象保留路径cache 无界、goroutine/closure 引用、队列积压
HeapAlloc 降但 RSS 高runtime metrics、RSS、scavenger tracepage 仍保留、碎片、非 Go 内存
GC CPU 高CPU profile、gctrace、trace分配速率高、scan heap 大、指针密集对象

可复制的诊断命令

# 逃逸与内联信息
go build -gcflags='all=-m=2' ./...

# 基准：分配次数和字节
go test -run='^$' -bench=. -benchmem ./...

# 生成 heap profile
go test -run='^$' -bench=BenchmarkX -memprofile=mem.out ./path/to/pkg
go tool pprof -http=:0 mem.out

# GC 与 scavenger 摘要
GODEBUG=gctrace=1,scavtrace=1 ./app

heap profile 的两个视角：

  • inuse_space/inuse_objects：采样时仍存活，适合看 retention；
  • alloc_space/alloc_objects：累计分配，适合看 churn。

Go 官方诊断总览也强调 profile、trace 与 runtime statistics 用途不同，参见 Diagnostics。

优化顺序

  1. 用 profile 证明热点，不从“感觉会逃逸”开始；
  2. 减少分配次数，通常比只减少单对象几字节更有效；
  3. 减少长期存活指针图，降低下一轮 GC scan work；
  4. 复用大 buffer 时设置上限，避免小请求长期持有峰值容量；
  5. 重新 benchmark，并比较 CPU、alloc、heap、延迟，而不是只看一个指标。

WARNING

sync.Pool 不是稳定缓存 sync.Pool 中对象可在 GC 时被清理。它适合降低临时对象 churn，不适合保存业务状态；放入超大 buffer 还可能提高短期 RSS。参见 同步和锁（Go 1.26.5 源码分析）。

七、常见误区

误区正确理解
所有 new 都走 heap是否上 heap 由逃逸分析决定
mcache 是 per-M/per-threadGo 当前实现是 per-P
small object 每次都要全局锁热路径只访问当前 P 的 mcache 与 mspan bitmap
GC 释放对象后 RSS 立即下降slot 可复用与物理页归还 OS 是两个阶段
内存高一定是 Go heap 泄漏还可能是 goroutine stack、mmap、cgo、碎片、profile 自身开销
32 KiB 对象正好占 4 页所以没有代价还要考虑 size class、元数据、存活时间与扫描属性

总结

Go 1.26.5 分配器的关键不是记住结构体名字，而是理解两条闭环：

分配：编译器 -> mallocgc -> mcache -> mcentral -> mheap -> OS
回收：可达性标记 -> sweep slot/span -> pageAlloc -> scavenger -> OS

它通过 size class 控制碎片，通过 per-P cache 消除热路径锁竞争，通过 span/page 分层摊销全局管理成本，再与 GC pacing、sweep 和 scavenger 协同控制吞吐与 RSS。下一篇应继续阅读 垃圾收集器，把“谁仍然存活”与“空 slot 如何重新出现”接起来。
