GMP 调度器：Go 1.26.5 源码分析

Go 调度器解决的核心问题是：如何用较少的操作系统线程运行数量巨大的 goroutine，同时在阻塞、系统调用、网络 I/O、抢占和 GC 之间维持吞吐与延迟。G、M、P 不是三个抽象首字母，而是 runtime 中真实存在、长期复用的数据结构。

[!info] 版本与源码基线 本文以 Go 1.26.5 为基准，源码链接固定到提交 c19862e5f8415b4f24b189d065ed739517c548ba。旧笔记 GMP 仅作历史参考，当前实现以 runtime 源码为准。

版本调度/runtime 相关变化
Go 1.1引入以 P 和 work stealing 为核心的新调度器
Go 1.14基于信号的异步抢占投入使用，纯计算循环也能被抢占
Go 1.21P 本地队列、netpoll、timer 等框架持续演进，GMP 基本模型保持稳定
Go 1.25默认 GOMAXPROCS 具备容器 CPU 配额感知，并可由 sysmon 周期性更新
Go 1.26Green Tea GC 默认启用；新增实验性 goroutineleak profile，可发现一类永久阻塞的 G

NOTE

GC 不是调度器，但两者高度耦合 P 持有分配缓存与 GC worker 状态，调度循环会优先运行 GC worker；STW、抢占和栈扫描也都需要调度器配合。因此理解 GMP 时不能完全绕开 GC。

快速理解：把 runtime 想成一个车间

第一次读源码容易被 G、M、P、g0、runnext、netpoll、sysmon 这堆名词淹没。先用一段话建立心智模型：

把 Go runtime 想成工厂车间。G 是任务卡，写 go f() 就是往筐里扔一张卡，卡很轻（栈初始 2KB），能同时有几十万张。M 是工人，即 OS 线程，一个工人同一时刻只干一张卡。P 是工牌加工具台，没有工牌的工人不能执行普通 Go 代码；工具台上挂着本地任务筐（256 槽的本地队列）、内存分配缓存、timer 等。GOMAXPROCS=N 就是发 N 个工牌，工人数量按需增减——所以工牌可以比工人多（活少，工人睡觉了），工人也可以比工牌多（多个 M 堵在 syscall 上）。

新卡优先放当前 P 的 runnext，筐满了进本地 256 槽队列，再满就把约一半倒去全局大筐。工人找活顺序是：本地筐 → 全局大筐 → GC worker → timer → 网络就绪 → 去别的 P 筐里偷一半（work stealing）→ 还没活就睡，但留一两个工人”装睡”（spinning）等新卡，省掉线程唤醒开销。

G 阻塞不等于工人卡住，这是最容易懵的地方，分三种：

  1. runtime 认识的阻塞（channel、sync.Mutex、timer、select）走 gopark，G 从 M 手里摘下来挂到 channel/锁上，M 拿着 P 立刻去拿下一张卡。工人没停。
  2. 系统调用阻塞（磁盘读、cgo）会真把 OS 线程挂住，M 进 syscall 前把 P 交出来，别的 M 捡起 P 继续跑。这是 M 数量能超过 P 的原因。
  3. 网络 I/O 由 runtime 自己用 epoll/kqueue/IOCP 实现 netpoller，G 等连接时只 park G，M 不进阻塞 syscall，epoll 报就绪再把 G 唤醒。所以几个线程能扛几十万连接。

调度的核心循环是 schedule() → findRunnable() → execute(g) → 跑用户代码，跑累了再回 schedule。schedule 和 findRunnable 跑在 M 自带的 g0 系统栈上（一块固定的、不属于任何 G 的栈），不是普通函数互相递归。一个 G 不能无限霸占 P：函数序言有同步抢占检查，纯 for{} 死循环则由 sysmon 发 SIGURG 信号做异步抢占，10ms 是发起抢占请求的阈值，不是硬时间片。

记住五个反直觉点：GOMAXPROCS=1 不是只有一个线程；goroutine 不保证按创建顺序跑；go f() 通常不创建新线程；G 退出后 g 结构会被复用；LockOSThread 把 G 和 M 焊死，是非默认逃生门。

后面章节按这个顺序展开：核心模型 → 调度循环 → 阻塞与 I/O（重点） → 抢占（重点） → 配置与边界 → 诊断实践。

一、核心模型：G、M、P

G：goroutine 的运行时描述

g 不等于”函数”。它保存一个 goroutine 从创建到退出所需的运行状态：

G 对象会复用：goroutine 退出后，其 g 进入空闲池，未来可代表另一个 goroutine。G 的用户栈起始很小，按需增长或收缩；运行时还会扫描它来寻找 GC root。

M：操作系统线程

m 是 machine，即 OS thread 的 runtime 表示：

M 可以没有 P，例如阻塞在系统调用、执行 cgo 或处于空闲线程池。M 的数量不等于 GOMAXPROCS；大量系统调用可以让 runtime 创建更多 M，但只有拿到 P 的 M 才能执行普通 Go 代码。M 总数有上限，由 runtime/debug.SetMaxThreads 控制（默认 10000）。

P：执行权与每 P 资源

p 是 processor。它不是 CPU 核心，也不是线程，而是执行用户 Go 代码所需的许可和一组分片资源：

P 的数量等于当前 GOMAXPROCS。把常用调度、分配和 timer 状态放在 P 上，可以让多数操作使用本地分片，减少全局锁竞争。

三者如何组合

  • G 提供”要运行什么”。
  • M 提供”在哪里运行”，即 OS 执行上下文。
  • P 提供”运行 Go 代码的权利和本地资源”。
  • 调度器持续匹配三者，而不是把 G 永久绑定给某个 M 或 P。

WARNING

常见误解 GOMAXPROCS=1 不是只有一个 M，也不是程序没有并发；它只限制同时执行普通 Go 代码的 P 数量为 1。阻塞系统调用、runtime 线程和 cgo 仍可能存在多个 M。

G 的状态机

主要状态定义在 runtime2.go：

_Gscan 是叠加在基础状态上的 GC 扫描位，不是普通独立生命周期状态。状态迁移必须通过 runtime 的原子/CAS 辅助函数完成，调度器、GC 和栈复制都依赖这些不变量。

二、调度循环：从 go f() 到 G 被执行

启动与创建 goroutine

程序启动先在系统栈执行 schedinit，初始化锁、栈、内存分配器、GC、CPU 特征、随机数、P 等子系统。

procresize 必须在 STW 下调整 P 数量，初始化新增 P 的本地资源，并把不再使用 P 上的 runnable G 迁移到可继续调度的位置。

编译器把 go f(args) 变成对 runtime 创建入口的调用，主体是 newproc/newproc1：

新 G 的初始 PC 被安排到 goexit 包装后的入口，使用户函数返回后必然进入 runtime 的 goroutine 退出清理。创建 goroutine 不等于马上新建 OS 线程；通常只是分配/复用 G 并把它放入当前 P 的本地队列。

运行队列与 work stealing

  • runnext 适合刚刚被当前 G 唤醒、很可能共享缓存的 G；它继承当前时间片。
  • 本地 runq 容量 256，owner P 从头取、尾部写；窃取者通过原子操作从头部批量取得。
  • 本地队列满时，runqputslow 把约一半旧任务加上新任务批量放到全局队列。
  • 全局队列由 sched.lock 保护；取任务时按 runqsize/gomaxprocs+1 批量分给本地 P，见 globrunqgetbatch。

空闲 P 不会立刻休眠；findRunnable 会综合检查本地/全局队列、GC worker、timer、netpoll，并尝试从其他 P 窃取工作。

runqsteal 通常窃取 victim P 可运行队列的大约一半，把多数任务留在自己的本地队列并返回一个立即执行：

窃取一半是在负载均衡开销与缓存局部性之间折中；如果每次只偷一个，空闲 P 会频繁扫描。

schedule → findRunnable → execute

schedule 运行在 M 的 g0 系统栈上：

execute 会把 G 绑定到 M、更新状态和时间片，再通过 gogo 恢复 g.sched 中保存的寄存器上下文。调度器不是普通 Go 函数之间递归调用，而是在用户栈和 g0 系统栈之间切换。

g0 系统栈为什么存在

每个 M 自带两块栈：

  • 用户 G 的栈：goroutine 跑业务代码用，初始 2KB，按需扩缩，GC 扫栈时可能被整体复制到新地址。
  • g0 栈（系统栈）：M 出生时就在 OS 线程上分配好的一块栈，属于 M 自己，大小固定、不扩容、不被 GC 移动。M 上还有一块独立的 gsignal 栈用于信号处理。

g0 是 runtime 干脏活的地方：调度、栈增长、信号处理、GC、defer/panic 的关键路径、cgo 切换。不能直接在用户 G 的栈上做这些事，原因有四：

  1. 栈可能不够大。用户 G 栈最小 2KB，调度、GC、信号处理链路深、局部变量大，塞进去容易爆。
  2. 用户栈会被 GC 搬家。栈扩容时 runtime 会分配新栈、复制内容、改掉所有指针；调度器正跑在那块栈上等于自己抽走自己脚下的地板。g0 栈不参与栈复制，地址稳定。
  3. 切换 G 需要中立落脚点。从 G-A 切到 G-B 时，要先存 A 的寄存器再恢复 B 的；这段代码不能跑在 A 或 B 任何一个栈上。g0 提供这个中立地带。
  4. 信号必须落在已知安全的栈上。SIGSEGV、SIGURG 这类信号可能在用户栈任意指令处打断，信号处理函数落在 gsignal 上，必要时再切到 g0 进调度。

切换由两段汇编完成：mcall 从用户 G 栈切到 g0 栈，gogo 从 g0 切回某个用户 G 的栈和寄存器。字段在 runtime2.go 的 m 结构体里，汇编函数在 runtime/asm_amd64.s（其他架构对应 asm_*.s）。

三、阻塞、系统调用与网络 I/O

IMPORTANT

这是 GMP 最关键的一章 用户写 Go 代码碰到的 90% 调度困惑——为什么 IO 密集服务没几个线程、为什么磁盘 IO 会卡 P、为什么一个 for{} 以前能把整个程序搞挂——答案都在这三种阻塞的区别里。它们在 runtime 里走完全不同的路径。

runtime 可感知阻塞：只 park G，M 不停

Channel、Mutex、Cond、timer、select 等 runtime 原生同步原语走 gopark：

gopark 把当前 G 从 M 手里摘下来、状态改为 _Gwaiting、挂到那个 channel/锁/timer 的等待队列上，然后 M 立刻回调度器找下一张卡。整个过程没有任何系统线程阻塞。

ready 是反向操作：把 waiting G 改为 runnable 并入队（优先放 runnext），它不是直接让目标 G 在当前线程上继续执行。Channel 的完整阻塞链见 Channel（Go 1.26.5 源码分析）。

系统调用：M 被占住，P 必须流动

系统调用可能让 OS thread 长时间阻塞，runtime 喊不醒。runtime 用 _Gsyscall / _Psyscall 记录它，并允许 P 被其他 M 接管：

入口和返回路径见 entersyscall/exitsyscall。进 syscall 前 M 把 P 交回 idle 链表，exitsyscall 时 M 试图拿回自己原来的 P，拿不到就从 idle 链表取一个，再拿不到就把 G 塞进全局队列、M 自己睡觉。这解释了为什么 M 数量可能超过 P：被系统调用占住的 M 暂时不能执行其他 G，但它原来的 P 可以继续服务。

网络轮询器：几个线程扛几十万连接

网络 I/O 不会为每个连接长期占一条线程。runtime netpoller 把等待 fd 的 G 停在 poll descriptor 上，OS 多路复用器报告就绪后再把 G 变为 runnable：

公共逻辑位于 runtime/netpoll.go，平台文件负责具体 OS 接口。

底层流程是 Go “同步写法、异步执行”的关键：

  1. socket 被设成非阻塞。net.Dial/net.Listen 返回的 fd 底层带 O_NONBLOCK。conn.Read(buf) 实际执行 read(fd, buf)：有数据立刻返回；没数据内核返回 EAGAIN，不阻塞线程。
  2. EAGAIN 时把 G 挂到 pollDesc。每个网络 fd 绑一个 runtime.pollDesc，rg/wd 记录等读/等写的 G。internal/poll.FD.Read 在 EAGAIN 时调 runtime.netpollblock(pd, 'r')，内部 gopark 把当前 G 改成 waiting、把 G 指针存进 pd.rg，M 立刻回调度器找别的 G 跑。
  3. epoll 在后台等。Linux 用 epoll、macOS/BSD 用 kqueue、Windows 用 IOCP。有一个不绑 P 的 M 真正阻塞在 epoll_wait 上（这是少数真正阻塞的 OS 线程之一）。
  4. 就绪事件把 G 改回 runnable。数据到了 epoll_wait 返回一批事件，netpoller 从对应 pollDesc.rg/wd 取出之前挂着的 G，改成 runnable 注入调度器（优先塞空闲 P 的本地队列，没有就放全局队列）。poller M 自己不执行业务 G，只卸货。
  5. G 被重新调度，Read 返回数据。某个 M+P 取到这个 G，从它被 park 的位置继续，重新 read(fd, buf)；这次数据已在内核缓冲，直接返回。用户代码视角就是 conn.Read 阻塞了一段时间后返回，感知不到中间被切走。

findRunnable 和 netpoll 有两个关键交互：每次找活开头先调一次非阻塞 netpoll(0) 顺手收割就绪 G（延迟极低）；当本地/全局队列、偷任务、GC、timer 都没活时，P 休眠前再做一次非阻塞 netpoll；整个系统都没活就让一个 M 阻塞在 epoll_wait 上，避免空转烧 CPU。

展开说，这是”绝不浪费一次调度，也绝不空转”的设计：

  1. 每次开头顺手 netpoll(0)：netpoll(0) 里的 0 表示非阻塞——有就绪的网络事件就立刻返回那批 G，没有也马上返回，不会让 P 等。反正正要找活，顺便查一下网络有没有已经准备好的 G，有就直接拿来跑，省去专门唤醒的延迟。
  2. 真没活了，P 睡觉前再查一次：本地队列、全局队列、work stealing、GC worker、timer 全找过一遍都没活，P 准备 park 了，最后再非阻塞 netpoll 一次，防止这期间刚好有网络事件就绪。有就不用睡了。
  3. 全系统空闲 → 一个 M 阻塞在 epoll_wait：不能让所有线程 while(true) 空转烧 CPU。让唯一一个不绑 P 的 M 阻塞在 epoll_wait 上（这是系统调用，没事件时线程完全睡眠不占 CPU），其余 M/P 都休眠；网络数据到来时 epoll_wait 返回，这个 M 把就绪 G 注入调度队列并唤醒空闲 P 来跑。

所以两次非阻塞轮询保证低延迟（就绪 G 被顺手发现，不用等唤醒），最终阻塞在 epoll_wait 保证空闲时零 CPU 消耗。

为什么能扛几十万连接：每个等待中的连接只占一个 parked 的 G（初始栈 2KB 且等待期间不增长），不占 M、不占 P、不参与调度；真正需要 M 的只有活跃连接；epoll 一个线程能等百万级 fd。典型 Go 服务的 M 数约等于 GOMAXPROCS 加几个 runtime 后台线程（sysmon、netpoller），再加少量被 syscall/cgo 堵住的 M。

几个边界：

  • 只有网络 fd 走 netpoller。Linux 上 epoll 对 regular file 永远报就绪，但磁盘读仍可能真阻塞，这种 read 走 entersyscall 路径（M 与 P 解绑），不是 park G，所以磁盘 IO 重的服务 M 数会明显增多。
  • cgo 调用同理，会占住 M，不走 netpoller。
  • DNS 默认走纯 Go resolver，走 netpoll；CGO_ENABLED=1 且命中 cgo resolver 时那次查询会阻塞 M。
  • deadline（SetReadDeadline）是把 timer 和 pollDesc 联动，超时由 runtime 唤醒 G 并让 Read 返回 timeout 错误，不是真的中断 syscall。
  • Windows IOCP 模型不同（overlapped 读写、完成后返回完成项），runtime 把它适配成同样的”G park → 完成后唤醒”抽象，用户代码不用区分。

四、抢占：怎么打断一个死循环

IMPORTANT

这是 GMP 的第二个重点 Go 调度器是协作式还是抢占式？答案是”两者都有”。理解这一章就理解了为什么现代 Go 里 for{} 不会把调度器饿死。

Go 1.26 的抢占设计在 preempt.go#L5-L51 明确区分三类安全点：

安全点场景做法
blocked safe-pointG 已阻塞、在同步原语或系统调用中本来就不在执行用户代码
synchronous safe-point函数序言检查栈边界把 stackguard0 设为 stackPreempt，下次检查转入抢占
asynchronous safe-point用户代码中的可安全暂停指令向 M 发 OS 信号，修改上下文进入 asyncPreempt

同步抢占与异步抢占

抢占只针对此刻正跑在 M 上的 G（_Grunning）。G 在等 channel、锁、timer、网络、syscall 时早就让出 M 了，谈不上抢。真正的难题是：一个 G 正在 CPU 上死循环，runtime 怎么把它拽下来。

同步抢占：编译器在每个函数序言插栈边界检查，大致是 CMP SP, g.stackguard0。stackguard0 平时存栈增长阈值；runtime 想抢占时把它改成特殊值 stackPreempt。下次函数调用执行到序言的 CMP 时必然命中，跳进 runtime.morestack，判断是抢占请求而非真的栈溢出，就转到 runtime.gopreempt → mcall(gosched) 主动挂起。问题在于：检查只在函数被调用的瞬间发生一次。for {} 里没有任何函数调用，序言代码根本不执行，哨兵永远检测不到。Go 1.14 以前这就是著名的调度器饿死问题，一个死循环能把一个 P 永久占住，连 GC STW 都过不去。

异步抢占（Go 1.14+） 靠 OS 信号解决：

  1. sysmon 扫描 P，发现某个 G 连续跑超过 forcePreemptNS（10ms），给它的 M 发 SIGURG（挑这个信号因为几乎没别的程序用它）。
  2. 内核直接中断那个 M 上正在执行的指令，跳到 runtime 注册的 sighandler，此时 M 已切到独立的信号栈 gsignal 上。
  3. 信号处理函数拿被打断时的 PC 查 pclntab，判断这个指令地址是不是”异步安全点”——即此刻栈和寄存器里的指针能否被保守扫描识别。不是就跳过，等下一次信号。
  4. 是安全点就修改信号上下文 mcontext：把 PC 改成 runtime.asyncPreempt 的地址，把原 PC、SP 等压到用户栈上伪装成一次普通调用，然后从信号返回。
  5. M 恢复执行时”以为自己刚调用了 asyncPreempt”，后者把所有寄存器 spill 到栈上，调 asyncPreempt2 → mcall(gopreempt_m)，在 g0 上把当前 G 挂起，进 schedule 找下一个 G。
  6. 等这个 G 下次被调度回来，gogo 恢复寄存器和栈，PC 回到被信号打断的位置继续，就像什么都没发生。

编译器还在可能长时间循环的**回边（back edge）**通过 PCDATA 表标记异步安全点。所以即便 for {} 一个函数都不调，回边也会被打标，SIGURG 落在那里就能被识别为安全点并抢走。

10ms 不是硬上限

容易误以为”每个 G 至多跑 10ms 就一定被切走”。实际不是，延迟来自：

  1. sysmon 不是精确 10ms 定时器。它在循环里动态 sleep：闲置时可睡到 ~10s，发现有 P 在跑 G 时才缩短到 ~10ms 粒度。判断是 pd.schedwhen + forcePreemptNS <= now，所以从 G 开跑到被发现超时，实际是 10ms 加 sysmon 下一轮唤醒延迟；机器忙、被宿主机调度拖慢时更大。
  2. 检测到不等于立刻抢走。sysmon 只是投递 SIGURG：信号要等当前指令完成；打断时 PC 必须在异步安全点，不是就跳过等下轮；G 若在 runtime 内部、持有 m.locks、跑在 g0、在 cgo、或在 malloc/GC 某些阶段，canPreemptM 直接返回 false，抢占推迟到离开临界区。
  3. 同步抢占通常更早发生。普通 Go 代码几乎不可能一个函数都不调，函数序言会先撞到 stackPreempt，往往不到 10ms 就让出了。10ms 只是”纯计算无函数调用”这种最坏情况的兜底。

用 trace 观察 CPU 密集型 goroutine，单次连续运行时间一般分布在：几十微秒到几毫秒（撞到同步安全点或主动阻塞）；~10ms 附近（纯循环被异步信号抢走）；偶尔明显超过 10ms（runtime 临界区、安全点未命中、sysmon 被拖慢）。

Go 调度器不是按 vruntime 公平分配 CPU 的轮转调度器（不像 CFS）：G 主动阻塞时立刻让出，远早于 10ms；取哪个 runnable G 有自己的偏好（runnext、本地队列优先、work stealing 偷一半），不保证轮转公平；G 被抢占后重回队列，理论上可能马上又被同一个 P 取走继续跑。

更准确的说法：在用户代码、非 runtime 临界区、且能找到异步安全点的前提下，一个持续占用 CPU 的 goroutine 通常会在约 10ms 量级收到抢占请求，但这不是硬 SLA。单次运行可能更短（撞到同步安全点），也可能更长（临界区/安全点未命中/sysmon 延迟）。

sysmon 与 spinning M

sysmon 是不绑定 P 的后台 M，不执行用户代码，因此在所有 P 忙碌或陷入系统调用时仍能工作。它负责：检查网络轮询器和长时间阻塞的系统调用；retake 长时间处于 syscall 的 P；请求抢占运行过久的 G；触发周期 GC、调度 trace 等后台动作；Go 1.25+ 周期性检查默认 GOMAXPROCS 是否应随容器 CPU 配额变化。它睡眠间隔动态调整，不是持续忙轮询。

当有 P 找不到工作时，runtime 允许少量 M 处于 spinning 状态继续寻找工作；如果全部立刻休眠，新 G 到来需要更昂贵的线程唤醒。反之，过多 spinning M 会浪费 CPU 并争抢同一批 P。

这套协议避免”先发布任务、后让最后一个搜索者休眠”之间的丢失唤醒，相关代码分散在 wakep/startm/stopm 和 findRunnable 中。

五、配置与边界

GOMAXPROCS 与容器 CPU 配额

P 的数量决定同一时刻最多有多少执行普通 Go 代码的执行上下文。Go 1.25 起，未被用户显式设置时，默认值会考虑逻辑 CPU、CPU affinity 和 Linux cgroup CPU 配额，并可动态更新。

sysmonUpdateGOMAXPROCS 的关键约束：

  • 程序显式调用 runtime.GOMAXPROCS 或显式配置时，runtime 不自动覆盖。
  • sysmon 读取外部限制后不能自己直接 STW；它唤醒辅助 G 完成 P 数量调整。
  • 修改 P 数量需要 procresize，会影响运行队列、timer、mcache 等 per-P 状态。

TIP

性能调优 不要机械地把 GOMAXPROCS 设为宿主机核数。容器中应优先验证默认行为，再结合 CPU 配额、节流指标、延迟和吞吐测量决定是否显式覆盖。

LockOSThread：G 与 M 的例外绑定

普通 G 可在不同 M 之间迁移。runtime.LockOSThread 会建立 lockedg/lockedm 双向关系，使当前 G 后续继续在同一 OS thread 上运行，适用于线程局部状态、GUI 主线程或特定系统 API。

代价是降低调度自由度；锁定的 G 阻塞时，runtime 可能需要额外 M 承载其他 P。每次 LockOSThread 必须匹配 UnlockOSThread，除非 goroutine 设计上永久占用该线程。

调度器不保证什么

  1. 不保证 goroutine 按创建顺序运行。
  2. 不保证 runnext 或 select 的严格公平性。
  3. 不保证每个 G 精确获得固定 10ms 时间片。
  4. 不保证 G 固定在同一个 P/M/CPU 上。
  5. 不保证 goroutine 退出时自动 join；需要显式 WaitGroup/Channel/Context 生命周期。
  6. 不保证增加 goroutine 或增大 GOMAXPROCS 就一定提升吞吐。

六、诊断与实践

schedtrace

GODEBUG=schedtrace=1000,scheddetail=1 ./app

重点观察 gomaxprocs、idle P、线程数、spinning threads、全局 runqueue 和各 P runqueue。它适合快速看整体失衡，但输出本身会有开销。

执行 trace

go test -trace=trace.out ./...
go tool trace trace.out

trace 可以回答：G 在哪个 P 上运行、何时被抢占/阻塞、系统调用持续多久、netpoll 何时唤醒、并行度为什么下降。

pprof

# goroutine 堆栈
curl -o goroutine.pb.gz http://127.0.0.1:6060/debug/pprof/goroutine

# 阻塞与锁竞争
curl -o block.pb.gz http://127.0.0.1:6060/debug/pprof/block
curl -o mutex.pb.gz http://127.0.0.1:6060/debug/pprof/mutex

Go 1.26 还提供实验性 goroutine 泄漏 profile：

GOEXPERIMENT=goroutineleakprofile go build ./cmd/app
curl -o leaks.pb.gz http://127.0.0.1:6060/debug/pprof/goroutineleak

它利用 GC 可达性识别一类永远无法解除的 Channel、Mutex、Cond 等等待；全局变量仍可达、或逻辑上”很久但可能恢复”的泄漏不一定能被判定。

调度器源码解释现象，但优化应从测量开始。大多数业务性能问题首先是工作量、锁竞争、I/O、分配或并行度设计问题，不应直接归因于”GMP 调度慢”。

总结

  1. G 保存 goroutine 的栈、寄存器上下文和生命周期状态；M 是 OS thread；P 是执行 Go 代码的许可与本地资源。
  2. GOMAXPROCS 决定 P 数，不限制 M 总数；Go 1.25+ 默认值可感知并动态适应容器 CPU 配额。
  3. 新 G 通常进入当前 P 的 runnext 或本地 256 槽运行队列，不会直接创建线程。
  4. 调度循环从本地/全局队列、GC、timer、netpoll 和其他 P 获取 G；空闲 P 通过 work stealing 均衡负载。
  5. runtime 可感知阻塞只 park G，M/P 可继续运行别的 G；阻塞系统调用则可能占住 M，P 可被 sysmon 回收；网络 I/O 走 netpoller，几个线程能扛几十万连接。
  6. 抢占同时使用同步安全点和基于信号的异步安全点；约 10ms 是 sysmon 请求抢占的阈值，不是严格时间片保证。
  7. 调度问题应使用 trace、schedtrace 和 pprof 建立证据，再决定是否调整并发结构或 GOMAXPROCS。
