GMP 调度器：Go 1.26.5 源码分析

Go 调度器解决的核心问题是：如何用较少的操作系统线程运行数量巨大的 goroutine，同时在阻塞、系统调用、网络 I/O、抢占和 GC 之间维持吞吐与延迟。G、M、P 不是三个抽象首字母，而是 runtime 中真实存在、长期复用的数据结构。

当前版本需要关注的变化

版本调度/runtime 相关变化
Go 1.1引入以 P 和 work stealing 为核心的新调度器
Go 1.14基于信号的异步抢占投入使用，纯计算循环也能被抢占
Go 1.21P 本地队列、netpoll、timer 等框架持续演进，GMP 基本模型保持稳定
Go 1.25默认 GOMAXPROCS 具备容器 CPU 配额感知，并可由 sysmon 周期性更新
Go 1.26Green Tea GC 默认启用；新增实验性 goroutineleak profile，可发现一类永久阻塞的 G

📝 GC 不是调度器，但两者高度耦合

P 持有分配缓存与 GC worker 状态，调度循环会优先运行 GC worker；STW、抢占和栈扫描也都需要调度器配合。因此理解 GMP 时不能完全绕开 GC。

通俗解释：把 runtime 想成一个车间

第一次读源码容易被 G、M、P、g0、runnext、netpoll、sysmon 这堆名词淹没。先用一个工厂车间的类比建立直觉，后面的章节再回到源码。

三个角色

  • G（goroutine） 是一张任务卡。写 go f() 就是往筐里扔一张卡。卡本身很轻（栈初始 2KB），所以能同时存在几十万张。
  • M（machine） 是工人，也就是 OS 线程。一个工人同一时刻只能干一张卡。
  • P（processor） 是工牌加工具台。没有工牌的工人只能干瞪眼，不能执行普通 Go 代码；工具台上挂着本地任务筐、内存分配缓存（mcache）、timer 等分片资源。

GOMAXPROCS=N 就是发 N 个工牌。工牌数量固定等于 GOMAXPROCS，工人数量按需增减，所以两边都可能出现不相等：

  • P > M（工牌比工人多）：活少。程序刚启动，或者大部分 goroutine 都阻塞着，runtime 不会傻养 N 个线程；没活的 M 回空闲池睡觉，P 挂在 sched.pidle 链表上等。比如 GOMAXPROCS=8 但只跑一个计算 goroutine，可能只有 1~2 个 M 醒着，其余 P 闲置。
  • M > P（工人比工牌多）：活被堵住。多个 M 同时卡在阻塞 syscall 上，runtime 为了不让 P 闲着，会唤醒或新建 M 来接 P；被堵住的 M 还活着但暂时没工牌。

关键边界有两条：

  1. 同一时刻最多 GOMAXPROCS 个 M 在执行普通 Go 代码，因为只有拿到 P 才能跑，而 P 就那么多。多余的 M 要么在 syscall、cgo，要么在 idle 池睡觉。
  2. M 总数有上限，由 runtime/debug.SetMaxThreads 控制（默认 10000），防止 cgo 阻塞之类的场景把线程数撑爆。

所以 G、M、P 三者数量没有”谁必须大于谁”的固定关系：G 可以几十万；P 永远等于当前 GOMAXPROCS（除非运行时调用 runtime.GOMAXPROCS 或容器配额变化触发 sysmonUpdateGOMAXPROCS）；M 在「需要的最少」到 10000 之间弹性浮动。

为什么要有 P，不直接 G 到 M

早期 Go 是 G-M 两层，所有工人抢一个全局任务筐，锁打到爆。加一层 P 等于把大筐拆成 N 个小筐挂在工牌上，大多数时候工人只摸自己面前的筐，几乎不加锁。

任务卡怎么流动

  1. go f()：新卡优先放进当前 P 的 runnext 槽（专门留给”刚被唤醒、缓存还热”的卡），筐满了才进本地 256 槽队列；本地队列再满，runqputslow 会把大约一半旧任务连新卡一起倒进中央大筐（全局队列）。
  2. 工人找活的顺序大致是：本地筐 → 全局大筐 → 帮 GC 干活 → 看 timer → 看网络就绪事件 → 去别的 P 筐里偷一半（work stealing） → 实在没活就睡，但留一两个工人”装睡”（spinning）等新卡，省掉线程唤醒开销。
  3. 偷一半是折中：偷少了要反复跑过来偷，偷多了又破坏人家的缓存局部性。

G 阻塞不等于工人卡住

这是最容易懵的地方，要分两种情况。

runtime 认识的阻塞（channel 收发、sync.Mutex、sync.Cond、timer、select）：

  • 走 gopark，当前 G 从工人手里摘下来，标记成 waiting，挂到那个 channel 或锁上。
  • 工人 M 拿着 P 立刻回筐里拿下一张卡。工人没有停。
  • 别人 ch <- x 时调 goready，把 waiting 的 G 改回 runnable，丢回某个 P 的队列。

系统调用阻塞（读文件、DNS、cgo）：

  • OS 线程真的会被内核挂起，runtime 喊不醒。
  • 进 syscall 前 M 把 P（工牌加工具台）交出来。M 堵在 read() 上时，别的空闲 M 或新 M 捡起这个 P 接着跑筐里的卡。
  • 这就是 M 数量可以超过 P 的原因：被堵在 syscall 上的 M 占着茅坑，但茅坑（P）已经让出来了。

网络 I/O 是第三种优化：runtime 用 epoll/kqueue/iocp 自己实现 netpoller。goroutine 等连接时只 park G，M 不进阻塞 syscall；epoll 报就绪后再把 G 唤醒。所以一个 Go 服务用几个线程就能扛几十万连接。

网络 I/O 详解：netpoller 怎么做到几个线程扛几十万连接

传统阻塞 IO 模型里，一个连接一个线程：accept() 后开线程，线程里 read() 等数据；没数据时整个 OS 线程被内核挂起。几万连接要几万线程，每线程栈 MB 级，内核调度和上下文切换都扛不住。事件循环（epoll + 回调）省线程，但代码被拆成状态机难写。Go 的做法是：用户代码写同步阻塞的 conn.Read(buf)，一个连接一个 goroutine，看着像一连接一线程；底层 runtime 集成 netpoller，让阻塞只停 G、不停 M，两边的好处都拿到。

底层流程：

  1. socket 被设成非阻塞。net.Dial/net.Listen 返回的 fd 底层都带 O_NONBLOCK。调 conn.Read(buf) 时实际执行 read(fd, buf)：有数据立刻返回；没数据内核返回 EAGAIN，不阻塞线程。
  2. EAGAIN 时把 G 挂到 pollDesc。每个网络 fd 绑一个 runtime.pollDesc，其中 rg/wd 记录等读/等写的 G。internal/poll.FD.Read 大致逻辑是：read 返回 EAGAIN 就调 runtime.netpollblock(pd, 'r')，内部用 gopark 把当前 G 改成 waiting、把 G 指针存进 pd.rg，然后 M 回调度器找别的 G 跑。M 没进阻塞 syscall，拿着 P 去执行别的 goroutine 了。
  3. epoll 在后台等。runtime 启动时起 netpoller，Linux 用 epoll、macOS/BSD 用 kqueue、Windows 用 IOCP、Solaris/AIX 用 event ports/pollset。所有等待的 socket 都注册进去；有一个不绑 P 的 M 真正阻塞在 epoll_wait 上（这是少数真正阻塞的 OS 线程之一）。
  4. 就绪事件把 G 改回 runnable。数据到了，epoll_wait 返回一批事件，netpoller 根据 fd 找到 pollDesc，从 rg/wd 取出之前挂着的 G，改成 runnable 放进就绪列表，再注入调度器（优先塞给空闲 P 的本地队列，没有就放全局队列）。那个 poller M 自己不执行业务 G，只卸货。
  5. G 被重新调度，Read 返回数据。某个 M+P 取到这个 G，从它被 park 的位置继续，也就是重新执行 read(fd, buf)；这次数据已在内核缓冲，直接返回。用户代码视角就是 conn.Read 阻塞了一段时间后返回，完全感知不到中间被切走。

findRunnable 里和 netpoll 有两个关键交互：

  • 每次找活开头先调一次非阻塞 netpoll(0)（epoll_wait 立即返回），顺手收割已就绪的 G。绝大多数就绪 G 不用等后台 poller，下一个找活的工人顺手带走，延迟极低。
  • 当本地/全局队列、偷任务、GC worker、timer 都没活时，P 在休眠前再做一次非阻塞 netpoll；如果整个系统都没活，会让一个 M 阻塞在 epoll_wait 上等待，避免空转烧 CPU。

为什么能扛几十万连接：每个等待中的连接只占一个 parked 的 G，初始栈 2KB 且等待期间不增长，10 万连接约几百 MB（加 socket 内核缓冲）；等待期间不占 M、不占 P、不参与调度；真正需要 M 的只有活跃连接；epoll 一个线程能等百万级 fd。典型服务的 M 数约等于 GOMAXPROCS 加几个 runtime 后台线程（sysmon、netpoller），再加少量被 syscall/cgo 堵住的 M。

几个边界：

  • 只有网络 fd 走 netpoller。Linux 上 epoll 对 regular file 永远报就绪，但磁盘读仍可能阻塞，这种 read 走的是 entersyscall 路径（M 与 P 解绑），不是 park G，所以磁盘 IO 重的服务 M 数会明显增多。
  • cgo 调用同理，会占住 M，不走 netpoller。
  • DNS 默认走纯 Go resolver，走 netpoll；CGO_ENABLED=1 且命中 cgo resolver 时那次查询会阻塞 M。
  • deadline（SetReadDeadline）是把 timer 和 pollDesc 联动，超时由 runtime 唤醒 G 并让 Read 返回 timeout 错误，不是真的中断 syscall。
  • Windows IOCP 模型不同（发起 overlapped 读写、完成后返回完成项），runtime 把它适配成同样的”G park → 完成后唤醒”抽象，用户代码不用区分。

类比：传统阻塞 IO 像每张桌配一个服务员站着等；事件循环像一个传菜员盯所有桌但所有逻辑都写成回调；Go netpoller 像每桌一张点菜单（G），客人没决定时菜单挂在厨房墙上（pollDesc + epoll），服务员去服务别的桌，菜好了取下菜单扔进出餐队列，任意空闲服务员接着上菜——菜单视角以为自己一直占着服务员，实际服务员只在真正干活时才来。

调度循环

每个工人的生活就是：

schedule() → findRunnable() → execute(g) → 跑用户代码
      ↑                                            │
      └────────── gopark / 阻塞 / 时间片到 ─────────┘

schedule 和 findRunnable 跑在 M 的 g0 系统栈上，不在用户 G 的栈上。execute 通过 gogo 切到 G 自己保存的栈和寄存器开始跑，跑累了再切回 g0 找下一张卡。所以调度器不是普通函数之间互相调用，而是栈和寄存器上下文的切换。

g0 系统栈是什么

每个 M 自带两块栈：

  • 用户 G 的栈：goroutine 跑业务代码用的，初始 2KB，按需扩缩，GC 扫栈时可能被整体复制到新地址。go f() 里的局部变量都在这上面。
  • g0 栈（系统栈）：M 出生时就在 OS 线程上分配好的一块栈，属于 M 自己，不属于任何用户 G。大小固定、不参与扩容、不被 GC 移动。

g0 不是用来跑业务函数的，是 runtime 干脏活的地方：调度、栈增长、信号处理、GC、defer/panic 的关键路径、cgo 切换。

为什么不能直接在用户 G 的栈上做这些事：

  1. 栈可能不够大。用户 G 栈最小 2KB，调度、GC、信号处理链路深、局部变量大，塞进去容易爆。g0 栈固定且足够大，不用担心。
  2. 用户栈会被 GC 搬家。goroutine 栈扩容时 runtime 会分配新栈、复制内容、改掉所有指针。调度器要是正跑在那块栈上，等于自己把自己脚下的地板抽走。g0 栈不参与栈复制，地址稳定。
  3. 切换 G 需要中立落脚点。从 G-A 切到 G-B 时，要先把 A 的寄存器存进 g.sched，再把 B 的寄存器恢复。这段代码不能跑在 A 或 B 任何一个的栈上——切走后那块栈就不属于当前执行流了。g0 提供这个中立地带。
  4. 信号必须落在已知安全的栈上。SIGSEGV、SIGURG（异步抢占）这类信号可能在用户栈任意指令处打断，如果信号处理函数也用那个栈，栈状态可能已经不一致。信号实际落在 M 的另一块独立系统栈 gsignal 上，必要时再切到 g0 进调度。

切换由两段汇编完成：mcall 从用户 G 栈切到 g0 栈，gogo 从 g0 切回某个用户 G 的栈和寄存器。整个过程只是换栈指针、保存恢复寄存器，不是普通函数调用。

类比：用户 G 栈像每张任务卡自带的折叠式小工作台，需要多大摊多大；g0 栈像工人自己腰上的工具腰带，永远在身上、不借人、不会变大变小。调度下一张卡、处理车间警报、切换工作台这些管理动作都在工具腰带上完成——不能在工件台上做，因为工件台随时可能被收走或搬走。

源码定位：m.g0 / m.gsignal 字段在 runtime2.go 的 m 结构体里；mcall、gogo 是 runtime/asm_amd64.s 中的汇编函数（其他架构对应 asm_*.s）。

抢占：不能让一张卡霸占工人

先说一个前提：抢占只针对此刻正跑在 M 上的 G（状态 _Grunning）。如果 G 在等 channel、锁、timer、网络、syscall，它已经是 _Gwaiting/_Gsyscall，M 早被调度器拿走给别的 G 用了，谈不上”抢”——它本来就没占着工人。真正的难题是：一个 G 正在 CPU 上死循环，runtime 怎么把它拽下来。

  • 同步抢占：编译器在每个函数序言插栈边界检查，大致是 CMP SP, g.stackguard0。stackguard0 平时存的是栈增长阈值；runtime 想抢占这个 G 时，把它改成特殊值 stackPreempt。下次函数调用执行到序言的 CMP 时必然命中，跳进 runtime.morestack，里面判断是抢占请求而非真的栈溢出，就转到 runtime.gopreempt → mcall(gosched) 主动挂起。问题在于：检查只在函数被调用的瞬间发生一次。for {} 里没有任何函数调用，CPU 一直在同一函数的循环体里转，序言代码根本不执行，哨兵永远不会被检测到。Go 1.14 以前这就是著名的调度器饿死问题，一个死循环能把一个 P 永久占住，连 GC STW 都过不去。
  • 异步抢占（Go 1.14+）：靠 OS 信号解决，流程：
    1. sysmon 扫描 P，发现某个 G 连续跑超过 forcePreemptNS（10ms），给它的 M 发 SIGURG（挑这个信号是因为几乎没别的程序用它）。
    2. 内核直接中断那个 M 上正在执行的指令，跳到 runtime 注册的信号处理函数 sighandler，此时 M 已切到独立的信号栈 gsignal 上执行。
    3. 信号处理函数拿被打断时的 PC 查 pclntab，判断这个指令地址是不是”异步安全点”——即此刻栈和寄存器里的指针能否被保守扫描识别。不是就跳过，等下一次信号。
    4. 是安全点就修改信号上下文 mcontext：把 PC 改成 runtime.asyncPreempt 的地址，把原来的 PC、SP 等压到用户栈上伪装成一次普通调用，然后从信号返回。
    5. M 恢复执行时”以为自己刚调用了 asyncPreempt”，后者把所有寄存器 spill 到栈上，调 asyncPreempt2 → mcall(gopreempt_m)，在 g0 上把当前 G 挂起，进 schedule 找下一个 G。
    6. 等这个 G 下次被调度回来，gogo 恢复它之前保存的寄存器和栈，PC 回到被信号打断的位置继续，就像什么都没发生。

编译器还配合做了一件事：在可能长时间循环的**回边（back edge）**通过 PCDATA 表标记异步安全点。所以即便 for {} 一个函数都不调，回边也会被打标，SIGURG 落在那里时就能被识别为安全点并抢走。这就是现在纯计算循环最多独占一个 P 约 10ms 的原因。

注意 forcePreemptNS = 10ms 是 sysmon 发起抢占请求的阈值，不是每个 goroutine 固定跑 10ms，也不是保证延迟。真正什么时候让，要等安全点、GC、syscall 和 OS 调度。

10ms 不是硬上限

容易误以为”每个 G 至多跑 10ms 就一定被切走”，实际不是。延迟来自几个地方：

  1. sysmon 不是精确 10ms 定时器。它在循环里动态 sleep：闲置时可睡到 ~10s，发现有 P 在跑 G 时才缩短到 ~10ms 粒度。判断条件是 pd.schedwhen + forcePreemptNS <= now，所以从 G 开跑到被发现超时，实际是 10ms 加上 sysmon 下一轮唤醒的延迟；机器忙、被宿主机调度拖慢时这个延迟会更大。
  2. 检测到不等于立刻抢走。sysmon 只是投递 SIGURG，真正停下 G 还要等信号处理：
    • 信号要等当前指令完成（某些 atomics、unsafe 窗口、持不可抢占锁的 runtime 代码不能立刻打断）。
    • 打断时的 PC 必须在异步安全点，不是就跳过这次信号，等 sysmon 下一轮重试。
    • G 若在 runtime 内部、持有 m.locks、跑在 g0 系统栈上、在 cgo、或在 malloc/GC 的某些阶段，canPreemptM 直接返回 false，抢占推迟到离开临界区。
  3. 同步抢占通常更早发生。普通 Go 代码几乎不可能一个函数都不调，函数序言会先撞到 stackPreempt，往往不到 10ms 就让出了。10ms 只是”纯计算无函数调用”这种最坏情况的兜底。

用 trace 观察 CPU 密集型 goroutine，单次连续运行时间一般分布在：几十微秒到几毫秒（撞到同步安全点或主动阻塞）；~10ms 附近（纯循环被异步信号抢走）；偶尔明显超过 10ms（runtime 临界区、安全点未命中、sysmon 被拖慢）。

另外要强调：Go 调度器不是按 vruntime 公平分配 CPU 的轮转调度器（不像 CFS）。

  • G 主动阻塞（channel、锁、syscall）时立刻让出，远比 10ms 早。
  • 取哪个 runnable G 有自己的偏好（runnext、本地队列优先、work stealing 偷一半），不保证轮转公平。
  • 没有”时间片用完必须轮到别人”的保证：G 被抢占后重回队列，理论上可能马上又被同一个 P 取走继续跑。

更准确的说法是：在用户代码、非 runtime 临界区、且能找到异步安全点的前提下，一个持续占用 CPU 的 goroutine 通常会在约 10ms 量级收到抢占请求，但这不是硬 SLA。实际单次运行可能更短（撞到同步安全点），也可能更长（临界区/安全点未命中/sysmon 延迟）。

sysmon：不拿工牌的保安

一个不绑定 P 的后台 M，不执行用户代码，负责：

  • 回收堵在 syscall 上太久的 P（retake）
  • 给跑太久的 G 发抢占
  • 轮询网络、触发周期 GC
  • Go 1.25 起周期性检查 cgroup CPU 配额，按需调整默认 GOMAXPROCS

它睡眠间隔会动态调整，不是死循环烧 CPU。

几个反直觉但重要的点

  1. GOMAXPROCS=1 不是只有一个线程，也不是没有并发。netpoll、syscall、cgo 都可能让 runtime 多开 M，只是同一时刻只有一个 M 跑普通 Go 代码。
  2. goroutine 不保证按创建顺序执行，runnext、select 也不保证严格公平。
  3. go f() 通常不创建新线程，只是把 G 塞进当前 P 的队列，极端情况才唤醒或新建 M。
  4. G 会被复用：goroutine 退出后 g 结构体进空闲池，下次 go 直接拿来装新任务。
  5. runtime.LockOSThread 把当前 G 和 M 焊死，用于 GUI 主线程、OpenGL context、某些 thread-local 要求；代价是这对组合调度器动不了，必须配对 UnlockOSThread（除非设计上永久占用）。

G、M、P 分别是什么

G：goroutine 的运行时描述

g 不等于“函数”。它保存一个 goroutine 从创建到退出所需的运行状态：

G 对象会复用：goroutine 退出后，其 g 进入空闲池，未来可代表另一个 goroutine。G 的用户栈起始很小，按需增长或收缩；运行时还会扫描它来寻找 GC root。

M：操作系统线程

m 是 machine，即 OS thread 的 runtime 表示：

M 可以没有 P，例如阻塞在系统调用、执行 cgo 或处于空闲线程池。M 的数量不等于 GOMAXPROCS；大量系统调用可以让 runtime 创建更多 M，但只有拿到 P 的 M 才能执行普通 Go 代码。

P：执行权与每 P 资源

p 是 processor。它不是 CPU 核心，也不是线程，而是执行用户 Go 代码所需的许可和一组分片资源：

P 的数量等于当前 GOMAXPROCS。把常用调度、分配和 timer 状态放在 P 上，可以让多数操作使用本地分片，减少全局锁竞争。

三者如何组合

可以把关系简化为：

  • G 提供“要运行什么”。
  • M 提供“在哪里运行”，即 OS 执行上下文。
  • P 提供“运行 Go 代码的权利和本地资源”。
  • 调度器持续匹配三者，而不是把 G 永久绑定给某个 M 或 P。

⚠️ 常见误解

GOMAXPROCS=1 不是只有一个 M，也不是程序没有并发；它只限制同时执行普通 Go 代码的 P 数量为 1。阻塞系统调用、runtime 线程和 cgo 仍可能存在多个 M。

创建 goroutine：从 go f() 到 _Grunnable

编译器把 go f(args) 变成对 runtime 创建入口的调用；当前主体是 newproc/newproc1：

新 G 的初始 PC 被安排到 goexit 包装后的入口，使用户函数返回后必然进入 runtime 的 goroutine 退出清理。创建 goroutine 不等于马上新建 OS 线程；通常只是分配/复用 G 并把它放入当前 P 的本地队列。

运行队列：局部性、全局公平与 work stealing

队列层次

  • runnext 适合刚刚被当前 G 唤醒、很可能共享缓存的 G；它继承当前时间片。
  • 本地 runq 容量 256，owner P 从头取、尾部写；窃取者通过原子操作从头部批量取得。
  • 本地队列满时，runqputslow 把约一半旧任务加上新任务批量放到全局队列。
  • 全局队列由 sched.lock 保护；取任务时会按 runqsize/gomaxprocs+1 批量分给本地 P，见 globrunqgetbatch。

Work stealing

空闲 P 不会立刻休眠；findRunnable 会综合检查本地/全局队列、GC worker、timer、netpoll，并尝试从其他 P 窃取工作。

runqsteal 通常窃取 victim P 可运行队列的大约一半，把多数任务留在自己的本地队列并返回一个立即执行：

窃取一半是在负载均衡开销与缓存局部性之间折中；如果每次只偷一个，空闲 P 会频繁扫描。

调度循环：schedule → findRunnable → execute

schedule 运行在 M 的 g0 系统栈上：

execute 会把 G 绑定到 M、更新状态和时间片，再通过 gogo 恢复 g.sched 中保存的寄存器上下文。调度器不是普通 Go 函数之间递归调用，而是在用户栈和 g0 系统栈之间切换。

阻塞与唤醒：为什么 G 阻塞不等于线程阻塞

Channel、Mutex、Cond、timer 等 runtime 可感知的阻塞会走 gopark：

ready 把 waiting G 改为 runnable 并入队；它不是直接让目标 G 在当前线程上继续执行。Channel 的完整阻塞链见 Channel（Go 1.26.5 源码分析）。

系统调用：M 可以被占住，P 必须继续流动

系统调用可能让 OS thread 长时间阻塞。runtime 用 _Gsyscall / _Psyscall 记录它，并允许 P 被其他 M 接管：

入口和返回路径见 entersyscall/exitsyscall。这解释了为什么 M 数量可能超过 P：被系统调用占住的 M 暂时不能执行其他 G，但它原来的 P 可以继续服务。

网络轮询器：少量线程等待大量 fd

网络 I/O 不会为每个连接长期占一条线程。runtime netpoller 把等待 fd 的 G 停在 poll descriptor 上，OS 多路复用器报告就绪后再把 G 变为 runnable：

公共逻辑位于 runtime/netpoll.go，平台文件负责具体 OS 接口。findRunnable 会用非阻塞 netpoll 检查就绪事件；所有 P 即将空闲时，也可由一个 M 阻塞在 netpoll 等待。

抢占：协作安全点与异步安全点

Go 1.26 的抢占设计在 preempt.go#L5-L51 明确区分三类安全点：

安全点场景做法
blocked safe-pointG 已阻塞、在同步原语或系统调用中本来就不在执行用户代码
synchronous safe-point函数序言检查栈边界把 stackguard0 设为 stackPreempt，下次检查转入抢占
asynchronous safe-point用户代码中的可安全暂停指令向 M 发 OS 信号，修改上下文进入 asyncPreempt

retake 当前使用约 10ms 的 forcePreemptNS 判断同一调度时间片是否过长。10ms 不是 goroutine 保证执行时长，也不是固定轮询周期；调度仍受安全点、系统调用、GC、OS 调度和负载影响。

sysmon：没有 P 的后台监督线程

sysmon 不绑定 P，因此在所有 P 忙碌或陷入系统调用时仍能工作。它负责或参与：

  • 检查网络轮询器和长时间阻塞的系统调用。
  • retake 长时间处于 syscall 的 P。
  • 请求抢占运行过久的 G/时间片。
  • 触发周期 GC、调度 trace 等后台动作。
  • Go 1.25+ 周期性检查默认 GOMAXPROCS 是否应随容器 CPU 配额变化。

sysmon 的休眠间隔会动态调整，它不是持续忙轮询。

Spinning M：避免频繁休眠与惊群

当有 P 找不到工作时，runtime 允许少量 M 处于 spinning 状态继续寻找工作；如果全部立刻休眠，新 G 到来需要更昂贵的线程唤醒。反之，过多 spinning M 会浪费 CPU 并争抢同一批 P。

这套协议试图避免“先发布任务、后让最后一个搜索者休眠”之间的丢失唤醒，相关代码分散在 wakep/startm/stopm 和 findRunnable 中。

GOMAXPROCS 与容器 CPU 配额

P 的数量决定同一时刻最多有多少执行普通 Go 代码的执行上下文。Go 1.25 起，未被用户显式设置时，默认值会考虑逻辑 CPU、CPU affinity 和 Linux cgroup CPU 配额，并可动态更新。

sysmonUpdateGOMAXPROCS 的关键约束：

  • 如果程序显式调用 runtime.GOMAXPROCS 或显式配置，runtime 不自动覆盖。
  • sysmon 读取外部限制后，不能自己直接 STW；它唤醒辅助 G 完成 P 数量调整。
  • 修改 P 数量需要 procresize，会影响运行队列、timer、mcache 等 per-P 状态。

💡 性能调优

不要机械地把 GOMAXPROCS 设为宿主机核数。容器中应优先验证默认行为，再结合 CPU 配额、节流指标、延迟和吞吐测量决定是否显式覆盖。

LockOSThread：G 与 M 的例外绑定

普通 G 可在不同 M 之间迁移。runtime.LockOSThread 会建立 lockedg/lockedm 双向关系，使当前 G 后续继续在同一 OS thread 上运行，适用于线程局部状态、GUI 主线程或特定系统 API。

代价是降低调度自由度；锁定的 G 阻塞时，runtime 可能需要额外 M 承载其他 P。每次 LockOSThread 必须匹配 UnlockOSThread，除非 goroutine 设计上永久占用该线程。

调度器不保证什么

  1. 不保证 goroutine 按创建顺序运行。
  2. 不保证 runnext 或 select 的严格公平性。
  3. 不保证每个 G 精确获得固定 10ms 时间片。
  4. 不保证 G 固定在同一个 P/M/CPU 上。
  5. 不保证 goroutine 退出时自动 join；需要显式 WaitGroup/Channel/Context 生命周期。
  6. 不保证增加 goroutine 或增大 GOMAXPROCS 就一定提升吞吐。

调度器初始化

程序启动会先在系统栈执行 schedinit，初始化锁、栈、内存分配器、GC、CPU 特征、随机数、P 等 runtime 子系统。

procresize 必须在 STW 下调整 P 数量，初始化新增 P 的本地资源，并把不再使用 P 上的 runnable G 迁移到可继续调度的位置。

G 的状态机

主要状态定义在 runtime2.go：

_Gscan 是叠加在基础状态上的 GC 扫描位，不是普通独立生命周期状态。状态迁移必须通过 runtime 的原子/CAS 辅助函数完成，调度器、GC 和栈复制都依赖这些不变量。

诊断调度问题

schedtrace

GODEBUG=schedtrace=1000,scheddetail=1 ./app

重点观察 gomaxprocs、idle P、线程数、spinning threads、全局 runqueue 和各 P runqueue。它适合快速看整体失衡，但输出本身会有开销。

执行 trace

go test -trace=trace.out ./...
go tool trace trace.out

trace 可以回答：G 在哪个 P 上运行、何时被抢占/阻塞、系统调用持续多久、netpoll 何时唤醒、并行度为什么下降。

pprof

## goroutine 堆栈curl -o goroutine.pb.gz http://127.0.0.1:6060/debug/pprof/goroutine

## 阻塞与锁竞争curl -o block.pb.gz http://127.0.0.1:6060/debug/pprof/block
curl -o mutex.pb.gz http://127.0.0.1:6060/debug/pprof/mutex

Go 1.26 还提供实验性 goroutine 泄漏 profile：

GOEXPERIMENT=goroutineleakprofile go build ./cmd/app
curl -o leaks.pb.gz http://127.0.0.1:6060/debug/pprof/goroutineleak

它利用 GC 可达性识别一类永远无法解除的 Channel、Mutex、Cond 等等待；全局变量仍可达、或逻辑上“很久但可能恢复”的泄漏不一定能被判定。

从业务代码看调度器

调度器源码解释现象，但优化应从测量开始。大多数业务性能问题首先是工作量、锁竞争、I/O、分配或并行度设计问题，不应直接归因于“GMP 调度慢”。

总结

  1. G 保存 goroutine 的栈、寄存器上下文和生命周期状态；M 是 OS thread；P 是执行 Go 代码的许可与本地资源。
  2. GOMAXPROCS 决定 P 数，不限制 M 总数；Go 1.25+ 默认值可感知并动态适应容器 CPU 配额。
  3. 新 G 通常进入当前 P 的 runnext 或本地 256 槽运行队列，不会直接创建线程。
  4. 调度循环从本地/全局队列、GC、timer、netpoll 和其他 P 获取 G；空闲 P 通过 work stealing 均衡负载。
  5. runtime 可感知阻塞只 park G，M/P 可继续运行别的 G；阻塞系统调用则可能占住 M，P 可被 sysmon 回收。
  6. 抢占同时使用同步安全点和基于信号的异步安全点；约 10ms 是 sysmon 请求抢占的阈值，不是严格时间片保证。
  7. 调度问题应使用 trace、schedtrace 和 pprof 建立证据，再决定是否调整并发结构或 GOMAXPROCS。
