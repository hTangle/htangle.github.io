Ranking：从候选集合到最优顺序

[!abstract] 一句话定义 **Ranking 是根据查询、候选、用户和场景信号，为候选计算效用并生成最优顺序的过程。**它在有限展示位或 Context 预算中，把最有价值、最可信的结果放到前面。

Retrieval - 从大规模信息中找到候选 解决“可能相关的有哪些”，Ranking 解决“先看谁”。在 RAG - 从检索到可信生成的完整系统 中，排序不仅影响用户点击，也决定模型最终看见哪些证据，因此一次排序错误可能直接变成一次无依据回答。

1. 排序不是一个 score 字段

生产排序通常是漏斗，而不是单模型：

每一层有不同预算：

层目标常见模型约束
召回打分低成本覆盖BM25、双塔、规则毫秒级、大候选
粗排快速淘汰明显无关项线性模型、GBDT、轻量网络特征可批量获取
精排深度理解 query-documentCross-Encoder、LLM rerankerGPU、批处理、超时
策略重排满足产品与安全约束规则、MMR、去重可解释、可审计

2. 相关性分数的来源

一个简化排序目标可以写成：

Score(d∣q,u,c)=wrR(q,d)+wfF(d)+waA(d)+wpP(u,d)+wbB(d,c)Score(d|q,u,c)= w_rR(q,d)+w_fF(d)+w_aA(d)+w_pP(u,d)+w_bB(d,c)Score(d∣q,u,c)=wr​R(q,d)+wf​F(d)+wa​A(d)+wp​P(u,d)+wb​B(d,c)
  • RRR：文本或语义相关性；
  • FFF：新鲜度；
  • AAA：权威度/质量；
  • PPP：个性化；
  • BBB：业务或场景效用。

难点不在写出加权和，而在：各信号如何标定、标签如何获得、约束如何表达、线上分布变化后是否仍有效。

3. BM25 与向量分数不能直接相加

BM25 没有固定上界，cosine 通常位于有限区间，dot product 又受向量模长影响。下面这种写法常造成静默错误：

final_score = 0.5 * bm25_score + 0.5 * cosine_score

“0.5”不表示两个通路贡献相等。可选方案：

  • min-max、z-score 或分位数归一化，但要处理查询间分布差异；
  • 在标注集上学习融合权重；
  • 只用名次做 RRF；
  • 分查询意图采用不同融合策略。

RRF：

RRF(d)=∑r∈R1k+rankr(d)RRF(d)=\sum_{r\in R}\frac{1}{k+rank_r(d)}RRF(d)=r∈R∑​k+rankr​(d)1​

RRF 稳定、易回滚；学习融合上限更高，但需要可靠标签和漂移监控。

4. Bi-Encoder、Late Interaction 与 Cross-Encoder

架构交互方式可预计算质量/成本典型位置
Bi-Encoderquery/document 各自编码文档可快、细粒度交互弱召回
Late Interactiontoken 表示延后交互文档部分可中等高质量检索/粗排
Cross-Encoderquery 与 document 联合编码不可准、昂贵Top-N 精排
LLM Reranker指令化比较或打分不可语义强、延迟和稳定性风险高小候选精排

Cross-Encoder 能看到词序、否定和细粒度对应关系，但成本近似随候选数线性增加。生产上要控制：候选长度、批大小、动态 batching、最大等待时间、GPU 饱和度和 fallback。

5. Learning to Rank：学的不是分类，而是顺序

5.1 Pointwise

把每个 query-document 当独立样本，预测相关性或点击概率。实现简单，但目标与“列表顺序”不完全一致。

5.2 Pairwise

学习同一查询下 d+d^+d+ 应排在 d−d^-d− 前：

Lpair=log⁡(1+e−(s(q,d+)−s(q,d−)))\mathcal{L}_{pair}=\log(1+e^{-(s(q,d^+)-s(q,d^-))})Lpair​=log(1+e−(s(q,d+)−s(q,d−)))

更贴近顺序，但没有直接区分榜首交换与榜尾交换的价值。

5.3 Listwise

直接基于整张列表和排名指标优化。LambdaRank/LambdaMART 用名次交换对 nDCG 的影响来调节梯度，能让顶部位置获得更合理的优化权重。

IMPORTANT

标签问题往往比模型问题更大 点击、停留时长、采纳和转化都受位置、曝光、UI、品牌以及推荐策略影响。没有偏差校正时，模型容易学会“过去排得高的继续排高”。

6. 特征工程与泄漏

生产排序特征通常分为：

  • Query：语言、意图、长度、实体、时间敏感度；
  • Document：质量、权威性、发布时间、流行度、类型；
  • Cross：词项匹配、语义相似、实体重合、查询-文档交互；
  • User/Context：权限、角色、历史偏好、设备、地区；
  • System：召回通路、原始 rank、索引版本。

特征必须满足 point-in-time correctness。用“点击后才生成的数据”训练点击前排序，就是标签泄漏。离线训练与在线服务还要避免 training-serving skew：同名特征的计算逻辑、时区、缺失值和版本必须一致。

7. Freshness、Authority 与 Relevance 的冲突

最新不一定最权威，权威不一定回答当前版本。可采用：

  • 时间衰减：freshness=e−λΔtfreshness=e^{-\lambda \Delta t}freshness=e−λΔt；
  • 查询意图触发：只有“最新、当前版本”等意图增强时效；
  • 文档有效期：valid_from / valid_to；
  • 权威源白名单与冲突标记；
  • 对旧版本文档做版本过滤，而不是只靠降权。

在技术知识库中，“v1 的高权威文档”不能因为质量高就压过“v2 的当前文档”。版本是硬约束还是软特征，需要产品明确。

8. 去重与多样性

Top-K 被同一文档的相邻 Chunk 占满，会浪费 Context。常见措施：

  • URL/document ID 去重；
  • 文本指纹或 embedding 相似度近重复去重；
  • 每个来源、文档、实体设置 quota；
  • MMR（Maximal Marginal Relevance）平衡相关与新颖：
MMR(d)=λSim(q,d)−(1−λ)max⁡s∈SSim(d,s)MMR(d)=\lambda Sim(q,d)-(1-\lambda)\max_{s\in S}Sim(d,s)MMR(d)=λSim(q,d)−(1−λ)s∈Smax​Sim(d,s)

但去重不能损害多证据完整性：同一文档的“配置方法”和“回滚限制”可能都是必要证据。应基于证据单元，而非简单一文档只留一条。

9. 业务规则要与相关性模型分层

置顶、合规下架、广告、来源配额和多样性属于策略层。推荐：

  • 模型输出相关性/效用分数；
  • 策略引擎执行硬约束和可审计规则；
  • 最终结果记录每次升降位原因；
  • 规则配置版本化、有有效期、有 owner；
  • 紧急关闭开关可独立于模型发布。

把大量隐式业务规则塞进模型特征，会使问题难解释、难回滚，也很难回答“为什么这条结果排第一”。

10. 排序评估指标

10.1 MRR

关注第一个相关结果：

MRR=1∣Q∣∑q∈Q1rankqMRR=\frac{1}{|Q|}\sum_{q\in Q}\frac{1}{rank_q}MRR=∣Q∣1​q∈Q∑​rankq​1​

适合只需一个正确答案的导航型查询。

10.2 DCG 与 nDCG

DCG@K=∑i=1K2reli−1log⁡2(i+1),nDCG@K=DCG@KIDCG@KDCG@K=\sum_{i=1}^{K}\frac{2^{rel_i}-1}{\log_2(i+1)},\qquad nDCG@K=\frac{DCG@K}{IDCG@K}DCG@K=i=1∑K​log2​(i+1)2reli​−1​,nDCG@K=IDCG@KDCG@K​

nDCG 支持等级相关性，并强调顶部位置。若问题需要多个证据，还应补充 evidence-set coverage。

10.3 线上指标

  • CTR、长点击、改写率、任务完成率；
  • RAG 答案正确率、证据支持率、引用采纳率；
  • 零结果与无答案率；
  • p95/p99、超时率、fallback 率；
  • 每次查询 GPU 时间与成本。

离线 nDCG 上升不保证线上价值上升。线上指标也可能被 UI 或位置偏差污染，两者必须闭环。

11. Offline、Shadow、A/B 与 Interleaving

  • Offline：快速筛掉明显退化，适合大量实验；
  • Shadow：验证服务容量、候选差异和模型稳定性；
  • Canary：控制故障半径，关注 p99、超时和安全约束；
  • A/B：测真实用户与任务指标；
  • Interleaving：把两套排序交织展示，更敏感比较偏好，但实现和解释更复杂。

发布必须明确 guardrail：ACL 违规、错误率、p99、成本、关键切片 nDCG 任一越界即自动降级或回滚。

12. 服务化与容量设计

Cross-Encoder 排序服务的主要杠杆：

  • 截断 query 和 document 长度；
  • 按 token 数做动态 batching，而非只按样本数；
  • 限制最大 batch 等待，避免低流量时反而延迟高；
  • 对相同 query-document-version 缓存，但缓存键包含模型版本；
  • CPU 轻量模型作为 GPU 故障 fallback；
  • 设置候选上限、超时和 partial result 语义；
  • 模型加载、warmup、显存和 OOM 独立监控。

粗略成本：

Compute∝QPS×Candidates×Tokens×ModelCostCompute \propto QPS\times Candidates\times Tokens\times ModelCostCompute∝QPS×Candidates×Tokens×ModelCost

把候选从 50 提到 200 可能让 Recall 略升，却让精排成本近四倍。必须看端到端 Pareto 曲线。

13. 降级设计

排序服务不是“要么全好，要么报错”。建议降级链：

  1. 主 Cross-Encoder；
  2. 轻量 reranker；
  3. RRF 或已校准的检索分数；
  4. 单路检索原始名次；
  5. 明确无结果/暂不可用。

每次响应应记录实际走到哪级。否则主服务长期超时、系统一直 fallback，业务表面可用但质量已经静默下降。

14. 高频生产事故

14.1 分数融合后某一路永远胜出

根因：不同分数尺度直接加权，或模型升级后分布漂移。
处理：查看分通路 score histogram、名次贡献，先切 RRF 稳住，再重做校准。

14.2 Reranker 超时但接口仍是 200

Fallback 吞掉错误，质量下降未告警。应把 ranking_tier、timeout、fallback_reason 写入 trace，并为 fallback rate 建 SLO。

14.3 离线效果很好，线上热门内容越来越热门

点击训练产生 position/popularity feedback loop。加入探索流量、偏差校正、时间切分验证与内容多样性约束。

14.4 Top-K 都是同一文档的相邻 Chunk

粗粒度去重和 MMR 可改善，但先确认下游是否需要同文档多证据。记录 document_id 与 section path 是前提。

14.5 新模型只让平均指标上升

代码查询、非英语、低频租户可能显著退化。上线门槛应包含关键切片不退化约束，而非只看 overall nDCG。

15. 可观测性设计

每次排序 trace 建议包含：

query_id: q_123
retrieval_version: hybrid_v7
ranker_version: ce_v12
policy_version: policy_2026_08
candidate_count: 180
reranked_count: 50
ranking_tier: primary
latency_ms:
  feature_fetch: 8
  inference: 37
  policy: 2
top_results:
  - document_id: doc_42
    retrieval_rank: 17
    final_rank: 1
    score: 0.91
    reason_codes: [semantic_match, current_version]

正文、敏感特征和用户身份应脱敏；但版本、阶段耗时、名次变化和 reason code 必须可诊断。

16. 上线清单

  • 候选召回与排序责任边界清楚
  • 分数融合做过标定，或使用可解释的 RRF
  • 训练标签考虑曝光和位置偏差
  • 特征满足 point-in-time correctness
  • 去重/多样性不会破坏多证据完整性
  • 离线指标覆盖关键业务切片
  • shadow、canary、A/B 和回滚路径齐备
  • GPU 容量、batch、超时和 fallback 有 SLO
  • 每次响应能追踪 ranker/policy 版本与降级层级

17. 高级工程师面试题

[!question] - 为什么精排不能解决低 Recall？ 精排只能重排已有候选，正确文档不在候选集合中就没有机会。应追踪 gold evidence 在每层的生存率，先解决召回缺口。

[!question] - Pointwise、Pairwise、Listwise 怎么选？ Pointwise 简单且易使用绝对标签；Pairwise 直接学习偏序；Listwise 更贴近 nDCG 等列表指标但训练复杂。选择取决于标签形态、规模、解释要求和线上目标，工程上 GBDT/LambdaMART 仍常用于结构化特征。

[!question] - Cross-Encoder 如何控制线上成本？ 先用高召回+轻粗排缩小候选，限制输入长度，按 token 动态 batching，缓存稳定候选，设置超时和多级 fallback，并基于质量-延迟-成本曲线选择候选数。

[!question] - 如何判断排序模型学到了位置偏差？ 比较随机或探索流量数据，按历史曝光位分层评估，检查位置特征移除后的变化；可用逆倾向加权、随机化实验或 interleaving 获得更可靠偏好。

[!question] - RAG 排序与网页搜索排序有什么不同？ RAG 的消费者是模型，除单项相关性外还要优化证据互补、可引用性、权威与 token 预算。重复的高分 Chunk 可能对网页展示尚可，却会挤占 Context 并降低生成质量。

19. 与 Memory、Retrieval、Recall、RAG 的对比

概念决策对象典型输出失败后果
Memory - Agent 如何记住、更新与遗忘哪些状态长期保存及何时更新记忆项及其版本Agent 稳定记错、越权或过时
Retrieval - 从大规模信息中找到候选去哪里、用什么方式找无序或粗排候选正确结果未进入候选
Recall - 召回阶段与 Recall@K 指标候选覆盖是否足够覆盖指标和缺口对漏检没有正确认知
Ranking候选应按什么顺序出现有序结果与分数正确证据被噪声挤出顶部
RAG - 从检索到可信生成的完整系统如何用外部证据生成回答答案、引用和证据链无依据、错误引用或不完整答案

一条清晰的责任链是：Retrieval 提供“可选集合”，Recall 衡量集合完整度，Ranking 压缩为“最值得看的顺序”，RAG 再把顶部证据装配给模型；Memory 则为其中一部分长期状态提供来源。
