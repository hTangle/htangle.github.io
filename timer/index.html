定时器：Go 1.26.5 源码分析

Go 的定时器不是一个独立线程在”数时间”，而是把到期事件分散挂在每个 P 自己的最小堆上，由调度器在找活时顺手检查、由 netpoller 的超时来兜底唤醒。这样既没有全局锁竞争，也不会为了等定时器空烧 CPU。

TIP

  1. 每个 P 有一个 runtime.timers，内部是按 when（到期时间）排序的四叉最小堆，堆顶是最近要触发的那个。
  2. time.After、time.Tick、Timer、Ticker、time.Sleep、context 超时，底层都是同一个 runtime.timer。
  3. 定时器不靠专门的计时线程到点触发，而是靠两处驱动：
    • 调度器在 findRunnable 里调 checkTimers/runTimer，有活干时顺手把到期的跑了；
    • netpoller 阻塞 epoll_wait 时，把”最近一个定时器的到期时间”作为超时传进去，没人唤醒它时时间到了也会自己醒。
  4. time.Timer.C / Ticker.C 从 Go 1.23 起对用户表现为同步、无缓冲 channel：Stop/Reset 之后不会再收到旧配置的过期值，且没引用的定时器可以被 GC 回收。

一句话：定时器是挂在 P 堆上的到期回调，调度器和 netpoll 各负责一种唤醒路径。

结论先行

  • 运行时架构主线没变：每 P 一个四叉最小堆，与调度器、netpoll 协同触发。
  • 内部状态从 Go 1.14 的 10 个枚举状态，精简为 Go 1.26.5 的 3 个可组合位（timerHeaped/timerModified/timerZombie）。
  • Go 1.23 重做了 channel timer：Timer.C/Ticker.C 对用户呈同步语义；Stop/Reset 无旧值泄漏；未引用的定时器可被 GC。
  • Go 1.25 起 testing/synctest 提供虚拟时钟，测超时代码不再需要真实 Sleep。
  • Go 1.26 保留 GODEBUG=asynctimerchan 兼容旧行为，Go 1.27 将移除该开关。

数据结构：每 P 一个四叉堆

Go 1.26.5 在每个 P 上维护一个 runtime.timers：

// 简化自 src/runtime/time.go
type timers struct {
    mu              mutex
    heap            []timerWhen
    len             atomic.Uint32
    zombies         atomic.Int32
    minWhenHeap     atomic.Int64
    minWhenModified atomic.Int64
    // ...
}

type timerWhen struct {
    timer *timer
    when  int64
}

const timerHeapN = 4
  • 堆是 4 叉树：插入/删除是 $O(\log_4 n)$，比二叉堆层数少、对缓存更友好。
  • heap[0] 是最早到期的定时器。
  • minWhenHeap 缓存堆顶时间，minWhenModified 记录”被改期到更早”的下界，调度器可先原子读这两个字段走快路径，不必每次加锁扫堆。
  • zombies 统计留在堆里、但已标记删除的定时器；超过当前 P 定时器数的 1/4 时强制清理，避免僵尸长期占内存。

单个定时器是 runtime.timer，用一把自身锁保护：

type timer struct {
    pp     puintptr    // 所属 P
    when   int64      // 到期时间
    period int64      // 周期（Ticker > 0，Timer = 0）
    f      func(any, uintptr)  // 到期回调
    arg    any
    seq    atomic.Uint64

    isSending uint32     // channel timer 发送状态
    sendTime  atomic.Int64
    nextWhen  int64

    // 状态位
    status uint8
}

状态机：3 个可组合位

Go 1.26.5 不再用 10 个互斥的枚举状态，而是三个可组合的标志位：

const (
    timerHeaped   uint8 = 1 << iota // 已挂在某个 P 的堆里
    timerModified                  // when 被改过，堆中快照待调整
    timerZombie                    // 已停止，等待从堆中清理
)
  • Heaped：这个 timer 已经在某个 P 的堆中（或刚被取出正在跑）。
  • Modified：用户调了 Reset 改了 when，但堆里的位置还没重新调整；下次 checkTimers 会处理。
  • Zombie：Stop 之后，逻辑上已死，但仍占着堆位置，等待清理或被惰性摘除。

位可组合，例如”在堆里且被改过”就是 timerHeaped|timerModified。状态变迁由 timerModifiedEarlier、timerModifiedLater、timerDeleted 等内部函数完成。判断一个定时器是否还有效、要不要触发，都是对这几个位的组合检查，而不是 switch 十个状态。

NOTE

为什么不用旧的 10 态 旧实现把”在堆里、正在跑、被修改、被删除、正在删除”等都编码成互斥枚举，代码里到处是状态转换表，边界 case 多。用 3 个独立位后，状态语义正交，删除/改期/触发并发交错时更容易推理正确性。

time.Timer 与 time.Ticker 的当前语义

Go 1.23 之后：同步、无缓冲 channel

行为Go 1.22 及以前Go 1.23+ 新语义
Timer.C / Ticker.C容量 1 的异步 channel对用户呈容量 0 的同步 channel
Stop 返回后仍可能读到旧值，要手动 drain之后不会再读到旧值
Reset 返回后可能读到上一次配置的值之后不会再读到旧配置的值
未触发、未 Stop 的 Timer触发前无法回收无引用即可被 GC
未 Stop 的 Ticker无法回收无引用即可被 GC
time.After / time.Tick长循环里有泄漏风险不再仅为 GC 改写成 NewTimer/NewTicker
// Go 1.23+：不需要 Stop 后 drain channel
timer := time.NewTimer(timeout)
defer timer.Stop() // 取消业务触发用，不是为了帮 GC

for {
    select {
    case item := <-work:
        handle(item)
        timer.Reset(timeout)
    case <-timer.C:
        return
    }
}

源码里 NewTimer 仍 make(chan Time, 1) 是为了 asynctimerchan 兼容路径；默认新语义下 runtime 用同步发送，用户视角 len/cap 都为 0。不要用 len(t.C) 轮询，用非阻塞 select。

Stop 与 Reset

  • Timer.Reset 的返回值表示重置前定时器是否仍活动，不是”重置成功与否”。
  • AfterFunc 的 timer 没有 channel（C == nil）；对已触发的 AfterFunc 调 Reset 会再跑一次 f，新旧两次 f 可能并发，需要外部同步。
  • Ticker.Stop 不关闭 Ticker.C：for range ticker.C 不会因为 Stop 而退出，要另监听 ctx.Done() 或退出信号。
  • Ticker 消费慢时，runtime 会跳过错过的 tick，不保证每个周期都投递。

惰性入堆与 GC

Go 1.23+ 的 channel timer 知道自己是否有人在接收。没人等的 timer 可以从堆里移出，有接收者阻塞时才入堆。这是”未 Stop 也能被 GC”的关键——没有 goroutine 引用 timer 时，它不会被堆引用，GC 可以回收。

触发路径：调度器 + netpoll 两条腿

定时器不是”到点自己跳出来”，而是被两处代码检查并执行：

1. 调度器路径：findRunnable 在找可运行 G 之前，会调 checkTimers → runTimer，把当前 P 堆里所有 when <= now 的定时器跑掉。回调直接在调度器的 g0 上执行（channel 发送就是在这里做的），然后 G 被唤醒入队。

2. netpoll 路径：当 P 没有别的活、准备阻塞在 netpoll 时，调度器把当前 P 最早定时器的到期时间作为 epoll_wait 的超时传进去。这样即使没有任何网络事件、也没人唤醒它，时间一到 epoll_wait 自己返回，调度器回来跑定时器。全系统空闲时，只有一个 M 阻塞在 netpoll，CPU 占用为零。

3. sysmon 兜底：后台 sysmon 周期性检查所有 P 的最早定时器；如果某个 P 长时间没被调度（在跑 cgo、被抢占等），sysmon 会启动一个 M 把到期定时器跑掉，避免定时器被无限延迟。

4. 改期时主动唤醒：Reset/新增定时器把到期时间提前时，runtime 调 wakeNetPoller，唤醒可能正以更晚 deadline 阻塞的 netpoller，让它重新以更早的 deadline 等待。

周期定时器的”补 tick”

Ticker 触发后，下一次 when = when + period，而不是 now + period。如果消费慢、错过了多个周期，runtime 会按原计划时间跳过错过的周期，而不是把 tick 堆积起来。这保证慢消费者不会被 tick 洪流淹没。

用 testing/synctest 测试时间

Go 1.25 起 testing/synctest 正式可用。在 synctest.Test 的气泡里，所有 goroutine 用一个虚拟时钟，当所有 goroutine 都持久阻塞时，虚拟时钟直接跳到下一个时间事件：

func TestTimeout(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        ctx, cancel := context.WithTimeout(t.Context(), time.Hour)
        defer cancel()

        time.Sleep(time.Hour - time.Nanosecond)
        synctest.Wait()
        if err := ctx.Err(); err != nil {
            t.Fatalf("before timeout: %v", err)
        }

        time.Sleep(2 * time.Nanosecond)
        synctest.Wait()
        if err := ctx.Err(); err != context.DeadlineExceeded {
            t.Fatalf("after timeout: %v", err)
        }
    })
}

这个测试不会真实等待一小时。它是测试超时、重试、timer 重置逻辑的利器，能同时消除真实 Sleep 的慢和抖动。

兼容性边界

  • 主模块 go.mod 声明 go 1.23+ 时默认用新同步语义。
  • GODEBUG=asynctimerchan=1 强制恢复 Go 1.23 之前的异步 channel 行为；=0 强制新语义。
  • Go 1.26 已宣布 Go 1.27 移除该开关，始终使用同步 timer channel。不要把它当长期方案。
  • 同一 timer 跨 goroutine 的 Stop/Reset 仍需自行同步；新语义只保证”之后的接收看不到旧值”，不保证多个 goroutine 并发调用 Reset 的顺序。

附录：历史实现（Go 1.14）

以下是 Go 1.14 引入”每 P 定时器堆”时的设计，保留用于理解演进。Go 1.26.5 的结构、状态和函数名已有变化，不要当作当前 API。

从全局堆到每 P 堆

  • Go 1.9 之前：全局唯一四叉堆 + 全局锁，所有定时器操作抢同一把锁。
  • Go 1.10–1.13：64 个分片四叉堆，降低锁竞争，但每个桶一个常驻 goroutine 处理唤醒，上下文切换开销大。
  • Go 1.14：移除桶 goroutine，定时器挂到每个 P 的堆上，由调度器和 netpoll 协同触发。这成为至今的主线架构。

四叉堆相对二叉堆的优势：子节点到根的层数少（$\log_4 n$），数组前部数据更集中，缓存友好。

Go 1.14 的 P 字段与状态

当时的 P 上有 timersLock、timers []*timer、numTimers、adjustTimers、deletedTimers 等字段，并使用一组互斥状态（timerNoStatus、timerWaiting、timerRunning、timerDeleted、timerRemoving、timerRemoved、timerModifying 等）管理生命周期。增删改查都要在锁内转换状态。

Go 1.26 把这一组互斥状态压成了 3 个标志位，结构更简单，但”每 P 堆 + 调度器/netpoll 协同”这一核心架构没变。如果需要对照旧源码，可参考 Git 历史中的 src/runtime/time.go。
