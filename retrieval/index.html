Retrieval：从大规模信息中找到候选

NOTE

一句话定义 **Retrieval 是在受延迟、成本、权限和新鲜度约束的条件下，从大规模语料中找出一小批可能相关候选的过程。**它首先追求“别漏掉”，再把精排工作交给 Ranking - 从候选集合到最优顺序。

搜索框只是入口。生产检索系统还包括数据接入、解析、切分、索引、查询理解、候选生成、权限过滤、融合、缓存、观测和索引迁移。只会“文本转向量后查 Top-K”，通常还不足以支撑企业级 RAG。

1. Retrieval、Search 与 Ranking 的边界

概念核心问题典型输入典型输出
Retrieval哪些对象可能相关？查询、过滤条件、租户身份数十到数千个候选
Search面向用户的完整检索产品查询、交互、业务规则排序结果、摘要、筛选项
Ranking - 从候选集合到最优顺序候选谁更应该靠前？查询和候选特征有序列表
Recall - 召回阶段与 Recall@K 指标相关对象是否被找全？检索结果与相关性标注指标或候选覆盖情况

检索的典型优化目标不是单一相关性，而是多目标约束：

max⁡  Recall@Ks.t.p99<L,  Cost<C,  ACL=100%,  Freshness<F\max \; \text{Recall@K} \quad \text{s.t.} \quad p99 < L,\; Cost < C,\; ACL=100\%,\; Freshness < FmaxRecall@Ks.t.p99<L,Cost<C,ACL=100%,Freshness<F

其中 ACL 正确性不是可以拿来交换的软指标，而是必须满足的安全约束。

2. 一条完整的生产链路

这条链路有两种时延：

  • 数据时延：源数据改变到索引可查询所需时间；
  • 查询时延：收到查询到返回候选所需时间。

很多“RAG 答错”的根因不在模型，而在数据面：文档未解析、索引没刷新、删除事件没传播、ACL 元数据丢失。

3. 稀疏检索：关键词仍然不可替代

倒排索引把词项映射到包含它的文档列表。BM25 是经典的稀疏检索函数：

BM25⁡(q,d)=∑t∈qIDF(t)⋅f(t,d)(k1+1)f(t,d)+k1(1−b+b∣d∣avgdl)\operatorname{BM25}(q,d)=\sum_{t\in q} IDF(t)\cdot \frac{f(t,d)(k_1+1)}{f(t,d)+k_1\left(1-b+b\frac{|d|}{avgdl}\right)}BM25(q,d)=t∈q∑​IDF(t)⋅f(t,d)+k1​(1−b+bavgdl∣d∣​)f(t,d)(k1​+1)​
  • f(t,d)f(t,d)f(t,d)：词项在文档中的频率；
  • IDF(t)IDF(t)IDF(t)：稀有词权重；
  • bbb：文档长度归一化强度；
  • k1k_1k1​：词频饱和速度。

它尤其擅长：错误码、API 名、产品型号、人名、版本号、精确短语。其弱点是同义表达和跨语言语义匹配。

TIP

生产经验 查询 ERR_CONNECTION_RESET 时，精确词项通常比向量语义更可靠；查询“怎么处理连接被对端重置”时，向量检索更有优势。两者不是替代关系。

4. 稠密检索：在向量空间里寻找语义近邻

双塔模型分别编码查询和文档：

eq=fq(q),ed=fd(d),s(q,d)=cos⁡(eq,ed)  或  eqTede_q=f_q(q),\qquad e_d=f_d(d),\qquad s(q,d)=\cos(e_q,e_d)\;\text{或}\;e_q^Te_deq​=fq​(q),ed​=fd​(d),s(q,d)=cos(eq​,ed​)或eqT​ed​

训练时通常让正样本分数高于负样本。负样本质量决定模型是否真正学会区分“看似相近但不相关”的内容：

  • 随机负样本太简单；
  • BM25 hard negative 更接近线上混淆项；
  • 线上曝光但未点击不能直接当负样本，存在位置偏差；
  • 跨租户数据不能因训练方便而突破隔离边界。

4.1 向量相似度的常见坑

  • cosine、dot product、L2 的分数不可直接混用；
  • dot product 会受向量模长影响，是否归一化必须与训练一致；
  • embedding 维度越大不必然效果越好，却会线性增加内存与带宽；
  • 同一索引混入不同模型或不同预处理版本的向量，分数将失去语义；
  • 短查询与长文档的编码分布可能不同，需要专门评估。

5. ANN：为什么不做精确全量扫描

当有 NNN 个 DDD 维向量时，暴力检索近似需要 O(ND)O(ND)O(ND) 计算。ANN（Approximate Nearest Neighbor）牺牲少量近邻召回率换取延迟和成本。

HNSW

HNSW 构建分层小世界图，查询从稀疏上层快速逼近，再在底层扩展邻居。

参数增大后的效果代价
M图连接更多，召回通常更高内存、构建时间增加
efConstruction索引质量更高构建更慢
efSearch查询召回更高查询延迟和 CPU 增加

IVF / PQ

IVF 先把向量分桶，查询只扫描部分桶；PQ 将向量压缩为码字。它们适合超大规模和内存敏感场景，但训练码本、分桶偏斜和量化损失都需要监控。

IMPORTANT

必须区分两种 Recall ANN Recall 比较近似索引与精确向量 Top-K；业务 Retrieval Recall 比较系统结果与人工相关文档。前者高，不代表 embedding 能理解业务相关性。

6. 不只有双塔：稀疏学习与 Late Interaction

  • Learned Sparse Retrieval：模型产生稀疏词项权重，保留倒排索引的可扩展性；
  • Late Interaction：查询和文档保留 token 级向量，检索时做细粒度最大相似度聚合；
  • Cross-Encoder：把查询与文档一起输入模型，质量高但成本大，通常用于精排。

ColBERT 的核心价值是把文档表示预计算，同时保留 token 级交互，处于双塔与 Cross-Encoder 之间。

7. 混合检索：解决不同相关性信号的互补

生产系统常并行执行 BM25 与向量检索，再融合结果。

直接对原始分数加权很危险：BM25、cosine、不同索引分片的分数分布都可能不同。RRF（Reciprocal Rank Fusion）只使用名次：

RRF⁡(d)=∑r∈R1k+rankr(d)\operatorname{RRF}(d)=\sum_{r\in R}\frac{1}{k+rank_r(d)}RRF(d)=r∈R∑​k+rankr​(d)1​

它易上线、对分数标定不敏感；缺点是忽略名次之间实际分差。若使用加权融合，需要离线标定、分查询类型校准并监控分布漂移。

8. Query Understanding：先理解要找什么

检索前处理可能包括：

  • 拼写修正、分词、语言检测；
  • 实体识别与字段过滤提取；
  • 同义词、缩写和版本别名展开；
  • 多跳问题拆解为多个子查询；
  • 根据查询意图路由到代码、文档、工单或指标索引；
  • 使用 LLM 生成检索改写或假想答案（HyDE）。

LLM 改写必须保留原查询并可回溯。它可能擅自补充错误实体，因此生产上常将“原查询通路”与“改写通路”并行，再融合结果。

9. Chunking：检索单位决定上限

Chunk 太小会丢失语境，太大则语义被稀释、token 成本上升。常见策略：

  • 固定 token + overlap：简单稳定，但会切断结构；
  • 按标题、段落、函数或表格切分：语义完整；
  • parent-child：小块负责命中，大块负责提供上下文；
  • hierarchical：先找章节，再在章节内找段落；
  • late chunking：先编码长上下文，再形成局部表示。

Chunk 必须携带 document_id、chunk_id、标题路径、页码/行号、版本、时间、租户和 ACL。否则即使命中，也难以引用、去重、删除或审计。

10. Filter 与 ACL：安全边界不是事后补丁

推荐顺序取决于引擎能力，但必须确保不可越权：

  1. 从可信身份生成租户与权限过滤器；
  2. 在检索引擎中尽早过滤；
  3. 返回候选后做防御性权限复核；
  4. 缓存键包含身份、租户和权限版本；
  5. 日志不记录敏感正文或完整 embedding。

[!danger] 常见事故 先全局向量检索再在应用层过滤，如果 Top-K 全被剔除，会导致“明明有权限文档却查不到”；如果过滤逻辑漏掉一次，则直接造成跨租户数据泄漏。应使用支持过滤感知 ANN 的索引，或扩大候选并进行严格复核。

11. 索引生命周期与无损迁移

索引不是一次性构建物，而是持续演进的生产资产。

实践要点：

  • 逻辑别名指向物理版本，如 docs_current -> docs_v17；
  • 文档主键幂等，重复消费不会产生重复 chunk；
  • 删除使用 tombstone 并追踪传播延迟；
  • 双写期间记录两个版本的成功状态，避免静默半失败；
  • shadow 只比较结果，不影响用户；
  • 切换后保留旧索引到回滚窗口结束；
  • embedding 版本、chunker 版本与解析器版本进入元数据。

12. 容量与延迟预算

粗略向量原始内存：

Memory≈N×D×bytes_per_dimensionMemory \approx N \times D \times bytes\_per\_dimensionMemory≈N×D×bytes_per_dimension

还需加 HNSW 图、元数据、倒排表、副本和运行时缓存。容量规划至少估算：

  • 日增文档/Chunk 数和保留周期；
  • embedding 维度与精度（FP32、FP16、量化）；
  • 分片数、副本数和故障冗余；
  • 峰值 QPS、热查询比例、批量写入吞吐；
  • merge/compaction 对尾延迟的影响；
  • 重建全量索引所需时间和临时双倍容量。

在线延迟要拆分，而不是只看总 p95：

query rewrite → embedding → lexical/vector search → fusion → ACL → rerank

层面指标回答的问题

评估集应按语言、租户、文档类型、查询意图、热门/长尾和时间切片分层。总体均值很容易掩盖某个关键客户或新数据源完全失效。

14. 高频生产故障与排查

14.1 精确 ID 查不到

现象：自然语言效果好，错误码、订单号、类名失效。
根因：只启用向量检索，分词器又拆坏标识符。
处理：保留 keyword 字段与 BM25 通路，对 ID 意图做精确路由。

14.2 新文档查不到但写入成功

检查事件消费 lag、解析状态、chunk 数、embedding 任务、索引 refresh 和 alias 指向。API 写入成功只说明入口接受，不代表可搜索。

14.3 embedding 升级后相关性骤降

检查是否将新查询向量打到旧文档向量索引，或新旧归一化策略不一致。embedding 模型与索引版本必须原子绑定。

14.4 延迟偶发尖峰

常见原因是 compaction、热点分片、efSearch 动态放大、冷缓存、同步 LLM 改写或 reranker 批处理等待。需要 span 级分段观测。

14.5 已删除文档仍被回答

追踪源删除事件、tombstone、索引删除、缓存失效和生成上下文缓存。对法规删除设置独立 SLO 与审计证据。

15. 上线清单

  • 有 lexical、dense 或 hybrid 的明确选择依据
  • Recall@K 按关键切片达标
  • ACL 在检索前后均有防线，并做越权测试
  • 索引版本、embedding 版本和 chunker 版本可追踪
  • 新索引支持 backfill、双写、shadow、canary 和回滚
  • 删除与更新具有传播 SLO
  • 分段 latency、失败、空结果和 fallback 可观测
  • 精确 ID、长尾、多语言、时间敏感查询进入回归集
  • 容量包含副本、重建和双索引窗口

16. 高级工程师面试题

TIP

- 为什么不能只用向量数据库？ 向量检索擅长语义相似，但对精确 ID、罕见词、否定关系和最新实体可能不稳定。生产上通常需要关键词、向量、元数据过滤和业务路由的组合，还要解决索引生命周期、权限与观测问题。

TIP

efSearch 如何选择？ 在代表性查询集上绘制 ANN Recall、p95/p99 延迟和 CPU 的 Pareto 曲线；按查询类型或负载动态设置上限。不能只用平均延迟，也不能把 ANN Recall 当业务 Recall。

TIP

- 如何升级 embedding 模型且不停机？ 新建版本化索引，全量回填，增量双写，影子查询比较，按租户或流量金丝雀切换；alias 原子切换并保留旧索引回滚。严禁新查询向量与旧文档向量混查。

TIP

- 混合检索为什么常用 RRF？ 不同检索器分数尺度很难直接比较，RRF 基于名次融合，工程上稳定且无需复杂标定。若相关性收益需要分数信息，再用学习融合并监控分布漂移。

TIP

- 如何证明检索问题而不是生成问题？ 固定问题，检查 gold evidence 是否进入候选、精排和最终 Context；分别测 Recall@K、nDCG、Context Recall 与答案支持度。证据从未进入候选是检索问题，进入上下文但回答仍错误才更偏生成或提示问题。

18. 与 Memory、Recall、Ranking、RAG 的对比

概念它负责什么它不负责什么关键生产问题
Memory - Agent 如何记住、更新与遗忘保存、更新、治理跨时状态不等于每次查询算法写入质量、冲突、遗忘、权限
Retrieval从大规模语料生成候选不保证最终顺序或答案可信索引、召回、延迟、新鲜度、ACL
Recall - 召回阶段与 Recall@K 指标描述“有没有漏掉”及候选阶段目标不是某一种数据库或算法标注分母、分层评估、成本权衡
Ranking - 从候选集合到最优顺序对候选排序与重排无法挽回未召回文档精排延迟、特征偏差、融合、降级
RAG - 从检索到可信生成的完整系统将外部证据装配给生成模型不等于单纯向量检索证据链、引用、安全、端到端评估

一句话串起来：Memory 决定长期保留什么，Retrieval 找候选，Recall 衡量漏没漏，Ranking 决定先看谁，RAG 把证据变成有出处的回答。
