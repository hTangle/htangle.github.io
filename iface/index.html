Interface 与动态调用：Go 1.26.5 源码分析

TIP

先抓住主干 Go 的接口在运行时只有两种形态：

  • eface（空接口 any）：两个字——(_type, data)，只记录”装的是什么类型 + 数据指针”；
  • iface（带方法的接口）：两个字——(itab, data)，itab 里缓存了”接口方法 → 具体类型方法”的跳转表。

接口调用 r.Read() 不是反射查找，而是一次数组下标：itab.Fun[0]。类型断言和 type switch 靠 itab 缓存（Go 1.26 还加了调用点本地缓存加速）。理解这三样——eface/iface/itab——就理解了 Go 的所有动态分发。

两个字的接口：eface 与 iface

// runtime/runtime2.go
type eface struct {
    _type *_type         // 动态类型
    data  unsafe.Pointer // 指向实际值
}
type iface struct {
    tab  *itab           // 接口方法表 + 动态类型
    data unsafe.Pointer  // 指向实际值
}
  • 空接口 any 用 eface，只装类型和值，没有方法可调（要调方法得先类型断言成具体类型或非空接口）。
  • 非空接口（如 io.Reader）用 iface，tab 指向一个 itab，里面既有动态类型也有方法跳转表。
  • data 永远是指针。若值本身是指针/chan/map/func（TFlagDirectIface），data 直接装这个字；否则装值的地址（值通常在堆上，装箱 i=T(x) 可能触发逃逸分配）。
  • nil 接口：两个字都为 0。一个接口是否为 nil，只看这两个字，不看 data 指向的内容。

itab：接口方法表

itab 是接口和具体类型配对的产物，是动态调用的核心：

type itab struct {
    inter *interfacetype  // 接口类型
    _type *_type          // 具体类型
    hash  uint32          // 仅 type switch 用（注意：不是 itabTable 的哈希）
    _     [4]byte
    fun   [1]uintptr      // 变长：接口方法数 N，实际分配 N 个字
}
  • fun[0] 是接口第一个方法的实现地址，fun[1] 是第二个……接口方法调用 r.Read() 编译成 (*itab).Fun[0]，一次间接跳转，和 C++ 虚函数同价。
  • fun 是变长数组：分配时额外分配 len(inter.Methods)-1 个字，避免二级指针。
  • fun[0] == 0 是”该类型未实现此接口”的哨兵。构建 itab 时若某个接口方法找不到，fun[0] 保持 0，这个 itab 还会被缓存起来作为负缓存，下次同样的断言直接失败。

构建方法表在 itabInit 里：接口方法和具体类型方法都按名排序，双指针归并匹配，O(ni+nt) 而非 O(ni×nt)。匹配要求方法名相同、函数类型完全一致、未导出方法还要包路径一致。匹配上的不是直接放具体方法地址，而是放 Ifn（接口调用入口），这样需要时编译器能插入接收者转换的适配代码。

itab 缓存：全局表 + 调用点本地缓存

itab 一旦构建就全局缓存、永不释放、只读复用。key 是 (inter, _type) 对。

1. 全局 itabTable（规范存储）

  • 进程级单例，开放寻址 + 二次探测（h(i) = h0 + i*(i+1)/2 mod 2^k），初始 512 槽，75% 负载时翻倍。
  • 哈希是 inter.Type.Hash ^ typ.Hash。
  • 读无锁（atomic.Loadp）；写加 itabLock，双检后用 atomic.StorepNoWB 发布。
  • 用 persistentalloc 分配 itab，不走 GC（程序生命周期内常驻）。

2. 调用点本地缓存（Go 1.26 新增的快路径）

getitab 仍是兜底，但高频的类型断言和 type switch 由编译器在每个调用点挂一个 abi.TypeAssertCache/abi.InterfaceSwitchCache：

  • 它直接把具体 *_type 映射到结果（case 编号 + itab），命中就跳过全局表查找；
  • 缓存以 CAS 安装，并发安全；
  • 大约每 1024 次调用才重建一次（随着表变大频率更低），摊销成本接近一次指针比较；
  • 架构不支持时回退到 getitab。

这是典型的”稳定配对值得缓存”的优化：接口和具体类型的组合在一个程序里通常就那么几个，却被反复断言。

装箱、断言与 type switch

装箱（var i any = x）：编译器生成 convT*，把值拷到堆上（若需要），构造 eface{typeOf(x), &x}。x 是指针类类型则不分配。

类型断言 v, ok := i.(T)：

  • i 是空接口、T 是非接口具体类型：走 assertE2T2（comma-ok）或 assertE2T（panic 版），直接比 i._type == typeOf(T)，相等就从 data 拷回值。
  • i 是非空接口、T 是接口：走 assertI2I，调 getitab(T, i.tab._type, canfail) 拿到 itab。
  • 失败时 comma-ok 返回零值 + false；非 comma-ok 调 panicdottypeE/I 抛 TypeAssertionError。

getitab(inter, typ, canfail) 的路径：

  1. 空接口方法集会 throw（内部误用，不可恢复）；
  2. 具体类型没有方法（TFlagUncommon 未置）直接失败；
  3. 无锁查全局表，命中且 fun[0]!=0 返回；
  4. 未命中加锁双检，再未命中就 persistentalloc + itabInit 构建，itabAdd 发布；
  5. fun[0]==0 表示未实现：canfail 返回 nil，否则 panic（负 itab 不记缺哪个方法，panic 时重跑一次 itabInit 只为取回缺失方法名）。

type switch：走 interfaceSwitch，优先查调用点缓存，把具体类型映射到 case 编号，比逐个 getitab 快得多。

nil interface 与 typed nil

这是最常见的坑：接口值是否为 nil，取决于两个字是否都为零，不取决于 data 指向的值是否为 nil。

var p *os.File = nil
var r io.Reader = p   // r != nil！
// r.tab != nil（类型是 *os.File），r.data == nil
// 所以 r != nil，调用 r.Read() 会用 nil 接收者进去
  • 把一个有类型的 nil 指针赋给接口，接口非 nil，因为 _type/itab 已填。
  • 函数返回 error 时，返回具体类型的 nil 指针会导致接口非 nil——经典 bug，应直接 return nil。
  • 真正的 nil 接口是 var r io.Reader（从未赋值），tab==nil && data==nil。

边界与误区

  • 空接口不做方法查找：any 没有方法表，所有动态行为都要先断言。
  • 接口值比较可能 panic：动态类型如果不可比较（slice/map/func），比接口会 panic，即使两个接口的 _type 相同。
  • 装箱可能分配：非指针值赋给接口通常逃逸到堆；值本身就是一字指针类（*T、chan、map、func、uintptr 大小的类型）则不分配。
  • 方法集是按值/指针接收者区分的：*T 的方法集包含 T 的，反之不然；itab 构建时按具体类型的方法集匹配，所以 var r io.Reader = T{} 可能失败而 &T{} 成功。
  • itab 是负缓存：类型不实现接口也会缓存一个 fun[0]==0 的 itab，反复断言不会重复构建。
  • 不要用反射替代类型断言：类型断言有缓存和编译优化，反射是慢路径。
