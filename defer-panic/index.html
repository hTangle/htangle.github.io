defer、panic 与 recover：Go 1.26.5 源码分析

TIP

先抓住主干 这三个机制本质是一条挂在 goroutine 上的 defer 链表，加上两种触发方式：

  • 正常返回：编译器在函数尾声插入 deferreturn，从 g._defer 链上按 LIFO 把本帧的 defer 跑完；
  • panic：gopanic 沿着同一个链表逐个执行 defer，每个 defer 里有机会调 recover() 中止 panic；
  • recover：只是把当前 _panic.recovered 置 true，真正的”复活”发生在 recovery——通过 gogo 把 G 跳回 defer 帧的 deferreturn，继续跑剩余 defer。

性能关键是 open-coded defer：不在循环里的 defer 被编译器内联成栈槽 + 位掩码，零堆分配、零链表遍历，只在 panic/Goexit 时才回退到 runtime 查表。

三种 defer 实现

Go 1.26 同时保留三种实现，编译器按函数特征选：

1. Open-coded defer（最快，默认路径）

当函数里的 defer 不出现在循环中、数量和复杂度在阈值内时，编译器：

  • 把每个 defer 的函数值和参数存到当前栈帧的专用槽位；
  • 用一个 deferBits 位掩码记录哪些 defer 已注册；
  • 在函数每个返回点插入内联代码：按位从高到低清位并调用对应函数；
  • 完全没有 _defer 记录、没有堆分配、没有链表遍历。

正常返回时这是纯寄存器/栈操作。只有在 panic 或 runtime.Goexit 发生时，runtime 才通过编译器生成的 FUNCDATA_OpenCodedDeferInfo（initOpenCodedDefers 读取）反查槽位和掩码，逐个执行。

2. Heap-allocated defer（deferproc）

defer 在循环里、数量超限或闭包逃逸时，编译器生成 deferproc(fn)：

  • 从 per-P 的 defer pool（newdefer，类似 sync.Pool）取一个 _defer；
  • 填 fn、调用者 pc/sp，链到 gp._defer 链头；
  • _defer.heap = true。

这是历史上最常见的”慢路径”，每次 defer 有 pool 操作（多数情况无真堆分配，但要写链表）。

3. Stack-allocated defer（deferprocStack）

编译器能在编译期确定 defer 记录数量时，直接把 _defer 结构放进函数栈帧，deferprocStack 只填字段并链入。heap=false，函数返回时随栈帧回收，零分配。它标了 //go:nosplit，因为记录里的指针字段在初始化前不能被 GC 误扫。

type _defer struct {
    started   bool
    heap      bool
    rangefunc bool          // range-over-func 的 defer
    sp        uintptr       // 调用者栈指针
    pc        uintptr
    fn        func()
    link      *_defer       // LIFO 链
    head      *atomic.Pointer[_defer] // rangefunc 子链
}

参数求值、返回值与执行顺序

三条铁律：

  1. 参数立即求值：defer f(x) 的 x 在 defer 语句执行时就求值，不是在 f 真正调用时。闭包 defer func(){...}() 捕获变量则按引用读取。
  2. LIFO 顺序：后注册的先执行，因为都挂在链头。
  3. 能改命名返回值：defer 在返回值赋值之后、真正 RET 之前跑，所以能读写命名返回值；匿名返回值已固化，defer 改不了。

deferreturn 是编译器插在函数尾声的函数，它创建一个特殊的 _panic{deferreturn:true}，然后循环 nextDefer() 取出本帧（按 sp 匹配）的 defer 执行，直到链上不再有属于本帧的记录。open-coded 的 defer 在这里通过清位派发。

panic：沿 defer 链展开

gopanic(e) 做的事：

  1. e == nil 时包装成 *PanicNilError（除非 GODEBUG=panicnil=1 恢复旧行为）。
  2. 禁止在系统栈、malloc 进行中、preemptoff、持有锁时 panic——这些是 runtime 内部不变量，违反会直接 throw。
  3. 创建 _panic 记录，挂到 g._panic 链头，runningPanicDefers++。
  4. 主循环反复调 nextDefer()：
    • 先派发光本帧的 open-coded defer；
    • 再走 _defer 链；
    • 每个 defer 函数在当前 G 上直接执行。
  5. 某个 defer 调了 recover() 后，nextDefer 发现 p.recovered，调 mcall(recovery) 永不返回。
  6. 所有 defer 跑完仍未 recover，打印 panic 栈（preprintpanics），fatalpanic 终止进程。

关键点：panic 不是一次”跳转”，而是一个遍历 defer 链的循环。 每跑一个 defer，控制权都回到 gopanic，它再决定继续展开还是恢复。

// 简化自 runtime/panic.go
func gopanic(e any) {
    gp := getg()
    p := &gp._panic /* 实际从池取 */
    p.arg = e
    p.start(...)
    for {
        d := p.nextDefer()
        if d == nil { break }
        d.fn() // 跑 defer；里面可能调 gorecover
        if p.recovered { mcall(recovery); /* 不返回 */ }
    }
    fatalpanic(p)
}

recover：为什么必须在 defer 里直接调

gorecover() 的有效性检查很严格（避免被间接调用骗到）：

  • 没有活跃 panic、是 Goexit、或 panic 已 recovered → 返回 nil；
  • 用 unwinder 从 gorecover 的调用帧往上走，跳过编译器生成的 wrapper 帧，数非包装帧；
  • 到达 gopanic 帧时，必须满足：帧指针匹配 p.gopanicFP，且恰好有一层非包装帧；
  • 多层非包装帧（recover 被嵌套函数调用）→ 判定不是”defer 直接调用”，返回 nil。

成功时设置 p.recovered = true 并返回 p.arg。注意 recover() 本身不做栈跳转，它只是置标志。

常见错误：

defer func() {
    doRecover()   // ❌ doRecover 里的 recover() 多了一层，无效
}()
defer recover()  // ❌ 同理，recover 不是直接在 defer 函数里

recovery：从 panic 复活

真正的”恢复”在 recovery(gp)，通过 mcall 切到 g0 执行：

  1. 记录触发 recover 的 defer 的 sp/pc/fp，以及是否还有 open-coded defer 没跑；
  2. 把目标 PC 解析回该函数 deferreturn 的调用点；
  3. 展开 panic 链：startSP < sp 的 panic 计数减回去；若链上挂着 Goexit，则改跳到 Goexit 的启动点而不是直接返回（保证 Goexit 语义不被 recover 破坏）；
  4. 把剩余 open-coded defer 的位掩码/槽位存进 gp.param（savedOpenDeferState），供恢复后的 deferreturn 继续消费；
  5. 校验 sp 在 G 栈范围内，设置 gp.sched，gogo 跳过去——G 像从一次正常调度中醒来，落在 deferreturn，继续把同帧剩余 defer 跑完，然后函数正常返回。

所以 recover 之后，当前函数的剩余 defer 仍然会执行，但更外层调用者根本不知道发生过 panic。

fatal/throw/panic 的边界

  • panic：用户可见的运行时恐慌，可被 defer/recover，会跑 defer 链。
  • throw/fatal：runtime 内部不变量被破坏（map 并发写、scheduler 不变量等），不跑 defer、不可 recover，直接打印栈并 exit(2)。
  • fatalpanic：未被 recover 的 panic 最终走到这里，跑完所有 defer 后终止。
  • Goexit：不是 panic，但走类似的 defer 展开路径，终止当前 goroutine；recover() 对它返回 nil，但它能在 recovery 时被”接力”回去。

边界与误区

  • defer 在循环里要小心：for { defer ... } 会堆积 _defer 直到函数返回才释放，可能暴涨；open-coded 不适用。
  • 闭包变量捕获：defer func(){ fmt.Println(i) }() 读的是循环结束后的 i；要当即捕获用 defer func(i int){...}(i) 或临时变量。
  • nil 函数的 defer：defer f() 里若 f 是 nil，注册不报错，但执行时 panic。
  • recover 吞掉 panic 不代表没事：被 recover 的 goroutine 恢复执行，但可能处于不一致状态；包级 invariant 被破坏时应让程序失败而不是吞掉。
  • defer 的开销在热路径要测：open-coded 已经极便宜（几条指令），但循环/闭包场景的 heap defer 仍有 pool + 链表开销，用 defer cleanup() 包裹大段逻辑前先 benchmark。
  • recover() 返回 nil 不代表没 panic：它在非 defer 上下文里恒返回 nil，不能用来”探测” panic。
