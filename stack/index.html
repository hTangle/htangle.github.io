栈空间管理：Go 1.26.5 源码分析

Go 能承载大量 goroutine，不是因为“goroutine 没有栈”，而是因为每个普通 G 从较小的连续栈开始，按需成倍扩容，并在安全点缩容。编译器负责函数序言、stack map 与逃逸分析；runtime 负责 stack cache、复制、指针修正、抢占和 GC 扫描。

IMPORTANT

当前实现 Go 1.26.5 使用 连续、可复制栈（contiguous copying stack）：从小栈开始，空间不足时分配更大的连续区域，复制有效数据并修正栈内指针。

一、进程里不止一种栈

普通 G stack

每个普通 goroutine 的 g.stack 描述严格的 [lo, hi) 地址区间，stackguard0 是函数序言比较的 guard，结构定义见 runtime2.go#L459-L483。

Go 支持的多数架构上栈向低地址增长。函数序言在真正建立较大 frame 前检查 SP 与 guard，空间不足则进入 morestack。

g0：每个 M 的调度栈

每个 OS thread 对应的 M 有一个 g0。调度器、栈分配、栈复制、部分 GC 和必须 //go:systemstack 的 runtime 代码运行在 g0 上。

为什么不能在待扩容的 G stack 上执行 stackalloc？因为分配过程自身可能持锁、调用 page allocator；若它再需要扩容会形成递归或自死锁。stackalloc 明确要求运行在 scheduler stack，见 stack.go#L338-L351。

gsignal：信号处理栈

每个 M 还有 gsignal，用于操作系统信号。morestack 明确禁止扩容 g0 与 gsignal；amd64 检查见 asm_amd64.s#L628-L653。

二、栈与堆的决定发生在哪里

逃逸分析的两个不变量

编译器要求：

  1. 指向 stack object 的指针不能被存入 heap 并在栈帧失效后继续存在；
  2. 指向 stack object 的指针不能比对象本身活得更久。

源码使用带权数据流图分析变量之间的地址/解引用关系，见 escape.go#L21-L47。

常见逃逸场景不是绝对规则

场景可能结果关键判断
返回局部变量地址常逃逸调用者是否可持有该指针
闭包捕获变量可能逃逸闭包是否逃出当前调用
传给 interface可能逃逸装箱值的生命周期与调用是否可内联
make([]T, const)可能在栈backing store 是否小且不逃逸
make([]T, n)Go 1.26 更多情况在栈动态容量是否通过运行时阈值判断且结果不逃逸
传指针给不会保存它的函数可不逃逸跨函数摘要是否证明安全

诊断命令：

go build -gcflags='all=-m=2' ./...

WARNING

编译器输出是结论，不是永久契约 内联、泛型实例化、PGO、Go 版本和控制流都会影响结果。优化必须用目标 Go 版本重新编译与 benchmark。

三、Go 1.26 的 variable-size slice 栈上分配

对于动态 make([]T, n)，Go 1.26 会在满足逃逸和大小条件时生成一个小型栈 backing store 与运行时分支：容量不超过阈值时使用栈，否则调用 makeslice 分配 heap backing store。

源码的默认阈值为 32 B，见 base/flag.go#L179-L190。lowering 伪代码直接写在 walk/builtin.go#L476-L500：

// K = 32 / sizeof(E)
if cap <= K {
    var arr [K]E
    slice = arr[:len:cap]
} else {
    slice = makeslice(elemType, len, cap)
}

注意：32 B 是当前默认启发式，不是 Go 语言保证，也不是所有栈对象总大小限制。编译器还要检查 element size、逃逸、优化开关和具体 IR 位置。

若该变化触发问题，可按官方说明：

# 使用 bisect 定位 variablemake 优化点
bisect -compile=variablemake <command>

# 临时关闭新增的 variable make 栈分配
go build -gcflags=all=-d=variablemakehash=n ./...

四、goroutine 创建与初始栈

编译器把 go f() 转成 runtime.newproc。newproc1 先尝试从当前 P 的 dead-G cache 取 g；没有则 malg(stackMin)，见 proc.go#L5313-L5325。

stackMin = 2048 定义在 stack.go#L70-L89。malg 把大小向上舍入为 2 的幂，调用 stackalloc，然后设置：

stackguard0 = stack.lo + stackGuard
stackguard1 = ^uintptr(0)  // 普通 G 不允许 systemstack prologue 使用它

实现见 proc.go#L5272-L5289。

NOTE

2 KiB 是初始 reservation，不等于 goroutine 的全部内存成本 g、sudog、timer、channel wait、defer、业务对象、profile/race 元数据都可能增加成本；已扩容 stack 也不会因为 goroutine 阻塞就立刻缩回 2 KiB。

五、小栈如何分配

per-P stack cache

小栈按 order 管理：2 KiB、4 KiB、8 KiB、16 KiB 等。当前 P 的 mcache.stackcache[order] 保存 free list；cache 空时从全局 stackpool 批量 refill。

小栈 fast path 见 stackalloc#L368-L405。栈内存不是普通 GC heap object：大栈通过 allocManual(..., spanAllocStack) 取得手工管理 span，GC 不把整段栈当普通对象扫描。

为什么栈大小必须是 2 的幂

stackalloc 明确检查 n&(n-1)==0。好处包括：

  • order 与 cache 索引简单；
  • grow/shrink 直接乘除 2；
  • span/page 分配与归还更可预测；
  • 复制成本可摊销为线性总成本。

六、函数序言与 morestack

编译器根据 frame 大小生成不同形式的 stack check。概念上可理解为：

if SP-frameSize < g.stackguard0 {
    runtime.morestack()
}

实际还要防止下溢、支持 small/large frame、NOSPLIT 链和架构 ABI。权威说明在 stack.go 顶部注释。

amd64 morestack 保存当前 G 的 PC/SP/BP/context，再保存调用者上下文，切到 g0 后调用 newstack，见 asm_amd64.s#L628-L682。

NOSPLIT 不是“更快”注解

//go:nosplit 表示函数不能触发栈增长。linker 会检查 NOSPLIT 调用链不能超过 guard 预算。它主要用于 runtime 的底层路径、信号与栈扩容自身；业务代码不应为了省一次检查而随意使用。

guard 除了增长检查，还复用为同步抢占触发器：runtime 可把 stackguard0 设置为特殊的 stackPreempt，让下一次函数序言失败并进入 newstack 的抢占分支，常量见 stack.go#L124-L145。

七、newstack：扩容与同步抢占共用入口

newstack 先读取一次 stackguard0。若等于 stackPreempt，它不会扩容，而是在安全条件允许时执行同步抢占、pending shrink 或 park，见 stack.go#L1076-L1145。

否则进入增长：

oldsize := gp.stack.hi - gp.stack.lo
newsize := oldsize * 2

若新 frame 更大，会继续翻倍直到 newsize-used >= maxFrame + stackGuard，见 stack.go#L1148-L1162。这避免“扩一次仍放不下，返回后马上再扩”。

普通 64 位平台 runtime 初始化时把最大 goroutine stack 设置为约 1 GB，32 位为约 250 MB，并另有 ceiling 防止计算溢出，见 proc.go#L156-L168。超过限制会 fatal，无法 recover。

八、copystack：复制的不只是字节

栈扩容最难的部分不是 memmove，而是修正所有指向旧栈的指针。copystack 的总体步骤见 stack.go#L898-L1003：

为什么 channel 会让复制复杂

阻塞的 send/receive 使用 sudog.elem 指向 goroutine 栈上的发送值或接收 slot。另一个 goroutine 可能通过 channel 操作访问这段内存，所以复制时必须与 channel lock 协调。

g.activeStackChans、g.parkingOnChan 记录这些危险状态，字段与注释见 runtime2.go#L526-L534。copystack 在 stack.go#L929-L953 调整 sudog，并只在安全同步后复制相关区域。

为什么 unsafe 很容易与栈移动冲突

Go 指针能被 runtime 根据 stack map 修正；藏在 uintptr、C 内存或 runtime 不知道的数据结构里的地址不会自动更新。

p := &buf[0]
u := uintptr(unsafe.Pointer(p))
runtimeCallThatMayGrowStack()
_ = *(*byte)(unsafe.Pointer(u)) // 不应假设 u 仍安全有效

规则：

  • 不用 uintptr 长期保存 Go pointer；
  • 遵守 unsafe.Pointer 转换规则，转换尽量保持在同一表达式；
  • cgo 交互遵守 pointer passing rules；
  • 不假设 goroutine stack 地址稳定。

九、栈缩容

GC stack scan 或同步安全点会调用 shrinkstack。当前策略不是“空闲一半就缩”，而是：

  • 目标 G 必须停止或当前 runtime 拥有其栈；
  • channel/libcall 等状态必须安全；
  • 新大小不能小于 fixedStack；
  • 当前使用量加 NOSPLIT guard 必须小于容量的 1/4；
  • 满足后缩为当前大小的一半并走 copystack。

判断见 stack.go#L1253-L1299。1/4 阈值提供迟滞，避免 1/2 附近反复扩缩。

NOTE

深递归后的 stack 不会立即收缩 增长发生在函数序言，收缩依赖后续 GC/安全点及 1/4 条件。因此一次峰值可能在一段时间内继续体现在 stack in-use 上。

十、GC 如何扫描栈

编译器为 safe point 生成 stack map，描述 frame 中哪些 slot 是指针。GC 获取 G 的扫描所有权，unwind frame 并 shade 指向 heap 的指针；stack 内部对象还会形成自己的待扫描图。

stackScanState 同时维护：

  • 精确指针 work buffer；
  • 异步安全点最内层 frame 的 conservative pointer buffer；
  • stack object 列表与按地址查找的树。

这连接了 垃圾收集器：goroutine 数量、平均 stack 大小和 stack 中的指针密度都会增加 root scan 工作。大量 blocked goroutine 即使 CPU 为零，也可能持续占用 stack 并保留 heap 对象。

大局部变量一定危险吗

大局部对象有三种可能：

  1. 优化后消失或进入寄存器；
  2. 进入当前 goroutine stack，增大 frame 并可能触发 grow；
  3. 因大小/逃逸被移到 heap，增加 allocation 与 GC 压力。

只看源码声明无法判断。必须结合 -m=2、汇编、benchmark 和 profile。

十二、优化原则

控制 goroutine 生命周期优先于微调初始栈

高级工程实践关注：

  • 所有后台 goroutine 有明确 owner；
  • context 能一路传递并被消费；
  • channel producer/consumer 退出协议闭合；
  • worker pool 与队列有上限；
  • shutdown 能等待 goroutine 收敛；
  • goroutine 数、stack bytes、waiting reason 有监控。

避免无界递归与巨型 frame

  • 输入深度不可信时改为显式 heap worklist；
  • 大 buffer 评估复用或分块，但不要盲目全局缓存；
  • 大数组按 value 传递会复制整个对象，优先审查接口设计；
  • benchmark 既看 allocs/op，也看延迟与 stack profile/metrics。

不要为了“栈上分配”破坏代码

让编译器做逃逸分析。只有 profile 证明 allocation 是瓶颈时，才尝试缩短生命周期、改善 API、减少接口装箱或帮助编译器内联；随后用目标版本复测。

十三、常见误区

误区Go 1.26.5 正确理解
goroutine 只有 2 KiB 成本2 KiB 是典型初始 stack，另有 G 与关联对象，且 stack 会增长
goroutine stack 由多个 segment 串联当前使用单段连续复制栈，扩容时整体搬迁有效区域
栈增长只是改一个边界要分配新栈、复制 live bytes、修正所有已知栈指针
栈会在函数返回时立刻缩小缩容依赖 GC/安全点和 1/4 阈值
返回局部变量地址一定慢可能逃逸，但性能影响要看调用频率、内联与 profile

stack memory 由普通 GC sweepstack 使用专门 pool/cache/manual spans，但 GC 会扫描它作为 root

总结

Go 1.26.5 的栈管理可以用一条链路概括：

逃逸分析决定 stack/heap
-> newproc1 分配小型连续栈
-> 函数序言检查 stackguard
-> morestack 切到 g0
-> newstack/copy 调整全部指针
-> GC safe point 扫描并择机 shrink

栈不是孤立机制：它连接 内存分配器 的 manual span 与 per-P cache，连接 垃圾收集器 的 root scan，也连接 GMP（Go 1.26.5 源码分析） 的抢占与调度。理解这三条连接，才真正理解“goroutine 为什么轻量”。
