Go 程序启动流程：Go 1.26.5 源码分析

TIP

先抓住主干 一个 Go 程序从内核 exec 到你的 main.main 被调用，中间只有四个关键动作：

  1. 汇编入口 rt0_go：在 g0 栈上搭好 m0、TLS、CPU 特征，这是 runtime 能跑起来的最小地基。
  2. schedinit：在 m0/g0 上顺序初始化栈、内存分配器、GC、P、调度器等所有子系统——此时还没有用户 G。
  3. newproc 创建 main goroutine：把真正要跑的 Go 代码变成一个 G，排进 P 的本地队列。
  4. mstart → schedule → runtime.main：m0 开始调度，main G 被跑起来，先执行所有包级 init，再调 main.main。

记住：前两步只有一个 M（m0）和一个栈（g0），main 函数本身也是一个 goroutine，不是什么特殊线程。

平台入口按架构/OS 各有一份（asm_amd64.s、asm_arm64.s、sys_linux_amd64.s 等），但汇编层之后全部汇入同一份 Go 代码。下面以 linux/amd64 为主线。

汇编入口：从 _rt0_amd64_linux 到 rt0_go

内核 execve 加载可执行文件后，把控制权交给 ELF 入口点。Go 用自己的链接器生成该入口，对 amd64 Linux 是 _rt0_amd64_linux，它几乎只有一条跳转指令，进入跨平台的 rt0_go。

rt0_go 是一段汇编，做的全是”在还没有任何 Go 代码能跑之前必须先有的东西”：

  • 初始化 g0 和 m0：m0 是程序启动时就存在的那个 OS 线程，g0 是它的系统栈（带栈保护页）。通过 TLS（Thread-Local Storage）把当前 M 的指针挂到寄存器/段上，之后 getg() 才能工作。
  • 运行 _cgo_init（如果启用 cgo）、检查 CPU 特征：用 CPUID 填 runtime.support_* 标志（如 AVX、ERMS），后续内存拷贝等会据此选实现。
  • 设置参数：把 argc/argv 从调用约定位置搬到 runtime 约定的寄存器，NOP 栈对齐，然后 CALL runtime·schedinit(SB)。

这一步不能写 Go 代码，因为栈、调度器、堆都还没就绪。它唯一调用的”高层”函数就是 schedinit。

schedinit：把 runtime 世界搭起来

schedinit 在 m0 的 g0 栈上顺序执行，是整个 runtime 的初始化主函数。关键顺序（Go 1.26.5）：

  1. 锁与调度骨架：初始化 sched 上的一堆锁（sched、defer、sudog、panic、allglock、allp 等），设置 sched.maxmcount = 10000（M 数量硬上限），标记 worldStopped()。
  2. stackinit()：初始化栈池，后续 G 的栈才有着落。
  3. mallocinit()：建立 mheap、page allocator、arena、size class——内存分配器就绪。
  4. cpuinit、alginit、mcommoninit(m0)：CPU 配置、哈希算法表、把 m0 登记进 allm。
  5. modulesinit、typelinksinit、itabsinit：加载 moduledata 表（链接器生成）、建立类型/itab 索引——interface 和反射的基础。
  6. goargs、goenvs、secure、checkfds：解析命令行参数、环境变量、安全/文件描述符检查。
  7. gcinit()：初始化 GC 状态、写屏障、后台 worker（worker 此刻还不会真的跑，因为没开始调度）。
  8. 设置 GOMAXPROCS：读 GOMAXPROCS 环境变量，否则用 CPU 数，procresize(nprocs) 创建 nprocs 个 P。

执行完 schedinit，堆、GC、P、类型系统都可用了，但用户代码一行都还没跑——此时仍在 m0/g0 上。理解这一点很重要：很多子系统（分配器、map、channel）的”零值即可用”前提，正是 schedinit 在这里铺好的。

创建 main goroutine 并进入调度

rt0_go 接着调用 newproc，把一个函数值（链接器填的 runtime.main）包装成一个新的 G：

  • newproc1 从 gfree 链表或新建一个 G，分配栈，设置入口 PC 为 runtime.main；
  • 把这个 G 放进当前 P 的本地运行队列；
  • 返回汇编，调用 mstart。

mstart 是 m0 的起点。它初始化自己的栈边界、信号处理，然后进入永不返回的 schedule() 循环。schedule 从 P 的本地队列、全局队列、netpoll、work stealing 中挑一个可运行 G——第一个被挑到的就是刚才入队的 main G。m0 从 g0 栈切到 main G 的栈，开始执行 runtime.main。

至此，“一个 M + 一个 g0”引导出了”一个 M 调度多个 G”的 GMP 世界。后续更多 M 是因为阻塞、cgo、sysmon 等需要才被创建的。

runtime.main：init 与 main

runtime.main 跑在 main G 上，是用户看到的”程序开始”：

  1. 启动 sysmon：newm(sysmon, nil, -1) 起一个不绑 P的后台 M，负责抢占、抢占式调度、netpoll、force gc（详见 GMP 笔记）。
  2. doInit(runtime_inittasks)：先执行 runtime 包自己的 init。
  3. gcenable()：允许 GC 后台 worker 真正开始工作。
  4. 按依赖顺序跑用户包 init：链接器把每个包的 init 函数组织成 inittasks 依赖图，runtime.main 遍历所有 moduledata，对每个调 doInit(m.inittasks)。同一个包内多个 init 按源文件字典序执行；包之间按导入依赖拓扑序。sync.Once 式的去重由依赖图本身保证。
  5. main_init_done 关闭：标志 init 阶段结束。
  6. fn := main_main; fn()：main_main 是链接器生成的跳板，直接调用用户的 main.main。
  7. main 返回后做 exit hook、race 收尾，最后 exit(0)。若有其他 goroutine 还活着，也随进程一起结束——main 返回不会等其他 goroutine。
// 简化自 runtime/proc.go
func runtime.main() {
    mp := getg().m
    if haveSysmon {
        systemstack(func() { newm(sysmon, nil, -1) })
    }
    doInit(runtime_inittasks) // runtime 包 init
    gcenable()
    for _, md := range moduledata {
        doInit(md.inittasks) // 各用户包 init，按依赖顺序
    }
    close(main_init_done)
    fn := main_main // == 你的 main()
    fn()
    runExitHooks(0)
    exit(0)
}

ABI、栈与调用约定：为什么入口是汇编

启动流程之所以必须有一层汇编，是因为 Go 的调用约定和平台 ABI 不一样：

  • 平台 ABI（ABI0）：参数主要走栈，遵循 C 调用约定。内核把 argc/argv 按这个约定交给入口。
  • Go 内部 ABI（ABIInternal）：Go 1.17 起寄存器传参（amd64 用 AX/BX/CX… 一组整数寄存器、X0… 浮点寄存器），栈只放溢出参数。funcval（闭包/方法值）通过上下文寄存器传环境指针。
  • rt0_go 负责把 ABI0 的状态搬到 ABIInternal 要求的位置，再 CALL 进 Go 函数。
  • 栈上还布有 FUNCDATA/PCDATA 和栈图（stack map），让 GC 能在调用点准确找到指针；这些表由编译器生成，汇编手写的入口要自己遵守。

理解这层边界，后面看 //go:nosplit、systemstack、mcall、getg().m.curg 就有了落点：它们都是在”Go 调度世界”和”裸 OS 线程/g0 世界”之间切换的工具。

边界与误区

  • main 不是”主线程”：在 Go 里它就是一个普通 goroutine，跑在某个 M 上。m0 是引导线程，但 runtime.main 之后它和其他 M 没有特权差异（除了初始栈、信号等）。
  • init 顺序是确定的：依赖图保证被依赖包先初始化；但同包多文件按文件名字典序，不要让 init 之间依赖隐式顺序。
  • init 里可以起 goroutine，但它可能在整个 init 完成后才真正跑：不要假设 init 期间启动的 G 能在 main 之前完成。
  • schedinit 里没有 G：它跑在 g0 上，不能调用会阻塞/调度的函数，否则没有 P 和调度循环接住它。
  • cgo 程序略有不同：如果用了 cgo，Go runtime 可能不是从 C 的 main 直接启动，而是跑在线程上通过交叉调用进入；但核心 schedinit/runtime.main 路径一致。
  • 返回即退出：main.main 返回会直接 exit(0)，不会等待其他 goroutine。需要等后台工作请用 sync.WaitGroup、channel 或 signal.NotifyContext 显式同步。
