网络轮询器：Go 1.26.5 源码分析

Go 网络程序能用少数几个操作系统线程扛住几十万长连接，靠的是 runtime 内置的网络轮询器（netpoller）。它把”连接没数据时阻塞谁”这件事从阻塞 OS 线程改成了park 住 goroutine：连接就绪后再把 G 唤醒、交回调度器。理解 netpoller，也就理解了为什么 Go 的网络 I/O 看起来是同步写法、却有异步的伸缩性。

TIP

先抓住主干 netpoller 不是一个独立线程在”轮询”，而是 runtime 与调度器协作的一套机制：

  1. 每个网络 fd 绑一个 pollDesc，记录”谁在读、谁在写”。
  2. goroutine 对一个暂不可读/写的 fd 调用 Read/Write 时，内部 gopark 把自己挂起，M 拿着 P 去跑别的 G，不阻塞 OS 线程。
  3. 后台一个不绑 P 的 M 阻塞在 OS 多路复用器（Linux epoll / macOS kqueue / Windows IOCP）上。
  4. fd 就绪后，多路复用器返回一批事件，netpoller 把对应 pollDesc 上挂着的 G 改成 runnable，塞进调度队列。
  5. 调度器在 findRunnable 里每次开头顺手非阻塞查一次 netpoll，没活干、要休眠前再查一次；全系统空闲时才让那个 M 阻塞在 epoll_wait。

记住一句话：netpoller 负责把”fd 就绪”翻译成”G 可运行”，调度器负责把可运行的 G 跑到 M 上。 两者通过 findRunnable 的两次非阻塞轮询和一个阻塞 M 协作。

平台差异主要在多路复用器后端：Linux 用 epoll，BSD/macOS 用 kqueue，Windows 用 IOCP，AIX/Solaris 用 ports/event ports。下面以 Linux epoll 为主线讲清机制，其他平台只是”事件怎么取”的差别。

核心模型：从”阻塞线程”到”park G”

传统阻塞 I/O 模型里，一个连接对应一个线程，read 没数据时线程进睡眠：

连接数 10 万 → 需要 10 万线程 → 内存爆、调度开销巨大

Go 的做法是让连接和 goroutine 绑定，而不是和线程绑定：

一次读操作在 runtime 内部的路径大致是：

// 简化自 internal/poll/fd_unix.go
func (fd *FD) Read(p []byte) (int, error) {
    for {
        n, err := syscall.Read(fd.Sysfd, p)
        if err == syscall.EAGAIN {
            // fd 暂不可读 → 把当前 G 挂在这个 fd 的 pollDesc 上
            if err := fd.pd.waitRead(fd.isFile); err != nil {
                return 0, err
            }
            continue // 被唤醒后重试 Read
        }
        return n, err
    }
}

关键点：返回 EAGAIN（fd 设了非阻塞，现在没数据）时，不是自旋重试，也不是阻塞线程，而是调 runtime_pollWait → netpollblock → gopark。当前 G 从 M 上摘下来、状态改成 _Gwaiting，M 立刻回调度器跑别的 G。等数据到了，netpoller 再把这个 G 唤醒，它从 waitRead 返回、重试 Read，这次就能读到。

pollDesc：每个 fd 的等待记录

pollDesc 把一个 fd 和”谁在等它”绑在一起，核心是两个指针：

type pollDesc struct {
    fd      *FD              // 关联的文件描述符
    rg      uintptr          // 等待读的 G（或状态常量）
    wg      uintptr          // 等待写的 G（或状态掩码）
    ...
    self    *pollDesc        // 用于在 epoll event 里找回自己
}
  • rg/wg 用一个字存两类信息：要么是一个 G 指针（有人在等），要么是状态常量 pdReady/pdWait。
  • 初始化时 rg=wg=pdReady，表示 fd 立即可用（还没有人在等）。
  • 当 G 要等读时，用 CAS 把 rg 从 pdReady 改成自己的 G 指针，然后 park。
  • fd 就绪/关闭时，netpollready 把 rg/wg 设回 pdReady，并调用 goready 唤醒挂着的 G。

一个 fd 只分配一个 pollDesc，读写各一个等待槽。这也解释了为什么一个 fd 同时只有一个等待读的 G 和一个等待写的 G：conn.Read/conn.Write 在 runtime 层不会有多个 G 同时读同一个 fd（上层 net.TCPConn 的读本来就要求串行）。

阻塞与唤醒：netpollblock 与 netpollgoready

netpollblock 是”把当前 G 挂到 pollDesc 上并休眠”的核心：

// 简化
func netpollblock(pd *pollDesc, mode int32, waitio bool) bool {
    gpp := &pd.rg
    if mode == 'w' { gpp = &pd.wg }

    for {
        old := atomic.Loaduintptr(gpp)
        if old == pdReady {   // 已经就绪
            atomic.Casuintptr(gpp, pdReady, 0)
            return true
        }        // CAS 把 gpp 改成当前 G
        if atomic.Casuintptr(gpp, 0, uintptr(mp.curg)) {
            break
        }
    }
    // 挂起当前 G，等被 goready 唤醒
    gopark(netpollblockcommit, unsafe.Pointer(gpp), waitReasonIO, ...)
    return ... // 被唤醒后检查是否真的就绪
}

注意几个细节：

  • 用 CAS 而不是直接赋值：挂 G 的同时可能有事件到达、要把它改成 pdReady，CAS 保证二者不丢。
  • 挂起前要能失败回滚：gopark 的 commit 回调会在真正停住前把 G 指针写入等待槽；如果这期间 fd 已经就绪，提交失败，G 不 park。
  • 被唤醒不等于 I/O 一定可用：唤醒可能来自 close、超时或用户取消，醒来后要重新检查 rg/wg 状态，不可用就重新等。

唤醒侧 netpollready 反过来：把 rg/wg 原子地设成 pdReady，再对之前挂着的 G 调 goready，把它从 _Gwaiting 改成 _Grunnable。

epoll 后端：注册、等待、卸货

Linux 后端（netpoll_epoll.go）维护一个全局 epoll 实例 epfd：

  • netpollopen：fd 初始化时调 epoll_ctl(EPOLL_CTL_ADD) 注册关注读/写事件，把 pollDesc 的地址通过 event.data 带进去，这样事件返回时能直接找到对应的 pollDesc。
  • netpoll(delay int64)：核心轮询函数，分两种用法：
    • delay < 0：阻塞调 epoll_wait，等够或有事件才返回；
    • delay == 0：非阻塞（epoll_wait timeout=0），有事件立刻返回，没有也立刻返回；
    • delay > 0：带超时阻塞。
  • 取到事件后，对每个就绪 fd 的 pollDesc 调 netpollready，把读/写对应的 G 摘下来收集到一个链表。

返回的 G 链表叫 netpoll 就绪队列。调度器拿到后优先塞给空闲 P 的本地队列，没有空闲 P 就放全局队列，再用 wakep 唤醒一个闲着的 M 来跑。

与调度器的三次握手

netpoller 真正省 CPU 的关键在 findRunnable 里对它的三次调用。这部分在 GMP 笔记里有详细背景，这里聚焦和 netpoll 直接相关的协作：

1. 找活开头，非阻塞 netpoll(0)：每次 findRunnable 第一件事就是调一次非阻塞 netpoll。这时若有网络事件，直接拿到就绪 G 来跑，省去专门唤醒一个 M 的延迟。代价极低，只是一次 epoll_wait(timeout=0) 系统调用。

2. 实在没活、P 要 park 前，再来一次 netpoll(0)：本地队列、全局队列、work stealing、GC worker、timer 全找过一遍都没活，P 准备休眠前再查一次。防止”刚查完没事件，事件就到了，结果 P 睡死过去”。

3. 全系统空闲时，让一个 M 阻塞在 netpoll(-1)：如果所有 P 都没活，不能让一堆 M 忙等。startTheWorld 时起的 sysmon 外，还有一个机制：调度器让唯一的一个 M 去跑阻塞的 netpoll(-1)，其他 M/P 都休眠。这个 M 一直睡在 epoll_wait 上，不占 CPU；网络事件到来时它醒来，把就绪 G 注入调度队列并唤醒空闲 P。

于是整体效果是：

  • 有活干时，P 顺手在两次非阻塞查询里把网络就绪 G 带走，低延迟；
  • 没活干时，只有一个 M 阻塞在 epoll，空闲时 CPU 占用接近零；
  • 从空闲到有连接数据，最多一次 epoll_wait 唤醒就能拉起工作。

NOTE

为什么不是每个 P 一个 epoll 线程 一个阻塞的 epoll_wait 足以监控所有已注册 fd，epoll 本身就是事件多路复用。多个 M 阻塞在同一个 epoll 上只会增加惊群和无意义竞争。Go 选择”全系统空闲时一个 M 阻塞”，用非阻塞轮询覆盖有活干的场景，是延迟和 CPU 之间的折中。

为什么能扛几十万连接

每个等待网络的连接背后只是一个 parked 的 G：

  • 栈初始 2KB，等待期间不增长；
  • 不占 M、不占 P、不参与调度（状态是 _Gwaiting）；
  • 只在 pollDesc 里留一个指针和 epoll 里注册一个事件。

OS 视角，真正”活着”的线程数大约是：

  • GOMAXPROCS 个执行用户代码的 M；
  • sysmon 等少数后台 M；
  • 一个阻塞在 epoll_wait 的 netpoll M；
  • 若干被 syscall/cgo 堵住的 M。

而 epoll_wait 一个线程就能监听上百万 fd。因此几十万连接只对应几十万 parked G，常驻 M 数与连接数无关。

边界与误区

  • 只有网络 fd 走 netpoller。Linux 上 epoll 对 regular file（普通磁盘文件）永远报”就绪”，但磁盘读本身可能在内核里阻塞。这种 read 走 entersyscall 路径：M 与 P 解绑、让 P 去找别的 M 跑，等 I/O 完成再回来，不是 park G。所以磁盘 IO 重的服务 M 数会明显多于 GOMAXPROCS。
  • cgo 调用同理，会占住一个 M，不经过 netpoller。
  • netpoll(0) 也不是零成本：它是一次系统调用。调度器只在”本来就要找活”和”要休眠”这两个点查，不在每个调度间隙都查，避免 syscall 过密。
  • 被唤醒的 G 不保证立刻跑到：它只是变成 runnable 进队列，前面可能还有别的 G；想理解它何时被选中执行，看 GMP 笔记的调度循环。
  • Close 也会唤醒等待者：fd 被关闭时对应 pollDesc 被标记，等在上面的 G 会被唤醒并收到错误，不会永远挂住。
  • Windows IOCP 模型不同：IOCP 是”操作完成后通知”，不是”fd 就绪后通知”，runtime 在 netpoll_windows.go 里把它适配成同样的 pollDesc 抽象，上层 conn.Read 写法不变。
