Go 源码环境与目录地图：Go 1.26.5

TIP

先抓住主干 读 Go 源码最容易犯的错是一头扎进 runtime/proc.go 然后迷路。正确的准备只有三件事：

  1. 固定一个版本和提交（本系列用 go1.26.5，commit c19862e5），所有行号链接都指向它，避免不同版本对不上；
  2. 先有一张目录地图：知道 runtime/、cmd/compile/、internal/ 各管什么，遇到函数能迅速定位到文件；
  3. 掌握四组工具：源码检索（rg/git blame）、编译器决策（-gcflags=-m、GOSSAFUNC）、汇编与符号（objdump/nm）、行为验证（trace/pprof/GODEBUG）。

这篇是后续所有源码笔记的”地图图例”。

固定源码与构建环境

# 克隆并检出本系列使用的精确版本
git clone https://github.com/golang/go.git
cd go
git checkout go1.26.5          # tag
git rev-parse HEAD              # 应为 c19862e5f8415b4f24b189d065ed739517c548ba

# 用一个已安装的稳定 Go 作为 bootstrap 编译它
cd src && ./make.bash           # 产出 ../bin/go
../bin/go version
../bin/go test runtime          # 跑一组最小测试
../bin/go test sync context

要点：

  • 编译 Go 需要一个已安装的 Go（bootstrap toolchain），通常用当前稳定版即可。
  • make.bash 只构建不跑测试；all.bash 构建并跑全量测试（耗时）。
  • 改了 runtime 后用自编译的 ../bin/go 跑实验，避免和系统 Go 混淆。
  • 每个主题建议建一个实验目录，保留 main.go、*_test.go、bench_test.go、以及 trace/profile 输出和一段 README 说明结论。

src 目录总览

主要目录：

目录作用
src/runtime/Go 运行时核心：调度、内存分配、GC、栈、channel、map、defer/panic、netpoll、timer、信号、cgo 桥接
src/cmd/compile/Go 编译器：语法/类型检查、逃逸分析、NIR→SSA、架构相关代码生成
src/cmd/link/链接器：符号解析、重定位、生成 ELF/Mach-O/PE
src/cmd/go/go 命令本身：build/test/mod/vet 等子命令
src/internal/abi/abi.Type、调用约定、栈图等编译器与 runtime 共享的 ABI 定义
src/internal/runtime/、runtime/internal/runtime 内部工具（原子、原子指针、平台抽象）
src/reflect/反射，依赖 runtime 的类型元数据
src/sync/、src/context/、src/net/、src/syscall/直接调用 runtime 的标准库包

runtime 关键文件分组

按主题找文件，而不是按文件名瞎翻：

调度与 GMP

  • proc.go：schedinit、runtime.main、schedule、newproc、mstart、findRunnable、park_m
  • runtime2.go：g/m/p/schedt/defer/panic/sudog 等核心结构体
  • preempt.go：异步抢占

内存与 GC

  • malloc.go：mallocgc、tiny/small/large 分配
  • mcache.go/mcentral.go/mheap.go：三级分配缓存
  • mpagealloc.go/mheap.go：page allocator、arena
  • mgc.go：GC 主循环、trigger、gcStart
  • mgcmark.go：标记 worker、gcDrain、markroot
  • mgcmark_greenteagc.go：Go 1.26 默认 Green Tea 标记路径
  • mbarrier.go：写屏障
  • mgcsweep.go/mgcscavenge.go：清扫与归还物理页
  • mfinal.go：finalizer

栈

  • stack.go：stackalloc、newstack、copystack、shrinkstack
  • asm_amd64.s/stmts_amd64.h：morestack 序言汇编

并发原语

  • chan.go：hchan、send/recv、select
  • select.go：select 实现
  • sync.go：gopark/goready、semaphore
  • rwmutex.go、sema.go（部分在 sync/）

netpoll 与 timer

  • netpoll.go：pollDesc、netpollblock
  • netpoll_epoll.go/netpoll_kqueue.go/netpoll_windows.go：平台后端
  • time.go/timer.go：timer 堆、checkTimers

类型与接口

  • type.go：_type = abi.Type、位图
  • iface.go：eface/iface、itab 缓存、assert
  • error.go、string.go、slice.go：基础类型的 runtime 操作

启动与平台

  • asm_amd64.s：rt0_go、mstart 等汇编
  • sys_linux_amd64.s、os_linux.go：平台/OS 特定
  • cgocall.go、cgo.go：cgo 桥接
  • trace.go、cpuprof.go、memprof.go：诊断

四组必备工具

源码查找

rg "func mallocgc" src/runtime/        # 按内容找
rg -t go "itabTable" src/runtime/
git log -L :schedinit:src/runtime/proc.go   # 追踪某函数的演变
git blame src/runtime/proc.go | grep -i netpoll
gh search code "findRunnable" --repo golang/go   # 跨版本/CL 参考

固定提交行号链接写法： https://github.com/golang/go/blob/<sha>/src/runtime/proc.go#L983-L1101

编译器决策

go build -gcflags='-m=2' ./...        # 逃逸分析、内联、边界检查决策（看两遍 -m）
go build -gcflags='-S' ./x.go        # 输出汇编
GOSSAFUNC=Foo go build ./...         # 生成 ssa.html，逐层看 SSA 优化
go build -gcflags='-d=ssa/check/on'  # 调试用

汇编与符号

go tool objdump -s "main.main" ./bin   # 反汇编指定函数
go tool nm ./bin | rg "runtime.mallocgc"
go tool compile -S x.go > x.s
dlv exec ./bin                        # 源码级调试，可下 runtime 断点

架构后缀决定文件选择：_amd64.s/_arm64.s/_linux.go/_darwin.go；build tag 在文件头 //go:build。

行为验证

GODEBUG=gctrace=1,schedtrace=1000,scheddetail=1 ./bin   # GC/调度器内部日志
GODEBUG=allocfreetrace=1 ./bin                          # 每次分配/释放（量很大）
go test -race ./...                                     # 竞态检测
go test -bench=. -benchmem -cpuprofile cpu.prof -memprofile mem.prof
go tool pprof -http :8080 cpu.prof
GODEBUG=clobberfree=1 ./bin                             # 调试 use-after-free
go tool trace trace.out                                  # 调度/syscall/GC/网络 时间线

注意区分：GODEBUG 的选项随版本变化，用 go doc runtime 或看 runtime/extern.go 里的 godebug 表确认 1.26 支持哪些。

runtime 的特殊约束

读 runtime 源码时要时刻记得它不是普通 Go 代码：

  • //go:nosplit：函数序言不插入栈增长检查。写这种函数时绝不能做可能增长栈的调用，否则栈溢出直接崩溃。用于调度、栈增长自身等最底层路径。
  • //go:systemstack、systemstack(fn)：在当前 M 的 g0 上运行 fn。需要大栈、不能被抢占、不能触发调度的工作（GC、调度本身）用它。
  • mcall(fn)：切到 g0 栈并永不直接返回（fn 负责调度回别的 G）。用于 park_m、recovery 等。
  • getg()：拿到当前 g。要区分 getg()（可能是 g0）和 getg().m.curg（当前用户 G）。getg() 在 g0 与用户 G 之间含义不同。
  • //go:nowritebarrier / //go:nowritebarrierrec：标注函数不允许/或其调用链不允许触发写屏障。GC 标记、栈管理等路径用，因为此时写屏障所需状态可能未就绪。
  • //go:linkname：绕过包可见性，把本地函数链接到另一个包的符号。标准库常用它调 runtime 私有函数（如 time 调 timer 内部）。这是没有 API 承诺的后门，随版本可能变。
  • runtime 内部尽量避免：普通 interface、defer、堆分配、复杂锁顺序、channel 操作——这些都会回调调度器/GC，而 runtime 正处在它们无法工作的上下文中。
  • 写屏障不是锁：它只保证 GC 的指针追踪正确性，不替代原子操作和同步。

推荐的阅读姿势

  • 一次追一条主链：比如”一个 goroutine 从 go func() 到被调度运行”，只追 newproc → newproc1 → ready → schedule → execute → gogo，不要同时铺开 GC、栈、netpoll。
  • 用实验验证结论：读到一个机制，写 30 行代码用 -gcflags=-m、trace 或 GODEBUG 复现它，再回源码。纯读容易产生”以为懂了”。
  • 先读注释再读代码：runtime 源码的头部注释（mgc.go、proc.go、hchan 上方）通常是设计文档，比代码更准确。
  • 行号会漂移：所有链接固定到 go1.26.5 commit；切到别的版本，行号不能直接信。
  • 画自己的图：每个主题画一张数据结构关系图（本篇其他笔记用 Mermaid），比硬记字段有效。
