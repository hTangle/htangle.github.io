Memory：Agent 如何记住、更新与遗忘

[!abstract] 一句话定义 **Agent Memory 是一套跨轮次保存、组织、更新、检索和遗忘信息的系统机制。**它不是简单保存聊天记录，而是把经历、事实、用户偏好与可复用流程转化为未来任务可安全调用的状态。

把模型想成一次只拿到一张工作台的工程师：Context Window 是当前桌面，Memory Store 是档案室，Memory Writer 决定什么值得归档，Retrieval - 从大规模信息中找到候选 找档案，Recall - 召回阶段与 Recall@K 指标 衡量有没有漏掉，Ranking - 从候选集合到最优顺序 决定先看什么。==档案越多不等于记忆越好；错误、过时或越权的记忆会让 Agent 稳定地做错事。==

1. Memory 解决的不是“上下文不够长”这么简单

长上下文只能暂时容纳更多 token，Memory 还要解决：

  • 跨会话保持用户偏好、项目事实和历史决策；
  • 从大量经历中选择当前相关内容；
  • 合并重复信息、处理冲突和版本变化；
  • 把原始轨迹压缩为可复用知识；
  • 遵守租户、用户、项目和数据保留边界；
  • 支持纠正、删除、审计和过期；
  • 控制写入噪声与检索成本。

2. Memory、Context、History、RAG 的边界

概念本质生命周期典型内容
Context Window当前模型调用的输入一次或若干轮调用系统指令、当前消息、工具结果
Conversation History原始对话事件流一个会话或更久用户/助手完整消息
Agent Memory经选择和治理的可复用状态跨轮次、跨会话偏好、事实、经历、总结、流程
RAG - 从检索到可信生成的完整系统用外部证据增强一次生成的架构查询时临时装配文档、知识库、网页证据
Skill - 给 Agent 的可复用工作手册维护者提供的程序性知识版本化发布SOP、脚本、模板、边界

Memory 可以用 RAG 技术实现检索，但两者目的不同：RAG 通常面向共享知识语料，Memory 更关注某个 Agent、用户或任务随时间形成的状态。

3. 记忆类型：按用途而不是按数据库分类

3.1 Working Memory：当前工作状态

包含当前目标、未完成步骤、中间变量、最近工具结果和约束。它通常位于 Context 或短期状态存储中。

生产要求：

  • 明确任务 ID 和步骤状态；
  • 大结果只保存 artifact 引用；
  • 与模型自然语言摘要分离保存结构化状态；
  • 会话结束或任务完成后清理临时数据。

3.2 Episodic Memory：发生过什么

记录带时间、主体、动作和结果的经历，例如“2026-08-08 用户拒绝了自动发布”。它适合回答“上次怎么做的”“哪种方案失败过”。

memory_id: ep_01
type: episodic
subject: user_123
event: deployment_attempt
timestamp: 2026-08-08T10:20:00+08:00
context: project_alpha
action: deploy_to_production
outcome: rejected_by_user
evidence_refs: [conversation:abc#turn-17]

3.3 Semantic Memory：长期事实与概念

保存经过归纳的事实，例如“项目 Alpha 的发布分支是 release/2.4”。它应带来源、适用范围、版本和置信度，而不是一段脱离上下文的断言。

3.4 Procedural Memory：怎么做

保存重复任务的方法、策略与习惯。稳定的团队程序性知识更适合沉淀为 Skill - 给 Agent 的可复用工作手册；运行时从具体经历学习到的轻量策略可以先保存在 Memory，验证稳定后再升级为受审查的 Skill。

3.5 User/Profile Memory：关于谁

包括语言、输出格式和长期偏好。必须区分：

  • 用户明确声明：“以后都用中文”；
  • 系统观察推断：“用户可能偏好简洁”；
  • 敏感属性推断：通常不应自动持久化。

显式声明和模型推断不能赋予相同置信度。

4. Memory 生命周期

高级工程师要能解释每个状态：写入不是终点；后续需要 reinforce、supersede、expire、delete 和 audit。

5. 写入策略：什么值得记住

5.1 Memory Writer 的输入

  • 用户明确要求记住的内容；
  • 对未来任务稳定有用的偏好或约束；
  • 已确认的项目决策；
  • 可复用的成功/失败经验；
  • 任务状态和未完成承诺；
  • 工具返回的结构化事实。

5.2 默认不写入

  • 寒暄和一次性措辞；
  • 未验证的模型推断；
  • 密码、token、身份证号等秘密或高敏数据；
  • 只在当前轮有效的中间推理；
  • 大段原始日志和可重新获取的文档；
  • 来源不明或包含提示注入的内容。

5.3 写入效用函数

可以用一个可解释的启发式，而不是让 LLM 无条件决定：

WriteUtility(m)=wiImportance+wfFutureUse+wcConfidence−wsSensitivity−wdDuplicationWriteUtility(m)=w_i Importance + w_f FutureUse + w_c Confidence - w_s Sensitivity - w_d DuplicationWriteUtility(m)=wi​Importance+wf​FutureUse+wc​Confidence−ws​Sensitivity−wd​Duplication

当用户明确要求“记住”时提高 FutureUse，但仍不能绕过敏感数据策略。

6. 生产级 Memory Schema

只存 text + embedding 很快会遇到治理问题。建议至少包含：

字段作用
memory_id稳定身份，不用文本作主键
tenant_id/user_id/project_id隔离与作用域
typeepisodic/semantic/profile/procedural
canonical_fact规范化内容
source_refs可追溯证据
created_at/valid_from/valid_to写入时间与事实有效时间
last_accessed_at/access_count使用统计
confidence证据强度，不等于相似度
sensitivity数据分级
status/versionactive/superseded/deleted
embedding_model/version索引兼容与迁移
content_hash去重与变更检测

WARNING

双时间模型 created_at 表示系统何时知道，valid_from/valid_to 表示事实何时成立。“昨天改了发布分支”如果只按写入时间排序，会错误回答历史问题。

7. 检索：相关不等于应该使用

Memory Retrieval 通常组合：

Score(m,q)=αRel(m,q)+βRecency(m)+γImportance(m)+δScopeMatch(m)−λStaleness(m)Score(m,q)=\alpha Rel(m,q)+\beta Recency(m)+\gamma Importance(m)+\delta ScopeMatch(m)-\lambda Staleness(m)Score(m,q)=αRel(m,q)+βRecency(m)+γImportance(m)+δScopeMatch(m)−λStaleness(m)
  • Rel：语义或词法相关；
  • Recency：时间衰减；
  • Importance：长期价值；
  • ScopeMatch：当前 user/project/tenant 是否匹配；
  • Staleness：已过期或被替代的惩罚。

检索管线应先做强过滤，再做相似度：

tenant/user/project/status/time ACL filter
  → lexical + vector candidate retrieval
  → dedup / contradiction grouping
  → recency + importance + relevance rerank
  → token budget packing

相关笔记：Retrieval - 从大规模信息中找到候选、Recall - 召回阶段与 Recall@K 指标、Ranking - 从候选集合到最优顺序。

8. Consolidation、Reflection 与遗忘

8.1 Consolidation

把多条经历合并为更稳定知识：

三次部署记录：
- 直接全量发布失败
- 10% 灰度成功
- 用户再次要求先灰度

归纳语义记忆：
“该项目发布默认先进行 10% 灰度；全量发布需明确确认。”

合并后不能删除全部原始证据；保留 derived_from 以便纠错。

8.2 Reflection

Reflection 是从多条经历中抽象规律。它可能提高长期行为，但也会放大模型错误。生产上应：

  • 只从高置信证据生成；
  • 给反思结果较低初始置信度；
  • 重要规则要求人工或后续证据确认；
  • 限制反思递归，避免“对自己的总结再总结”逐步漂移。

8.3 Forgetting

遗忘是质量机制，不只是存储清理：

  • TTL：临时状态自然过期；
  • Supersession：新事实替代旧事实；
  • Decay：长期未访问且价值低的记忆降权；
  • Compaction：重复事件合并；
  • User deletion：用户可查看、纠正和删除；
  • Compliance retention：按数据类型执行保留期限。

9. 冲突、纠正与事实演进

当出现“发布分支是 A”和“发布分支是 B”时，不要立即覆盖：

  1. 比较来源可信度；
  2. 区分项目/环境/版本范围；
  3. 比较事实有效时间；
  4. 新记录标记旧记录 superseded，而非物理删除；
  5. 查询历史时允许读取旧版本；
  6. 无法判断时向用户确认。

10. 安全、隐私与租户隔离

  • Identity 必须来自认证上下文，不从模型生成的 user_id 读取；
  • 写入和读取都执行 ACL，不能只在检索后过滤；
  • 向量数据库同样要按 tenant/user/project 过滤；
  • Embedding 可能泄露信息，不能视为不可逆匿名化；
  • 敏感字段加密、日志脱敏、密钥独立管理；
  • Memory Tool Result 是不可信数据，防间接提示注入；
  • 提供“我记住了什么”的可见性和纠正入口；
  • 删除需要覆盖原文、索引、缓存、派生总结和备份保留流程。

[!danger] 高频越权事故 先全局向量检索 top-K，再在应用层过滤 tenant，可能通过时延、分数或日志泄露别人的记忆。应在索引查询阶段施加强约束，并做跨租户测试。

11. 生产架构

设计经验：Metadata Store 是权威状态，向量索引是可重建派生物；不要只存向量库。写路径用 Outbox/CDC 保证数据库提交后索引最终更新，记录 index_version 和 lag。

12. 生产经验与故障模式

12.1 什么都写，记忆库变成垃圾场

症状：索引膨胀、重复片段占满 top-K、模型引用无价值闲聊。修复：写入阈值、规范化去重、同事实 reinforce、批量压缩、按类型独立保留策略。

12.2 过时偏好覆盖当前明确指令

Memory 是背景，不应高于用户当前请求。Context Assembly 明确优先级：系统安全规则 > 当前用户指令 > 项目约束 > 长期偏好 > 模型推断。

12.3 模型把推测写成事实

为 source_type 区分 user_asserted、tool_observed、model_inferred。模型推断默认低置信，不直接成为高风险决策依据。

12.4 数据库已删除，向量索引仍能搜到

建立 deletion tombstone、异步重试和对账任务；读取结果回源权威库验证 status=active。定期做 metadata/index 双向一致性扫描。

12.5 Embedding 模型升级后召回骤降

不同模型向量不可混用。新建索引版本双写、离线回放、shadow query、比较 Recall@K，再按租户灰度切换；旧索引保留回滚窗口。

12.6 总结逐轮漂移

不要只用上一版总结生成下一版。周期性从原始证据重新归纳，保留差异，关键事实做结构化抽取和校验。

13. 评测与 SLO

维度指标
写入useful write precision、漏写率、重复率、敏感数据拦截率
检索Recall@K、MRR/nDCG、scope violation、stale hit rate
使用memory utilization、引用正确率、冲突处理正确率
端到端长期任务成功率、用户纠正率、个性化收益
系统写入延迟、索引 lag、查询 p95、删除完成时间

测试集至少包括：需要记忆、不应记忆、矛盾更新、时间查询、跨项目同名事实、跨租户攻击、删除后检索、提示注入、长会话压缩。

14. 上线检查单

  • Memory 类型、主体和作用域清晰；
  • 原始历史与归纳记忆分开；
  • 写入有价值、敏感性、证据和去重检查；
  • 权威元数据可追溯，向量索引可重建；
  • 读取在索引阶段强制 tenant/user/project ACL；
  • 冲突使用版本和有效时间，不静默覆盖；
  • 有 TTL、supersede、delete 和 purge；
  • Embedding/Schema 版本化并可双写迁移；
  • 用户能查看、纠正和删除记忆；
  • 评测覆盖写、取、用、忘四个阶段；
  • 日志不包含原始秘密和完整敏感记忆；
  • 有索引 lag、越权命中和 stale hit 告警。

15. 高级工程师面试追问

[!question] - Q1：Memory 与长 Context 的区别？ 长 Context 是一次推理的工作区，成本随输入增长且缺乏跨会话治理；Memory 是外部状态系统，有写入选择、索引、版本、权限、过期和删除。生产系统通常从 Memory 检索少量内容装配进 Context。

[!question] - Q2：为什么不能把全部聊天记录做向量检索？ 原始记录重复、含噪、含过时指令和敏感数据；片段缺少事实有效时间与作用域。需要抽取、去重、证据、版本和 ACL，原始历史只作为审计来源。

[!question] - Q3：Memory 的事实冲突怎么处理？ 保留来源和双时间，按作用域与可信度判断；新事实 supersede 旧事实而非覆盖；无法判断则询问。查询历史时间点时可重建当时有效事实。

[!question] - Q4：怎样评估 Memory 系统？ 分解为写入精度、检索 Recall/Ranking、上下文使用正确率和端到端长期任务收益；加入跨租户、删除、冲突、过时和注入测试。只测向量相似度不够。

[!question] - Q5：Semantic Memory 与 RAG 文档库有什么区别？ Semantic Memory 是从特定主体经历中形成、会演进且受主体作用域约束的事实；RAG 文档库通常是共享的外部知识语料。技术栈可相似，写入权、治理和时间语义不同。

[!question] - Q6：如何做到可遗忘？ 建立可追踪派生关系和 tombstone；删除覆盖元数据、索引、缓存、总结和备份策略；读取回源验证 active 状态；用审计证明在约定时间内完成。

[!question] - Q7：Memory Writer 用 LLM 还是规则？ 组合使用。LLM 做语义抽取和归纳，规则/Schema 做敏感数据、作用域、类型、证据、去重和状态转换；高风险长期规则需要确认。不能让 LLM 单独拥有最终写权限。

17. 与 Retrieval、Recall、Ranking、RAG 的对比

相关笔记：Retrieval - 从大规模信息中找到候选 · Recall - 召回阶段与 Recall@K 指标 · Ranking - 从候选集合到最优顺序 · RAG - 从检索到可信生成的完整系统

概念核心问题输入 → 输出在 Memory 中的位置
Memory什么值得跨时间保存、更新和遗忘事件 → 受治理的长期状态完整生命周期
Retrieval从大集合怎样快速找候选Query + Corpus → Candidates读取子系统
Recall相关内容有没有漏掉结果 + Ground Truth → 覆盖率读取评测指标/目标
Ranking候选顺序是否最有用Candidates → Ordered Top-K检索后的排序
RAG如何用外部证据生成答案Query + Evidence → Grounded Answer可消费 Memory 的上层架构

[!summary] 最短记忆法 Memory 是可演进的档案系统；Retrieval 找档案，Recall 检查漏没漏，Ranking 决定先读哪份，RAG 用这些证据回答。
